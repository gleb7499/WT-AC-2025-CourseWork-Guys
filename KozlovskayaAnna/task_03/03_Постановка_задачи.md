# 3 Постановка задачи

## 3.1 Описание предметной области

Система «Zafid» предназначена для автоматизации процессов организации и проведения мероприятий различных типов: конференций, встреч, семинаров, воркшопов и других событий. Предметная область включает следующие основные понятия: события (мероприятия), пользователи системы, участники событий, спикеры, билеты и приглашения.

События характеризуются названием, описанием, местом проведения, датами начала и окончания, максимальной вместимостью и списком прикреплённых спикеров. Каждое событие может иметь визуальное оформление в виде обложки и детальное описание программы в формате размеченного текста.

Пользователи системы разделяются на две категории: обычные пользователи и администраторы. Обычные пользователи могут просматривать список событий, регистрироваться на мероприятия, получать билеты и приглашать других участников. Администраторы обладают расширенными правами для создания и редактирования событий, управления пользователями и спикерами.

Участники представляют собой связь между пользователем и событием, фиксирующую факт регистрации на мероприятие. Билеты выдаются зарегистрированным участникам и содержат уникальный код для идентификации. Приглашения позволяют пользователям рекомендовать события друг другу, формируя социальный аспект системы.

## 3.2 Исходные данные

Для функционирования системы используются следующие типы данных:

Пользовательские данные включают электронную почту, имя, хешированный пароль и роль пользователя в системе. Электронная почта служит уникальным идентификатором пользователя при аутентификации.

Данные событий содержат текстовую информацию (название, описание, место проведения), временные характеристики (даты начала и окончания), численные параметры (вместимость), ссылки на изображения обложек и связи со спикерами. Описание события поддерживает форматирование через Markdown с последующим преобразованием в HTML для безопасного отображения.

Информация о спикерах включает имя, биографию, контактные данные (телеграм, телефон, электронная почта) и фотографию. Спикеры связываются с событиями через ссылки на их идентификаторы.

Билеты содержат ссылки на участника, пользователя и событие, а также восьмизначный числовой код для идентификации. Приглашения хранят информацию о приглашающем пользователе, приглашённом пользователе и событии.

## 3.3 Функциональные требования

Система должна реализовывать следующие функциональные возможности, сгруппированные по категориям пользователей.

### 3.3.1 Требования для неавторизованных пользователей

Неавторизованные посетители должны иметь возможность просматривать список доступных мероприятий с базовой информацией о каждом событии. Система обеспечивает регистрацию новых пользователей с проверкой уникальности электронной почты и требованиями к надёжности пароля. Предусмотрена функция входа в систему для зарегистрированных пользователей с проверкой учётных данных.

### 3.3.2 Требования для авторизованных пользователей

Авторизованные пользователи получают доступ к расширенному функционалу. Система должна предоставлять детальную информацию о мероприятиях, включая программу, список спикеров с биографиями и контактными данными. Реализована возможность регистрации на события с автоматической проверкой доступности мест и предотвращением повторной регистрации.

После успешной регистрации на мероприятие система автоматически генерирует электронный билет с уникальным восьмизначным кодом. Пользователи могут просматривать список своих билетов и отменять регистрацию на события до их начала. Функция приглашений позволяет рекомендовать мероприятия другим зарегистрированным пользователям системы, при этом исключается возможность отправки приглашения самому себе и дублирования приглашений.

### 3.3.3 Требования для администраторов

Административная панель предоставляет полный контроль над содержимым системы. Администраторы могут создавать новые события, указывая все необходимые параметры, включая загрузку изображений обложек и формирование описания с использованием разметки Markdown. Реализовано редактирование существующих событий с частичным обновлением полей и удаление событий из системы.

Управление спикерами включает создание профилей с биографической информацией и контактными данными, редактирование профилей и удаление записей. Спикеры связываются с событиями при создании или редактировании мероприятий.

Функционал управления пользователями позволяет администраторам создавать новые учётные записи с назначением ролей, редактировать информацию о пользователях, изменять роли и удалять учётные записи. Предусмотрена возможность сброса паролей пользователей с проверкой на совпадение с текущим паролем.

## 3.4 Нефункциональные требования

### 3.4.1 Требования к производительности

Система должна обеспечивать приемлемое время отклика для пользовательских операций. Отображение списка событий и деталей мероприятия должно происходить не более чем за три секунды при стандартной нагрузке. Операции регистрации и аутентификации выполняются в течение двух секунд.

### 3.4.2 Требования к безопасности

Для защиты пользовательских данных применяется хеширование паролей с использованием алгоритма bcrypt. Аутентификация реализована на основе JSON Web Token с хранением токенов в HTTP-only cookies для защиты от XSS-атак [2]. Сессии имеют ограниченный срок действия, задаваемый через переменные окружения.

Все пользовательские входные данные проходят валидацию на стороне сервера для предотвращения инъекций и других типов атак. Контент, создаваемый пользователями в Markdown, санитизируется перед преобразованием в HTML и отображением. Настроена политика CORS для ограничения доступа к API только с доверенных доменов.

### 3.4.3 Требования к надёжности

Система использует Mongoose для взаимодействия с MongoDB, что обеспечивает валидацию схем данных и предотвращение несогласованности. Реализована централизованная обработка ошибок с возвратом структурированных ответов клиенту. Логирование всех входящих запросов позволяет отслеживать работу системы и диагностировать проблемы.

### 3.4.4 Требования к масштабируемости

Архитектура «клиент-сервер» с разделением фронтенда и бэкенда обеспечивает возможность независимого масштабирования компонентов. Использование MongoDB позволяет горизонтальное масштабирование базы данных при увеличении объёма данных.

### 3.4.5 Требования к совместимости

Клиентская часть должна корректно работать в современных веб-браузерах, включая Chrome, Firefox, Safari и Edge последних версий. Интерфейс адаптируется под различные размеры экранов благодаря применению Tailwind CSS и адаптивной вёрстки.

## 3.5 Ограничения и допущения

В текущей реализации системы присутствуют следующие ограничения.

Отсутствует интеграция с внешними платёжными системами, все билеты являются бесплатными. Не реализована отправка уведомлений по электронной почте или через другие каналы связи. Система не поддерживает многоязычный интерфейс, весь контент представлен на русском и английском языках в зависимости от контекста.

Управление изображениями реализовано через интеграцию с Amazon S3, однако полная функциональность загрузки и обработки изображений требует корректной настройки переменных окружения. Отсутствует функция восстановления пароля через электронную почту.

Предполагается, что система будет использоваться в доверенной среде с модерацией контента администраторами. Автоматическая модерация пользовательского контента не реализована. Нагрузочное тестирование и оптимизация для высоконагруженных сценариев не проводились в рамках данной работы.

## 3.6 Критерии приёмки MVP

Минимально жизнеспособный продукт считается готовым при выполнении следующих критериев:

1. Реализован полный цикл работы с пользователями: регистрация, вход в систему, выход из системы.

2. Доступен просмотр списка событий с базовой информацией для всех посетителей и детальная информация для авторизованных пользователей.

3. Авторизованные пользователи могут регистрироваться на события и получать билеты с уникальными кодами.

4. Реализована административная панель с возможностью создания, редактирования и удаления событий, спикеров и пользователей.

5. Функционирует система приглашений, позволяющая пользователям рекомендовать события друг другу.

6. API предоставляет endpoints для всех основных операций: `/api/events`, `/api/tickets`, `/api/invitations`, `/api/user`, `/api/admin/events`, `/api/admin/speakers`, `/api/admin/users`.

7. Данные корректно сохраняются в базе данных MongoDB, связи между сущностями поддерживаются через ссылки.

8. Реализована базовая валидация данных на сервере и обработка типовых ошибок.

9. Приложение может быть развёрнуто локально с использованием инструкций из документации.

10. Интерфейс адаптирован для работы на экранах различных размеров.

Выполнение данных критериев обеспечивает базовую функциональность системы, достаточную для организации небольших мероприятий и демонстрации ключевых возможностей платформы.
