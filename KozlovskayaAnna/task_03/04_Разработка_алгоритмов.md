# 4 Разработка алгоритмов

## 4.1 Описание сущностей и связей

Модель данных системы включает шесть основных сущностей, связанных между собой отношениями различных типов.

### 4.1.1 Сущность User (Пользователь)

Сущность User представляет зарегистрированных пользователей системы. Каждый пользователь характеризуется следующими атрибутами: уникальный идентификатор, электронная почта (обязательное уникальное поле), имя (необязательное поле), хешированный пароль и роль в системе. Роль принимает одно из двух значений: обычный пользователь или администратор. Автоматически сохраняются метки времени создания и последнего обновления записи.

### 4.1.2 Сущность Event (Событие)

Сущность Event описывает мероприятия. Атрибуты включают: уникальный идентификатор, название (обязательное поле), вложенный объект обложки с именем файла и альтернативным текстом, вложенный объект контента с исходным текстом в формате Markdown и преобразованным HTML, максимальную вместимость (числовое значение по умолчанию сто участников), место проведения, массив ссылок на спикеров, дату и время начала мероприятия (обязательное поле), дату и время окончания (обязательное поле). События также имеют автоматические метки времени создания и обновления.

### 4.1.3 Сущность Speaker (Спикер)

Сущность Speaker хранит информацию о выступающих. Атрибуты: уникальный идентификатор, имя (обязательное поле), биография (обязательное текстовое поле), вложенный объект контактов с полями для Telegram, телефона и электронной почты (все необязательные), вложенный объект фотографии с именем файла и альтернативным текстом. Записи включают метки времени создания и обновления.

### 4.1.4 Сущность Attendee (Участник)

Сущность Attendee фиксирует факт регистрации пользователя на событие. Содержит минимальный набор атрибутов: уникальный идентификатор, ссылку на пользователя и ссылку на событие. Связи реализованы через механизм ссылок MongoDB на коллекции User и Event. Автоматически сохраняются метки времени регистрации.

### 4.1.5 Сущность Ticket (Билет)

Сущность Ticket представляет электронные билеты участников. Атрибуты включают: уникальный идентификатор, ссылку на запись участника, ссылку на пользователя, ссылку на событие и восьмизначный числовой код для идентификации билета. Билет создаётся автоматически при регистрации пользователя на мероприятие. Связи с другими сущностями обеспечивают целостность данных.

### 4.1.6 Сущность Invitation (Приглашение)

Сущность Invitation фиксирует приглашения между пользователями. Содержит: уникальный идентификатор, ссылку на приглашённого пользователя, ссылку на пользователя, отправившего приглашение, и ссылку на событие. Временные метки позволяют отслеживать момент создания приглашения.

### 4.1.7 Связи между сущностями

Между сущностями установлены следующие отношения. User связан с Event через Attendee (многие-ко-многим), что позволяет одному пользователю регистрироваться на несколько событий, и одно событие может иметь множество участников. Attendee связан с Ticket отношением один-к-одному, каждая регистрация порождает ровно один билет.

Event связан со Speaker отношением многие-ко-многим, реализованным через массив ссылок на спикеров в документе события. Один спикер может выступать на нескольких мероприятиях, и одно мероприятие может иметь несколько спикеров.

Invitation создаёт связи между двумя User и одним Event, реализуя отношение многие-ко-многим с дополнительными атрибутами. Один пользователь может отправить множество приглашений и получить множество приглашений от других пользователей.

## 4.2 Алгоритм регистрации пользователя на событие

Процесс регистрации пользователя на мероприятие является ключевой операцией системы и включает несколько последовательных этапов с проверками корректности данных.

На входе алгоритм получает идентификатор события и идентификатор пользователя из аутентификационного токена. Первым шагом выполняется проверка наличия обязательных параметров, при их отсутствии возвращается ошибка с соответствующим сообщением.

Далее производится поиск события в базе данных по указанному идентификатору. Если событие не найдено, процесс прерывается с сообщением об ошибке. Для найденного события проверяется текущее количество зарегистрированных участников путём подсчёта записей в коллекции Attendee для данного события. Если число участников достигло максимальной вместимости, возвращается ошибка о недоступности регистрации.

Следующий шаг — проверка на повторную регистрацию. Система ищет существующую запись Attendee с комбинацией идентификатора пользователя и идентификатора события. При обнаружении такой записи процесс завершается с ошибкой, информирующей о том, что пользователь уже зарегистрирован.

Если все проверки пройдены успешно, создаётся новая запись в коллекции Attendee, связывающая пользователя с событием. После этого генерируется уникальный восьмизначный числовой код для билета с использованием генератора случайных чисел. Проверяется уникальность сгенерированного кода среди существующих билетов, при совпадении генерируется новый код.

Затем создаётся запись Ticket со ссылками на созданную запись участника, пользователя, событие и сгенерированным кодом. Новый билет сохраняется в базе данных, и его данные возвращаются клиенту в качестве результата операции.

В случае возникновения ошибок на любом этапе выполнения алгоритма транзакция откатывается, и клиенту возвращается информация о причине сбоя.

## 4.3 Алгоритм аутентификации пользователя

Механизм аутентификации обеспечивает безопасный доступ пользователей к защищённым ресурсам системы и основан на использовании JWT-токенов [3].

### 4.3.1 Процесс входа в систему

При попытке входа пользователь предоставляет электронную почту и пароль. Сначала выполняется валидация входных данных, проверяется наличие обоих полей и минимальная длина пароля не менее шести символов. При нарушении этих требований возвращается ошибка валидации.

Далее производится поиск пользователя в базе данных по электронной почте. Если пользователь не найден, возвращается сообщение об ошибке. Для найденного пользователя извлекается хешированный пароль из базы данных и сравнивается с предоставленным паролем с использованием функции сравнения bcrypt. При несовпадении паролей процесс прерывается с соответствующей ошибкой.

После успешной проверки учётных данных генерируется JWT-токен, содержащий идентификатор пользователя в качестве полезной нагрузки. Токен подписывается секретным ключом из переменных окружения и имеет ограниченный срок действия, определяемый конфигурацией. Сгенерированный токен помещается в HTTP-only cookie, что предотвращает доступ к нему через JavaScript на клиентской стороне и защищает от XSS-атак.

Клиенту возвращается успешный ответ с базовой информацией о пользователе без конфиденциальных данных, таких как пароль и роль.

### 4.3.2 Проверка токена при запросах

Каждый защищённый endpoint системы использует middleware для проверки аутентификации. При поступлении запроса middleware извлекает JWT-токен из cookies запроса. Если токен отсутствует, запрос отклоняется с кодом неавторизован.

Для присутствующего токена выполняется верификация подписи с использованием того же секретного ключа, что и при генерации. Если подпись недействительна или срок действия токена истёк, возвращается ошибка с требованием повторной аутентификации.

При успешной верификации из токена извлекается идентификатор пользователя и добавляется в объект запроса, делая его доступным для последующих обработчиков. Запрос передаётся дальше по цепочке обработки.

### 4.3.3 Дополнительная проверка роли администратора

Для административных endpoints применяется дополнительный middleware проверки роли. После стандартной проверки токена извлекается идентификатор пользователя из объекта запроса. Выполняется запрос к базе данных для получения роли пользователя.

Если роль не соответствует администратору, доступ запрещается с возвратом ошибки маршрут не найден для сокрытия факта существования административных endpoints от обычных пользователей. При соответствии роли запрос обрабатывается целевым контроллером.

## 4.4 Алгоритм создания события администратором

Создание нового события доступно только пользователям с ролью администратора и включает валидацию множества параметров.

На входе алгоритм получает объект с данными события: название, информацию об обложке, контент в формате Markdown, вместимость, место проведения, массив идентификаторов спикеров, дату начала и дату окончания. Первым шагом проверяется наличие всех обязательных полей, отсутствующие поля фиксируются, и при их наличии возвращается ошибка с перечислением.

Выполняется валидация дат начала и окончания мероприятия. Проверяется корректность формата дат и их преобразование в объекты Date. Если даты некорректны, возвращается соответствующая ошибка. Далее проверяется логическая корректность: дата окончания должна быть строго позже даты начала. Нарушение этого условия приводит к ошибке.

Вместимость мероприятия валидируется как положительное числовое значение. Отрицательные числа и нечисловые значения вызывают ошибку. Контент в формате Markdown проходит санитизацию для удаления потенциально опасных конструкций, затем преобразуется в HTML с использованием библиотеки markdown-it с настроенным безопасным режимом.

После прохождения всех проверок создаётся новый документ в коллекции Event с указанными параметрами. MongoDB автоматически генерирует уникальный идентификатор, устанавливает временные метки создания. Созданное событие сохраняется в базе данных, и его данные возвращаются клиенту для подтверждения успешного создания.

## 4.5 Алгоритм отправки приглашения

Функция приглашений реализует социальный аспект системы, позволяя пользователям рекомендовать события друг другу.

Алгоритм получает на вход идентификатор события, идентификатор приглашаемого пользователя и идентификатор пригласившего пользователя из аутентификационного токена. Проверяется наличие всех обязательных параметров.

Первая бизнес-проверка — предотвращение самоприглашения. Если идентификаторы пригласившего и приглашаемого совпадают, возвращается ошибка. Затем выполняется поиск в коллекции Invitation для проверки на дублирование. Ищется запись с идентичной комбинацией приглашаемого пользователя, пригласившего пользователя и события. При обнаружении такой записи процесс прерывается с сообщением о том, что приглашение уже отправлено.

Опционально может выполняться проверка существования приглашаемого пользователя и события в базе данных для предотвращения создания ссылок на несуществующие сущности. При прохождении всех проверок создаётся новая запись Invitation со всеми указанными ссылками. Запись сохраняется в базе данных, и клиенту возвращается подтверждение успешной отправки приглашения.

## 4.6 Алгоритм получения списка событий с фильтрацией

Отображение списка событий является основной точкой входа в систему и должно эффективно обрабатывать различные сценарии использования.

Алгоритм принимает необязательные параметры фильтрации и сортировки из query-параметров запроса. Формируется объект запроса к базе данных с базовыми условиями выборки. Если пользователь авторизован, информация об авторизации доступна для персонализации результатов.

Для неавторизованных пользователей возвращаются только базовые поля событий: идентификатор, название, краткое описание, дата начала, обложка. Детальная информация, включая полное содержание и список спикеров, скрыта.

Для авторизованных пользователей расширяется набор возвращаемых полей, включая полное описание. Выполняется запрос к базе данных с применением метода populate для автоматического заполнения информации о связанных спикерах вместо простых ссылок. Результаты сортируются по дате начала мероприятия в порядке возрастания для отображения ближайших событий в начале списка.

Полученные данные форматируются в структурированный JSON-ответ и отправляются клиенту. В случае ошибок при выполнении запроса к базе данных клиенту возвращается сообщение об ошибке сервера с соответствующим статусом.

## 4.7 Обеспечение транзакционности и согласованности данных

Хотя MongoDB не требует явного объявления транзакций для одиночных операций, система обеспечивает согласованность данных через несколько механизмов.

При регистрации пользователя на событие создание записей Attendee и Ticket выполняется последовательно с проверками на каждом этапе. В случае ошибки при создании билета после успешного создания участника предусмотрен откат через удаление созданной записи участника.

Валидация на уровне схем Mongoose предотвращает сохранение некорректных данных в базу. Обязательные поля, типы данных и форматы проверяются автоматически перед выполнением операций сохранения. Уникальность электронной почты пользователей обеспечивается через индексы на уровне базы данных.

Ссылочная целостность поддерживается через использование ObjectId в качестве ссылок между коллекциями. При удалении основной сущности система проверяет наличие зависимых записей и либо удаляет их каскадно, либо предотвращает удаление с возвратом предупреждения. Например, удаление события влечёт удаление связанных записей участников, билетов и приглашений.

Блокировки на уровне документов в MongoDB предотвращают одновременное изменение одних и тех же данных несколькими запросами, что важно при регистрации нескольких пользователей на событие с ограниченной вместимостью одновременно.
