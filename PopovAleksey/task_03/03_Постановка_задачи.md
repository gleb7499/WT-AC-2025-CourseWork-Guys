# 1 Постановка задачи

## 1.1 Исходные данные

Система управления бронированием аудиторий предназначена для автоматизации процесса распределения аудиторного фонда учебного заведения между пользователями различных категорий. Входными данными для системы являются сведения о пользователях, аудиториях и бронированиях. Данные хранятся в реляционной базе данных PostgreSQL и представлены в виде взаимосвязанных таблиц.

Сущность «Пользователь» включает уникальный идентификатор, имя пользователя, адрес электронной почты, хешированный пароль, роль и временные метки создания и обновления записи. Роль пользователя принимает одно из трёх значений: администратор, преподаватель или студент. Для обеспечения уникальности имена пользователей и адреса электронной почты не могут повторяться в пределах системы.

Сущность «Аудитория» содержит уникальный идентификатор, название, описание, вместимость, перечень оборудования, расположение и временные метки создания и обновления. Название аудитории является уникальным в рамках системы. Вместимость представлена целым числом, обозначающим количество посадочных мест.

Сущность «Бронирование» включает уникальный идентификатор, ссылки на аудиторию и пользователя, время начала и окончания бронирования, цель использования аудитории, статус бронирования и временные метки создания и обновления. Статус бронирования может принимать значение активного или отменённого. Время начала должно быть строго меньше времени окончания. Длительность бронирования ограничена четырьмя часами для всех пользователей с возможностью установления дополнительных лимитов в зависимости от роли.

Для обеспечения безопасности и отслеживания действий пользователей система использует сущности «Токен обновления» и «Журнал аудита». Токен обновления содержит идентификатор, ссылку на пользователя, хешированное значение токена, время истечения действия и метку создания. Журнал аудита фиксирует тип сущности, её идентификатор, выполненное действие, идентификатор пользователя, изменения в формате JSON, причину действия и время создания записи.

Между сущностями установлены следующие связи. Один пользователь может создать несколько бронирований. Одна аудитория может иметь множество бронирований в различные временные периоды. Пользователь может обладать несколькими токенами обновления и быть автором множества записей в журнале аудита. Удаление пользователя влечёт каскадное удаление связанных с ним бронирований, токенов и записей аудита. Удаление аудитории приводит к удалению всех связанных бронирований.

## 1.2 Функциональные требования

Система должна обеспечивать выполнение следующих функциональных требований минимально жизнеспособного продукта. Пользователи всех ролей должны иметь возможность регистрации в системе с указанием имени пользователя, адреса электронной почты и пароля. После успешной регистрации пользователю присваивается роль студента по умолчанию. Вход в систему осуществляется по адресу электронной почты и паролю. После успешной аутентификации пользователь получает токен доступа и токен обновления для поддержания сеанса работы.

Просмотр списка аудиторий и расписания их занятости доступен всем категориям пользователей без ограничений. Список аудиторий должен содержать название, вместимость, оборудование и расположение каждого помещения. Расписание отображает занятые временные слоты с указанием времени начала и окончания бронирования. Система должна предоставлять возможность фильтрации аудиторий по вместимости, оборудованию и расположению.

Создание бронирования доступно аутентифицированным пользователям. При создании бронирования пользователь указывает аудиторию, время начала и окончания, цель использования помещения. Система должна автоматически проверять наличие конфликтов с существующими активными бронированиями выбранной аудитории. Если в указанный временной интервал аудитория уже забронирована, система отклоняет запрос и возвращает информацию о конфликтующих бронированиях. Длительность бронирования для студентов ограничена двумя часами, для преподавателей — четырьмя часами. Администраторы могут создавать бронирования без ограничения по длительности.

Пользователи имеют право просматривать список своих бронирований, отменять и переносить их на другое время. Отмена бронирования изменяет его статус на отменённый. Перенос бронирования требует указания нового времени начала и окончания с соблюдением всех правил валидации и проверки конфликтов. Администраторы обладают правом отменять и переносить бронирования любых пользователей. При отмене чужого бронирования администратор обязан указать причину действия.

Администраторы должны иметь возможность управления аудиториями, включая создание, редактирование и удаление записей. При удалении аудитории система должна предупреждать о наличии связанных активных бронирований. Администраторы управляют пользователями, включая создание учётных записей, изменение ролей и удаление пользователей. Система должна предоставлять администраторам доступ к статистике использования аудиторий, включая количество бронирований за заданный период, общее количество часов использования и процент загруженности помещения.

Система должна регистрировать все критические операции в журнале аудита, включая создание, обновление и отмену бронирований, создание и удаление пользователей, создание и удаление аудиторий. Для каждой операции фиксируется тип сущности, её идентификатор, выполненное действие, идентификатор пользователя, внесённые изменения и время выполнения операции.

## 1.3 Нефункциональные требования

Безопасность системы обеспечивается следующими мерами. Пароли пользователей хешируются с использованием алгоритма bcrypt с фактором стоимости двенадцать. Аутентификация реализована на основе токенов JWT. Токен доступа имеет срок действия пятнадцать минут, токен обновления — семь дней. Токены обновления хранятся в базе данных в хешированном виде. Для защиты HTTP-заголовков применяется библиотека Helmet. Политика CORS настроена с явным указанием разрешённых источников запросов, использование подстановочного символа запрещено. Все входные данные валидируются на серверной стороне с применением библиотеки Zod для предотвращения инъекций и передачи некорректных данных.

Производительность системы должна обеспечивать обработку типичных запросов пользователей в приемлемые сроки. Время отклика на запросы чтения данных не должно превышать двух секунд при нормальной нагрузке. Запросы на создание и изменение данных должны обрабатываться не более пяти секунд. Для повышения производительности операций с бронированиями применяются индексы базы данных по полям идентификатора аудитории, времени начала и окончания, статуса бронирования.

Система должна быть доступна для работы в современных веб-браузерах, поддерживающих стандарты HTML5, CSS3 и JavaScript ES6. Интерфейс пользователя должен быть адаптивным и корректно отображаться на устройствах с различными размерами экрана. Серверная часть приложения разрабатывается на платформе Node.js версии восемнадцать или выше. Для работы системы требуется наличие сервера базы данных PostgreSQL.

## 1.4 Ограничения и допущения

В рамках разработки минимально жизнеспособного продукта приняты следующие ограничения и допущения. Система не реализует функциональность отправки уведомлений пользователям о создании, изменении или отмене бронирований. Экспорт расписания в формат iCalendar для интеграции с внешними календарными приложениями не входит в состав минимально жизнеспособного продукта и рассматривается как дополнительная возможность.

Система не поддерживает массовое создание бронирований и рекуррентные бронирования для периодически повторяющихся событий. Каждое бронирование создаётся отдельным запросом. Взаимодействие с системой осуществляется только через веб-интерфейс, мобильные приложения не разрабатываются. Система предполагает работу в контролируемой сетевой среде учебного заведения без публичного доступа из глобальной сети Интернет.

Предполагается, что все пользователи системы действуют добросовестно и не предпринимают попыток несанкционированного доступа к данным или функциональности системы. Административный персонал несёт ответственность за корректность вводимых данных об аудиториях и пользователях. Система не включает средства резервного копирования данных, эта задача возлагается на администраторов инфраструктуры.

## 1.5 Чеклист приёмки минимально жизнеспособного продукта

Для подтверждения соответствия реализованной системы требованиям минимально жизнеспособного продукта необходимо выполнение следующих критериев. Пользователи должны иметь возможность регистрации и входа в систему с получением токенов доступа. Реализована ролевая модель доступа с тремя категориями пользователей: администраторами, преподавателями и студентами. Каждая роль обладает определённым набором прав на выполнение операций.

Все пользователи могут просматривать список аудиторий с фильтрацией по параметрам и расписание занятости аудиторий. Аутентифицированные пользователи создают бронирования с указанием аудитории, времени и цели использования. Система автоматически проверяет конфликты бронирований и отклоняет запросы при обнаружении пересечений временных интервалов для одной аудитории. Ограничения длительности бронирования применяются в зависимости от роли пользователя: два часа для студентов, четыре часа для преподавателей, без ограничений для администраторов.

Пользователи имеют возможность просматривать свои бронирования, отменять и переносить их на другое время с соблюдением всех правил валидации и проверки конфликтов. Администраторы могут отменять и переносить бронирования любых пользователей с обязательным указанием причины действия. Реализовано управление аудиториями, включая создание, редактирование и удаление записей с проверкой на наличие активных бронирований перед удалением.

Администраторы имеют доступ к статистике использования аудиторий, включающей количество бронирований, общее время использования и процент загруженности за заданный период. Все критические операции регистрируются в журнале аудита с фиксацией типа операции, идентификаторов сущностей, пользователя и времени выполнения.

Обеспечены требования безопасности, включая хеширование паролей с использованием bcrypt, применение JWT для аутентификации и авторизации, валидацию входных данных на серверной стороне, защиту HTTP-заголовков посредством Helmet, настройку политики CORS с явным указанием разрешённых источников. Система развёртывается в локальном окружении разработки с использованием Docker или непосредственным запуском серверных процессов и доступна для тестирования через веб-браузер.
