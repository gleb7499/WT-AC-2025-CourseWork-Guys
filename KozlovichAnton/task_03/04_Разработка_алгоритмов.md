# 4 Разработка алгоритмов

## 4.1 Описание сущностей и связей

Модель данных системы базируется на реляционной схеме, реализованной средствами PostgreSQL и описанной с использованием Prisma ORM [7]. Основные сущности и их атрибуты представлены ниже.

Сущность User (пользователь) является центральной в системе аутентификации и авторизации. Атрибуты: id — уникальный идентификатор типа UUID, генерируется автоматически; username — имя пользователя, строка длиной от 3 до 20 символов, уникальное значение; email — адрес электронной почты, уникальное значение, используется для входа в систему; password_hash — хеш пароля, сгенерированный алгоритмом bcrypt; role — глобальная роль пользователя, принимает значения admin, manager, developer, user; created_at — временная метка создания записи.

Сущность Project (проект) представляет организационную единицу для группировки багов. Атрибуты: id — уникальный идентификатор типа UUID; name — название проекта, строка от 3 до 100 символов; description — текстовое описание проекта, необязательное поле; owner_id — внешний ключ на User.id, указывает владельца проекта; is_public — логический флаг публичности проекта, по умолчанию false; created_at и updated_at — временные метки создания и последнего обновления.

Сущность ProjectMember (участник проекта) реализует связь многие-ко-многим между пользователями и проектами с дополнительным атрибутом роли. Атрибуты: id — уникальный идентификатор; project_id — внешний ключ на Project.id, каскадное удаление; user_id — внешний ключ на User.id, каскадное удаление; role — роль участника в проекте, принимает значения owner, manager, developer, viewer; joined_at — временная метка добавления участника. Для пары (project_id, user_id) установлено ограничение уникальности, предотвращающее дублирование участников.

Сущность Bug (баг) описывает дефект или задачу в рамках проекта. Атрибуты: id — уникальный идентификатор; project_id — внешний ключ на Project.id, обязательное поле; title — название бага, строка от 3 до 200 символов; description — подробное описание, текстовое поле; status — статус обработки, принимает значения new, in_progress, testing, done, closed, по умолчанию new; priority — приоритет, принимает значения low, medium, high, critical, по умолчанию medium; assigned_to — внешний ключ на User.id, необязательное поле, указывает назначенного исполнителя, при удалении пользователя устанавливается NULL; created_by — внешний ключ на User.id, обязательное поле, указывает автора бага; created_at и updated_at — временные метки.

Сущность Attachment (вложение) представляет файл, прикреплённый к багу. Атрибуты: id — уникальный идентификатор; bug_id — внешний ключ на Bug.id, каскадное удаление; filename — имя файла, строка; file_path — путь к файлу в локальной файловой системе сервера; uploaded_by — внешний ключ на User.id, указывает пользователя, загрузившего файл; uploaded_at — временная метка загрузки.

Сущность Comment (комментарий) представляет текстовую запись в обсуждении бага. Атрибуты: id — уникальный идентификатор; bug_id — внешний ключ на Bug.id, каскадное удаление; author_id — внешний ключ на User.id, указывает автора комментария; content — текст комментария, строка от 1 до 2000 символов; created_at — временная метка создания.

Сущность RefreshToken (токен обновления) используется для реализации механизма обновления токенов доступа. Атрибуты: id — уникальный идентификатор; user_id — внешний ключ на User.id, каскадное удаление; token_hash — хеш токена обновления; family — семейство токенов, идентификатор цепочки ротации; expires_at — временная метка истечения срока действия; created_at — временная метка создания; revoked — логический флаг отзыва токена.

Связи между сущностями реализованы через внешние ключи с соответствующими политиками каскадного удаления и обновления. Один пользователь может владеть многими проектами (User 1:N Project через owner_id). Многие пользователи могут участвовать во многих проектах (User M:N Project через ProjectMember). Один проект содержит многие баги (Project 1:N Bug). Один пользователь создаёт многие баги (User 1:N Bug через created_by). Один пользователь может быть назначен исполнителем многих багов (User 1:N Bug через assigned_to). Один баг имеет многие вложения (Bug 1:N Attachment). Один баг имеет многие комментарии (Bug 1:N Comment). Один пользователь загружает многие вложения (User 1:N Attachment). Один пользователь пишет многие комментарии (User 1:N Comment).

Для обеспечения производительности запросов в схеме базы данных определены индексы по часто используемым полям. Индексы созданы по следующим полям: ProjectMember.project_id, ProjectMember.user_id, Bug.project_id, Bug.status, Bug.priority, Bug.assigned_to, Bug.created_by, Attachment.bug_id, Comment.bug_id. Уникальные индексы установлены на User.username, User.email, составной индекс на (ProjectMember.project_id, ProjectMember.user_id).

## 4.2 Алгоритм аутентификации и управления токенами

Аутентификация пользователей реализована с использованием JSON Web Tokens (JWT) и включает два типа токенов: краткосрочные токены доступа (access tokens) и долгосрочные токены обновления (refresh tokens) [3]. Данный подход обеспечивает баланс между безопасностью и удобством использования.

Алгоритм регистрации нового пользователя выполняется следующим образом. Принимаются входные данные: username, email, password. Выполняется валидация входных данных: username от 3 до 20 символов, email соответствует формату электронной почты, password не менее 8 символов и содержит заглавную букву, строчную букву и цифру. Проверяется уникальность username и email в базе данных, при наличии дубликата возвращается ошибка 409 Conflict. Пароль хешируется с использованием bcrypt с фактором сложности 10 раундов. Создаётся запись в таблице User с полями username, email, password_hash, role (по умолчанию user), created_at. Возвращается созданный объект пользователя без поля password_hash.

Алгоритм входа в систему (login) выполняется следующим образом. Принимаются входные данные: email, password. Выполняется поиск пользователя в базе данных по полю email. Если пользователь не найден, возвращается ошибка 401 Unauthorized с сообщением «Неверные учётные данные». Проверяется соответствие переданного пароля хешу, хранящемуся в базе, с использованием функции bcrypt.compare. При несоответствии возвращается ошибка 401. Генерируется токен доступа: создаётся JWT с полезной нагрузкой (payload), содержащей userId, username, role, устанавливается срок действия согласно конфигурации (по умолчанию 15 минут), токен подписывается секретным ключом JWT_ACCESS_SECRET с использованием алгоритма HS256.

Генерируется токен обновления: создаётся случайная строка длиной 32 байта с использованием криптографически стойкого генератора, строка кодируется в base64url формат, вычисляется хеш токена с использованием SHA-256 для хранения в базе данных, генерируется идентификатор семейства токенов (family) как UUID, создаётся запись в таблице RefreshToken с полями user_id, token_hash, family, expires_at (текущее время плюс 7 дней), created_at, revoked (по умолчанию false). Токен обновления устанавливается в HTTP-only cookie с именем refreshToken, флагами httpOnly (true), secure (true в продакшене), sameSite (strict), path (/auth/refresh), maxAge соответствующим сроку действия токена. Возвращается ответ с токеном доступа в теле JSON и объектом пользователя без поля password_hash.

Алгоритм обновления токена доступа (refresh) выполняется следующим образом. Извлекается токен обновления из cookie с именем refreshToken. Если токен отсутствует, возвращается ошибка 401. Вычисляется хеш токена для поиска в базе данных. Выполняется поиск записи в таблице RefreshToken по полю token_hash. Если запись не найдена или поле revoked установлено в true, это указывает на попытку повторного использования токена. В этом случае определяется семейство токена (family) и отзываются все токены этого семейства (устанавливается revoked в true), возвращается ошибка 401.

Если токен найден и не отозван, проверяется срок действия: если текущее время больше expires_at, токен отзывается, возвращается ошибка 401. Если токен валиден, выполняется его отзыв (устанавливается revoked в true) и генерируется новая пара токенов: создаётся новый токен доступа для пользователя, создаётся новый токен обновления с тем же family, что и у старого токена, сохраняется новый refresh token в базе данных, устанавливается новый refresh token в cookie. Возвращается ответ с новым токеном доступа в теле JSON.

Алгоритм выхода из системы (logout) выполняется следующим образом. Извлекается токен обновления из cookie. Если токен присутствует, вычисляется его хеш, выполняется поиск и отзыв всех токенов семейства (family) в базе данных. Очищается cookie refreshToken путём установки maxAge в 0. Возвращается успешный ответ. Данный алгоритм обеспечивает невозможность использования токенов после выхода пользователя.

Механизм защиты от повторного использования токенов (reuse detection) основан на отслеживании семейства токенов. При каждой ротации новый токен сохраняет идентификатор family. Если клиент использует старый отозванный токен из этого семейства, это сигнализирует о возможной компрометации, и вся цепочка токенов данного семейства немедленно аннулируется. Это заставляет пользователя пройти повторную аутентификацию.

## 4.3 Алгоритм проверки прав доступа

Проверка прав доступа выполняется на уровне middleware перед обработкой запросов к защищённым ресурсам. Система использует комбинацию глобальных ролей пользователя и ролей участника проекта для определения разрешённых действий.

Базовый алгоритм аутентификации запроса выполняется следующим образом. Извлекается заголовок Authorization из HTTP-запроса. Проверяется наличие заголовка и соответствие формату «Bearer <token>». Если заголовок отсутствует или формат неверен, возвращается ошибка 401. Извлекается токен доступа из заголовка. Выполняется верификация токена: проверяется подпись с использованием секретного ключа JWT_ACCESS_SECRET, проверяется срок действия. При неудаче верификации возвращается ошибка 401. Извлекается полезная нагрузка из токена (userId, username, role). Полезная нагрузка сохраняется в объекте запроса для использования в последующих обработчиках. Управление передаётся следующему middleware или обработчику маршрута.

Алгоритм проверки глобальной роли выполняется следующим образом. Принимается список допустимых ролей для данного endpoint. Извлекается роль текущего пользователя из полезной нагрузки токена. Проверяется наличие роли пользователя в списке допустимых. Если роль не соответствует, возвращается ошибка 403 Forbidden. Если пользователь имеет роль admin, доступ разрешается без дальнейших проверок, так как администраторы имеют полный доступ ко всем ресурсам.

Алгоритм проверки доступа к проекту выполняется следующим образом. Принимаются параметры: идентификатор проекта, минимальная требуемая роль участника (опционально). Извлекается роль текущего пользователя. Если роль равна admin, доступ разрешается. Выполняется запрос к базе данных для получения записи Project по идентификатору. Если проект не найден, возвращается ошибка 404. Проверяется флаг is_public проекта. Если проект публичный и минимальная роль не указана, доступ разрешается для операций чтения. Выполняется запрос к таблице ProjectMember для поиска записи с условиями project_id равен идентификатору проекта и user_id равен идентификатору текущего пользователя. Если запись не найдена, пользователь не является участником проекта, возвращается ошибка 403.

Если запись найдена, извлекается роль участника из поля ProjectMember.role. Определяется иерархия ролей: owner имеет наивысшие права, manager имеет средние права, developer имеет базовые права, viewer имеет права только на чтение. Сравнивается роль участника с минимальной требуемой ролью. Если роль участника ниже требуемой, возвращается ошибка 403. Если проверка пройдена, доступ разрешается.

Алгоритм проверки доступа к багу для операций редактирования выполняется следующим образом. Принимаются параметры: идентификатор бага, тип операции (чтение, обновление, удаление). Извлекается роль текущего пользователя. Если роль равна admin, доступ разрешается для всех операций. Выполняется запрос к базе данных для получения записи Bug по идентификатору с загрузкой связанного проекта. Если баг не найден, возвращается ошибка 404. Выполняется проверка доступа к проекту бага с использованием алгоритма проверки доступа к проекту. Если доступ к проекту запрещён, возвращается ошибка 403.

Для операции чтения дополнительных проверок не требуется. Для операции удаления проверяется, является ли пользователь владельцем или менеджером проекта. Если нет, возвращается ошибка 403. Для операции обновления выполняется более детальная проверка. Выполняется запрос к таблице ProjectMember для определения роли пользователя в проекте. Если роль равна owner или manager, доступ разрешается для всех полей бага. Если роль равна developer, проверяется, назначен ли баг на текущего пользователя (Bug.assigned_to равен userId) или пользователь является автором бага (Bug.created_by равен userId). Если одно из условий выполнено, разрешается обновление полей status и description. Если пользователь является автором бага (Bug.created_by равен userId), но не назначен исполнителем, разрешается обновление только поля description. В остальных случаях возвращается ошибка 403.

## 4.4 Алгоритм формирования списка багов с фильтрацией

Формирование списка багов с применением фильтров является одной из ключевых операций системы, обеспечивающей пользователям возможность быстрого поиска нужных дефектов [8].

Алгоритм получения списка багов выполняется следующим образом. Принимаются параметры запроса: projectId (идентификатор проекта, опционально), status (статус бага, опционально), priority (приоритет бага, опционально), assignedTo (идентификатор назначенного исполнителя, опционально), createdBy (идентификатор автора бага, опционально), limit (количество записей на страницу, по умолчанию 50), offset (смещение для пагинации, по умолчанию 0). Извлекается текущий пользователь из контекста запроса.

Инициализируется объект условий для запроса к базе данных. Если параметр projectId указан, добавляется условие project_id равен projectId. Если параметр status указан, добавляется условие status равен status. Если параметр priority указан, добавляется условие priority равен priority. Если параметр assignedTo указан, добавляется условие assigned_to равен assignedTo. Если параметр createdBy указан, добавляется условие created_by равен createdBy.

Формируются дополнительные условия для ограничения доступа на основе прав пользователя. Если роль пользователя равна admin, дополнительные ограничения не применяются. В противном случае выполняется запрос к базе данных для получения списка идентификаторов проектов, к которым пользователь имеет доступ. Это включает проекты, где пользователь является участником (выполняется запрос к ProjectMember для получения списка project_id, где user_id равен идентификатору текущего пользователя), и публичные проекты (выполняется запрос к Project для получения списка id, где is_public равен true). Объединяются оба списка идентификаторов проектов. Добавляется условие project_id IN (список доступных идентификаторов проектов).

Выполняется запрос к таблице Bug с применением сформированных условий, с загрузкой связанных данных: проект (Project), автор (User через created_by), назначенный исполнитель (User через assigned_to). Применяются параметры пагинации: skip равен offset, take равен limit. Результаты сортируются по полю updated_at в порядке убывания (недавно обновлённые баги отображаются первыми). Выполняется второй запрос для получения общего количества багов, соответствующих условиям (без пагинации). Формируется ответ с полями: data (массив багов), total (общее количество), limit (использованный лимит), offset (использованное смещение). Возвращается ответ клиенту.

Алгоритм формирования Kanban-доски по проекту выполняется следующим образом. Принимаются параметры: идентификатор проекта, priority (фильтр по приоритету, опционально), assignedTo (фильтр по исполнителю, опционально). Выполняется проверка доступа к проекту с использованием алгоритма проверки доступа к проекту. Если доступ запрещён, возвращается ошибка 403.

Инициализируется объект условий для запроса: project_id равен идентификатору проекта. Если параметр priority указан, добавляется условие priority равен priority. Если параметр assignedTo указан, добавляется условие assigned_to равен assignedTo. Выполняется запрос к таблице Bug с применением условий, с загрузкой связанных данных проекта, автора и исполнителя. Полученный массив багов группируется по полю status.

Инициализируется структура доски с пятью колонками: new (пустой массив), in_progress (пустой массив), testing (пустой массив), done (пустой массив), closed (пустой массив). Выполняется итерация по полученным багам. Для каждого бага извлекается значение поля status, баг добавляется в соответствующий массив структуры доски. Возвращается сформированная структура доски клиенту.

## 4.5 Алгоритм загрузки и скачивания вложений

Обработка файлов-вложений включает валидацию, сохранение на диск, запись метаданных в базу данных и обеспечение безопасного доступа к файлам.

Алгоритм загрузки вложения выполняется следующим образом. Принимаются данные: bugId (идентификатор бага), file (загружаемый файл из multipart/form-data). Выполняется валидация данных: проверяется наличие поля file, если отсутствует, возвращается ошибка 400 с сообщением «Файл не выбран». Проверяется размер файла, если превышает 10 МБ, возвращается ошибка 400 с сообщением «Размер файла не должен превышать 10 МБ». Проверяется MIME-тип файла, допустимые типы: image/*, application/pdf, text/plain, text/csv, если тип не соответствует, возвращается ошибка 400 с сообщением «Неподдерживаемый тип файла».

Выполняется проверка существования бага: запрос к таблице Bug по идентификатору bugId. Если баг не найден, возвращается ошибка 404. Выполняется проверка доступа к проекту бага с использованием алгоритма проверки доступа к проекту. Если доступ запрещён, возвращается ошибка 403.

Генерируется уникальное имя файла для хранения: извлекается расширение файла из оригинального имени, генерируется UUID, формируется имя файла как «{UUID}.{расширение}». Определяется путь для сохранения файла: базовая директория uploads/, поддиректория по идентификатору бага (для организации файлов), полный путь «uploads/{bugId}/{имя_файла}». Создаётся директория, если не существует. Файл сохраняется на диск по сформированному пути.

Создаётся запись в таблице Attachment с полями: bug_id равен bugId, filename равен оригинальному имени файла, file_path равен относительному пути к файлу, uploaded_by равен идентификатору текущего пользователя, uploaded_at равен текущему времени. Формируется URL для доступа к вложению: «/attachments/{id}/download». Возвращается ответ с созданным объектом вложения, включающим поля id, filename, url.

Алгоритм скачивания вложения выполняется следующим образом. Принимается параметр: идентификатор вложения. Выполняется запрос к таблице Attachment по идентификатору с загрузкой связанного бага и его проекта. Если вложение не найдено, возвращается ошибка 404. Выполняется проверка доступа к проекту бага с использованием алгоритма проверки доступа к проекту. Если доступ запрещён, возвращается ошибка 403.

Извлекается путь к файлу из поля file_path записи Attachment. Проверяется существование файла на диске. Если файл не существует, возвращается ошибка 404 с сообщением «Файл не найден». Определяется MIME-тип файла на основе расширения. Устанавливаются HTTP-заголовки ответа: Content-Type равен определённому MIME-типу, Content-Disposition равен «attachment; filename="{filename}"» для инициирования скачивания, Cache-Control для управления кешированием. Файл отправляется клиенту в виде потока данных.

Алгоритм удаления вложения выполняется следующим образом. Принимается параметр: идентификатор вложения. Выполняется запрос к таблице Attachment по идентификатору с загрузкой связанного бага и его проекта. Если вложение не найдено, возвращается ошибка 404. Выполняется проверка прав доступа: извлекается роль пользователя, если роль равна admin, доступ разрешается, иначе проверяется, является ли пользователь автором вложения (uploaded_by равен userId), если да, доступ разрешается, иначе выполняется проверка роли в проекте, если роль равна owner или manager, доступ разрешается, в остальных случаях возвращается ошибка 403.

Извлекается путь к файлу из поля file_path. Удаляется файл с диска. Если файл не существует, ошибка игнорируется (файл мог быть удалён ранее). Удаляется запись из таблицы Attachment. Возвращается успешный ответ с кодом 204 No Content.

## 4.6 Алгоритм санитизации комментариев

Для предотвращения атак типа Cross-Site Scripting (XSS) текстовые комментарии пользователей проходят санитизацию перед сохранением в базу данных [9].

Алгоритм обработки комментария выполняется следующим образом. Принимаются данные: bugId (идентификатор бага), content (текст комментария). Выполняется валидация: проверяется длина текста, если меньше 1 или больше 2000 символов, возвращается ошибка 400. Применяется функция санитизации к тексту комментария. Функция удаляет или экранирует потенциально опасные HTML-теги и атрибуты, оставляя только безопасные элементы форматирования (например, полужирный, курсив), если поддержка HTML разрешена, либо полностью удаляет все HTML-теги, преобразуя текст в plain text. Специальные символы HTML экранируются: символ < заменяется на &lt;, символ > заменяется на &gt;, символ & заменяется на &amp;, символ " заменяется на &quot;, символ ' заменяется на &#x27;.

Выполняется проверка существования бага и доступа к проекту аналогично алгоритму загрузки вложения. Создаётся запись в таблице Comment с полями: bug_id, author_id (из контекста текущего пользователя), content (санитизированный текст), created_at. Возвращается созданный объект комментария клиенту.
