# 3 Постановка задачи

## 3.1 Исходные данные и описание предметной области

Предметной областью разработанной системы является процесс управления дефектами и задачами в рамках проектов разработки программного обеспечения. Центральными понятиями предметной области выступают проекты (Project), баги или дефекты (Bug), пользователи системы (User) и взаимосвязи между ними [2].

Проект представляет собой логическую единицу организации работы, содержащую набор багов и список участников с определёнными ролями. Каждый проект имеет владельца, описание и настройку публичности. Публичные проекты доступны для просмотра и создания багов всем авторизованным пользователям, приватные проекты доступны только участникам проекта и администраторам системы.

Баг описывает обнаруженную проблему или задачу в рамках проекта и характеризуется названием, описанием, статусом, приоритетом, назначенным исполнителем и автором создания. Статус бага отражает текущий этап обработки и может принимать значения: новый (new), в работе (in_progress), на тестировании (testing), выполнен (done), закрыт (closed). Приоритет бага определяет важность его исправления и может быть низким (low), средним (medium), высоким (high) или критическим (critical).

Пользователи системы разделяются на глобальные роли: администратор (admin), менеджер (manager), разработчик (developer) и обычный пользователь (user). Администраторы имеют полный доступ ко всем ресурсам системы, включая управление пользователями и проектами. Остальные пользователи получают доступ к проектам через механизм участников проекта (ProjectMember), где каждому участнику назначается роль в конкретном проекте: владелец (owner), менеджер проекта (manager), разработчик проекта (developer) или наблюдатель (viewer).

К багам могут прикрепляться вложения (Attachment) в виде файлов и добавляться текстовые комментарии (Comment) для обсуждения проблемы и фиксации хода работ. Система должна обеспечивать хранение метаинформации о файлах, включая имя файла, путь в хранилище, автора загрузки и время загрузки.

Схема данных включает следующие основные сущности и их атрибуты. Сущность User содержит идентификатор (UUID), уникальные имя пользователя и адрес электронной почты, хеш пароля, глобальную роль и метку времени создания. Сущность Project содержит идентификатор, название, описание, ссылку на владельца, флаг публичности и метки времени создания и обновления. Сущность ProjectMember связывает пользователей с проектами и содержит идентификатор, ссылки на проект и пользователя, роль в проекте и время присоединения. Уникальность записей обеспечивается составным ключом по идентификаторам проекта и пользователя.

Сущность Bug содержит идентификатор, ссылку на проект, название, описание, статус, приоритет, ссылки на назначенного исполнителя и автора создания, метки времени создания и обновления. Сущность Attachment содержит идентификатор, ссылку на баг, имя файла, путь в файловой системе, ссылку на пользователя, загрузившего файл, и время загрузки. Сущность Comment содержит идентификатор, ссылку на баг, ссылку на автора, текст комментария и время создания.

Связи между сущностями определяются следующим образом. Один пользователь может владеть множеством проектов (связь User — Project через поле owner_id). Многие пользователи могут участвовать во многих проектах через промежуточную таблицу ProjectMember. Один проект содержит множество багов. Один пользователь может создать множество багов, один баг может быть назначен на одного пользователя. Один баг может иметь множество вложений и множество комментариев. Один пользователь может загрузить множество вложений и написать множество комментариев.

## 3.2 Функциональные требования

Функциональные требования к системе определяют набор операций, которые должны быть реализованы для обеспечения полноценной работы баг-трекера. Требования разделены на обязательные (MVP) и дополнительные возможности.

Система должна обеспечивать регистрацию новых пользователей и аутентификацию существующих пользователей по паре электронная почта и пароль. При успешной аутентификации пользователь получает пару токенов: краткосрочный токен доступа (access token) и долгосрочный токен обновления (refresh token). Токен доступа используется для авторизации запросов к защищённым ресурсам API, токен обновления сохраняется в защищённом HTTP-only cookie и используется для получения новой пары токенов при истечении срока действия токена доступа [3].

Администраторы должны иметь возможность создавать, редактировать и удалять проекты, указывая название, описание, владельца и флаг публичности. Владельцы и менеджеры проектов должны иметь возможность управлять списком участников проекта: добавлять новых участников с назначением роли, изменять роли существующих участников и удалять участников из проекта. Ограничение: владелец проекта не может быть удалён из списка участников.

Все авторизованные пользователи должны иметь возможность просматривать списки проектов с учётом прав доступа. Администраторы видят все проекты, остальные пользователи видят публичные проекты и проекты, в которых они являются участниками. Детальная информация о проекте, включая описание, список участников и список багов, должна быть доступна участникам проекта и всем пользователям для публичных проектов.

Пользователи должны иметь возможность создавать баги в проектах, к которым они имеют доступ. Участники проекта могут создавать баги в своих проектах, любые авторизованные пользователи могут создавать баги в публичных проектах. При создании бага указываются обязательные поля: идентификатор проекта, название бага, опционально описание и приоритет. Автор бага фиксируется автоматически на основе текущего пользователя. Баг создаётся со статусом «новый» по умолчанию.

Менеджеры и владельцы проектов должны иметь возможность назначать баги на разработчиков, являющихся участниками проекта с ролью developer. Разработчики должны иметь возможность изменять статус багов, назначенных на них, отражая переход от стадии к стадии обработки. Менеджеры и владельцы проектов должны иметь возможность изменять приоритет и статус любых багов в своих проектах. Авторы багов должны иметь возможность редактировать описание созданных ими багов.

Система должна предоставлять возможность фильтрации списка багов по следующим критериям: идентификатор проекта, статус бага, приоритет бага, назначенный исполнитель, автор бага. Фильтры должны работать независимо и поддерживать комбинирование условий. Результаты фильтрации должны учитывать права доступа пользователя к проектам.

Система должна предоставлять визуализацию багов проекта в виде Kanban-доски с колонками, соответствующими статусам (new, in_progress, testing, done, closed). Доска должна поддерживать фильтрацию багов по приоритету и назначенному исполнителю. Доступ к доске проекта предоставляется участникам проекта и всем пользователям для публичных проектов.

Пользователи должны иметь возможность добавлять текстовые комментарии к багам. Автор комментария фиксируется автоматически. Текст комментария должен проходить санитизацию для защиты от внедрения вредоносного кода (XSS). Авторы комментариев, менеджеры и владельцы проектов, а также администраторы должны иметь возможность редактировать и удалять комментарии.

Пользователи должны иметь возможность прикреплять файлы к багам. Поддерживаются файлы типов: изображения (image/*), PDF-документы (application/pdf), текстовые файлы (text/plain, text/csv). Максимальный размер загружаемого файла ограничен 10 мегабайтами. При загрузке файл сохраняется в локальном хранилище на сервере, в базе данных сохраняется метаинформация. Авторы вложений, менеджеры и владельцы проектов, а также администраторы должны иметь возможность удалять вложения. Все пользователи с доступом к багу должны иметь возможность скачивать прикреплённые файлы.

Дополнительные функциональные возможности включают отображение активности по проекту (последние действия с багами), статистику по проекту (количество багов по статусам и приоритетам, средний срок решения), персональный дашборд пользователя со списком багов, назначенных на него.

## 3.3 Нефункциональные требования

Нефункциональные требования определяют ограничения и качественные характеристики системы, не связанные непосредственно с её функциональностью, но влияющие на пользовательский опыт, безопасность и производительность [4].

Требования к производительности и масштабируемости включают обеспечение времени отклика API не более 500 миллисекунд для большинства запросов при стандартной нагрузке. Система должна поддерживать одновременную работу не менее 100 пользователей без существенного снижения производительности. База данных должна использовать индексы по часто используемым полям для ускорения операций выборки и фильтрации. Запросы к базе данных должны выполняться через ORM с использованием параметризованных запросов для предотвращения SQL-инъекций.

Требования к безопасности являются критически важными для защиты данных пользователей и предотвращения несанкционированного доступа. Пароли пользователей должны храниться в виде хешей с использованием алгоритма bcrypt с достаточным числом раундов. Токены доступа должны иметь ограниченный срок действия (по умолчанию 15 минут), токены обновления должны иметь более длительный срок действия (по умолчанию 7 дней). Токены обновления должны храниться в защищённых HTTP-only cookie с флагами Secure и SameSite для предотвращения атак типа CSRF [5].

Система должна реализовывать механизм ротации токенов обновления: при каждом обновлении токена доступа выдаётся новый токен обновления, старый токен отзывается. Должно быть реализовано обнаружение повторного использования отозванных токенов обновления, что свидетельствует о возможной компрометации и требует отзыва всей цепочки токенов пользователя.

Все пользовательские вводы должны проходить валидацию на стороне сервера с использованием схем валидации. Текстовые данные, отображаемые в браузере, должны проходить санитизацию для предотвращения атак типа XSS. Сервер должен использовать middleware для установки заголовков безопасности (helmet): Content-Security-Policy, X-Frame-Options, X-Content-Type-Options и другие.

Система должна реализовывать ограничение скорости запросов (rate limiting) для предотвращения DoS-атак и брутфорса. Для endpoints аутентификации устанавливается более строгое ограничение (например, 5 запросов в минуту на IP-адрес), для остальных endpoints — менее строгое (например, 100 запросов в минуту на пользователя).

Требования к надёжности включают корректную обработку ошибок на всех уровнях приложения с возвратом понятных сообщений об ошибках пользователю. Система не должна раскрывать внутренние детали реализации в сообщениях об ошибках, доступных клиенту. Должно быть реализовано логирование критических операций и ошибок для последующего анализа и диагностики проблем.

Требования к совместимости и доступности включают поддержку современных веб-браузеров (Chrome, Firefox, Safari, Edge последних версий). Клиентское приложение должно быть адаптивным и корректно отображаться на различных разрешениях экрана. API должно следовать принципам REST и использовать стандартные HTTP-методы и коды статусов.

Требования к развёртыванию включают использование переменных окружения для конфигурации приложения (подключение к базе данных, секретные ключи, настройки CORS). Должна быть предоставлена документация по развёртыванию, включающая инструкции по настройке окружения, выполнению миграций базы данных и запуску приложения.

## 3.4 Ограничения и допущения

При разработке системы приняты следующие ограничения и допущения. Система разрабатывается для развёртывания в контролируемом окружении с доступом к серверу PostgreSQL. Предполагается, что администратор системы имеет технические навыки для развёртывания Node.js приложений и настройки базы данных.

Хранение файлов-вложений реализуется в локальной файловой системе сервера. Для продуктивного использования в распределённых системах потребуется миграция на объектное хранилище (например, S3-совместимое). Максимальный размер файла ограничен 10 МБ для предотвращения чрезмерного использования дискового пространства и сетевого трафика.

Регистрация первого администратора выполняется через специальный endpoint при начальной настройке системы. После создания первого администратора этот endpoint отключается, дальнейшее создание пользователей выполняется администратором через управление пользователями. Данное ограничение обеспечивает контроль над доступом к системе.

Система не реализует механизм восстановления пароля через электронную почту в рамках MVP. Сброс пароля пользователя может быть выполнен администратором. Данное ограничение упрощает начальную реализацию и не требует интеграции с почтовым сервером.

Система не реализует историю изменений багов (audit log) в рамках MVP. Отслеживание изменений статусов, приоритетов и назначений может быть добавлено как дополнительная функциональность. Текущие версии полей сущности Bug отражают последнее состояние.

Система не реализует real-time уведомления о событиях (например, через WebSocket). Обновление данных выполняется при явном запросе пользователя или по таймеру на клиенте. Добавление real-time функциональности возможно в будущих версиях.

Предполагается, что количество проектов и багов в системе не превысит несколько тысяч в рамках использования небольшими и средними командами. Для поддержки более масштабных нагрузок потребуется оптимизация запросов, введение пагинации на всех списках и возможное применение кеширования.

## 3.5 Критерии приёмки MVP

Критерии приёмки определяют условия, при выполнении которых система считается реализованной в соответствии с требованиями минимально жизнеспособного продукта [6].

Система должна обеспечивать успешную аутентификацию пользователей с корректными учётными данными и отклонение запросов с неверными данными. Должна работать автоматическая ротация токенов доступа при их истечении с прозрачным для пользователя обновлением сессии. Выход из системы должен отзывать токены обновления, делая невозможным их дальнейшее использование.

Создание проекта администратором должно автоматически добавлять владельца в список участников с ролью owner. Просмотр списка проектов должен корректно отображать только те проекты, к которым пользователь имеет доступ согласно правам. Редактирование настроек проекта должно быть доступно только владельцу проекта и администратору.

Добавление участника в проект должно корректно назначать указанную роль. Изменение роли участника должно быть доступно только владельцу проекта. Попытка добавить пользователя, уже являющегося участником, должна возвращать ошибку валидации.

Создание бага в проекте должно автоматически фиксировать автора и устанавливать статус new. Фильтрация багов по статусу, приоритету и назначенному исполнителю должна возвращать корректные результаты, соответствующие условиям фильтра. Комбинирование нескольких фильтров должно работать по принципу логического И.

Endpoint получения доски проекта должен возвращать баги, сгруппированные по пяти колонкам статусов: new, in_progress, testing, done, closed. Фильтры на доске по приоритету и назначенному исполнителю должны корректно применяться. Доступ к доске приватного проекта должен быть запрещён пользователям, не являющимся участниками.

Назначение бага на разработчика менеджером проекта должно обновлять поле assigned_to. Попытка назначить пользователя, не являющегося участником проекта с ролью developer, должна возвращать ошибку. Изменение статуса бага разработчиком должно быть возможно только для багов, назначенных на него.

Добавление комментария к багу должно фиксировать автора и время создания. Текст комментария должен быть санитизирован для предотвращения XSS. Удаление комментария должно быть доступно автору, менеджеру, владельцу проекта и администратору.

Загрузка вложения должна проверять тип и размер файла, отклоняя недопустимые файлы. Скачивание вложения должно возвращать файл с корректными HTTP-заголовками Content-Type и Content-Disposition. Удаление вложения должно быть доступно автору, менеджеру, владельцу проекта и администратору, при этом файл должен удаляться как из базы данных, так и из файловой системы.

Все защищённые endpoints должны возвращать код 401 при отсутствии токена доступа или его невалидности. Попытка выполнить операцию без необходимых прав должна возвращать код 403 с описанием причины отказа. Запросы с невалидными данными должны возвращать код 400 с детальным описанием ошибок валидации.
