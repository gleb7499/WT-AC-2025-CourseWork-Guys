# 2 Разработка алгоритмов

## 2.1 Описание сущностей и связей

Модель данных системы построена на шести основных сущностях, связанных между собой отношениями «один ко многим» и «многие ко многим».

Сущность User представляет пользователя системы. Каждый пользователь имеет уникальное имя и адрес электронной почты. Пароль хранится в виде хеша, полученного с использованием алгоритма bcrypt с коэффициентом стоимости двенадцать раундов [4]. Атрибут role принимает значения «admin» или «user» и определяет уровень доступа в системе.

Сущность Trip описывает поездку. Поездка обязательно имеет владельца, который является пользователем системы. Поездка содержит название, текстовое описание, даты начала и окончания, а также необязательное значение планируемого бюджета. Атрибут created_at фиксирует момент создания записи.

Сущность Stop представляет остановку на маршруте. Каждая остановка связана с конкретной поездкой через внешний ключ trip_id. Остановка имеет название места и опционально может содержать адрес, географические координаты (latitude и longitude), время прибытия и отправления. Атрибут order определяет позицию остановки в последовательности маршрута.

Сущность Note описывает текстовую заметку, привязанную к поездке. Заметка имеет автора (author_id) и текстовое содержимое. Время создания фиксируется автоматически.

Сущность Expense представляет запись о расходе в рамках поездки. Расход содержит числовое значение суммы, текстовые поля категории и описания, а также дату. Каждый расход связан с поездкой и имеет автора.

Сущность TripParticipant реализует связь «многие ко многим» между пользователями и поездками. Запись в этой таблице указывает, что пользователь является участником поездки. Атрибут role может принимать значения «owner» или «participant», позволяя различать владельца и приглашённых участников.

Связи между сущностями организованы следующим образом. Один пользователь может владеть многими поездками, но каждая поездка имеет ровно одного владельца. Одна поездка может иметь множество остановок, заметок и расходов, при этом каждая из этих сущностей принадлежит только одной поездке. При удалении поездки каскадно удаляются все связанные остановки, заметки и расходы. Пользователь может быть автором многих заметок и расходов. Один пользователь может участвовать во многих поездках, и одна поездка может иметь многих участников — это отношение реализовано через промежуточную таблицу TripParticipant.

## 2.2 Алгоритм формирования списка доступных поездок

При запросе списка поездок система должна вернуть только те поездки, к которым пользователь имеет доступ. Алгоритм выборки поездок учитывает роль пользователя и его участие в поездках.

Если запрос выполняет пользователь с ролью «admin», система возвращает все поездки из базы данных без ограничений. Администратор имеет полный доступ для целей модерации и управления системой.

Если запрос выполняет обычный пользователь, система формирует выборку следующим образом. Сначала определяется идентификатор текущего пользователя из токена аутентификации. Затем выполняется запрос к базе данных, который извлекает поездки, удовлетворяющие одному из условий: поле owner_id поездки равно идентификатору текущего пользователя (пользователь является владельцем), либо существует запись в таблице TripParticipant, где trip_id соответствует поездке, а user_id равен идентификатору текущего пользователя (пользователь является участником).

Результат запроса включает основные атрибуты поездки: идентификатор, название, описание, даты, бюджет, идентификатор владельца и дату создания. Дополнительно для каждой поездки загружается информация о владельце (имя и email) и количество участников.

Список поездок возвращается с поддержкой пагинации. По умолчанию возвращается до пятидесяти записей за один запрос. Клиент может указать параметры limit и offset для постраничного получения данных.

## 2.3 Алгоритм совместной работы и разграничения прав

Механизм совместной работы основан на явном управлении списком участников через таблицу TripParticipant. При создании поездки автоматически создаётся запись в TripParticipant, где user_id равен идентификатору создателя, а role установлен в значение «owner».

Для добавления участника владелец поездки отправляет запрос с идентификатором пользователя, которого нужно пригласить. Система проверяет, что текущий пользователь является владельцем поездки. Затем проверяется, что приглашаемый пользователь существует в системе и ещё не является участником данной поездки. Если проверки пройдены, создаётся новая запись в TripParticipant с ролью «participant».

При выполнении операций с содержимым поездки (добавление остановок, заметок, расходов) система проверяет, что пользователь имеет доступ к поездке. Проверка выполняется запросом к таблице TripParticipant: пользователь должен иметь запись, связывающую его с данной поездкой. Если такая запись существует, операция разрешена.

Для операций редактирования и удаления применяются дополнительные правила. Редактировать и удалять поездку могут только владелец и администратор. Редактировать заметку может только её автор. Удалять заметку могут автор, владелец поездки или администратор. Аналогичные правила действуют для расходов.

Алгоритм проверки прав выглядит следующим образом. Из токена аутентификации извлекается идентификатор и роль текущего пользователя. Для целевого ресурса (поездка, заметка, расход) извлекаются связанные идентификаторы (owner_id, author_id). Если роль пользователя «admin», операция разрешена. Если операция относится к поездке, проверяется равенство owner_id идентификатору пользователя. Если операция относится к заметке или расходу, проверяется равенство author_id идентификатору пользователя или проверяется, является ли пользователь владельцем родительской поездки. Если ни одно условие не выполнено, возвращается ошибка доступа с кодом состояния четыреста три.

## 2.4 Алгоритм расчёта статистики по бюджету

Для отображения сводной информации о финансовых аспектах поездки реализован алгоритм расчёта статистики. При запросе сводки по поездке система выполняет следующие действия.

Извлекается значение поля budget из записи поездки. Если бюджет не был установлен, его значение считается равным нулю. Выполняется агрегирующий запрос к таблице Expense, суммирующий значения поля amount для всех записей, где trip_id соответствует целевой поездке. Результат представляет собой общую сумму потраченных средств.

Вычисляется остаток бюджета как разность между запланированным бюджетом и суммой расходов. Если остаток положителен, это означает, что расходы не превысили план. Если остаток отрицателен, расходы превысили запланированный бюджет.

Дополнительно система подсчитывает количество записей о расходах и количество остановок в маршруте, а также количество участников поездки. Эта информация возвращается клиенту в виде структурированного объекта, включающего totalExpenses (общая сумма расходов), remainingBudget (остаток бюджета), expensesCount (количество записей о расходах), stopsCount (количество остановок), participantsCount (количество участников).

## 2.5 Алгоритм аутентификации с использованием JWT

Система аутентификации построена на механизме JSON Web Tokens с разделением на токены доступа и токены обновления [3]. Алгоритм работы включает несколько этапов.

При входе пользователя система получает адрес электронной почты и пароль. Выполняется поиск пользователя в базе данных по email. Если пользователь найден, выполняется сравнение предоставленного пароля с сохранённым хешем с помощью функции bcrypt.compare. При успешной проверке генерируются два токена: access-токен со сроком жизни пятнадцать минут и refresh-токен со сроком жизни семь дней. В payload access-токена включаются идентификатор и роль пользователя. В payload refresh-токена дополнительно включается уникальный идентификатор jti.

Refresh-токен сохраняется в базе данных в виде записи, содержащей хеш значения jti, идентификатор пользователя, время истечения и статус отзыва. Сам токен отправляется клиенту в защищённой HttpOnly cookie с флагами secure и sameSite. Access-токен возвращается в теле ответа и хранится клиентским приложением в памяти.

При выполнении защищённых запросов клиент передаёт access-токен в заголовке Authorization с префиксом Bearer. Сервер проверяет подпись токена и извлекает данные пользователя из payload. Если токен истёк, сервер возвращает ошибку с кодом четыреста один.

Клиентское приложение при получении ошибки четыреста один автоматически отправляет запрос на обновление токенов к endpoint /auth/refresh. В этом запросе передаётся refresh-токен в cookie. Сервер проверяет подпись refresh-токена, извлекает jti и выполняет поиск соответствующей записи в базе данных. Если запись найдена, не отозвана и не истекла, текущий refresh-токен отзывается (устанавливается поле revokedAt), генерируется новая пара токенов, новый refresh-токен сохраняется в базе данных, и оба токена возвращаются клиенту. После успешного обновления клиент повторяет исходный запрос с новым access-токеном.

При выходе из системы клиент отправляет запрос к endpoint /auth/logout с передачей refresh-токена в cookie. Сервер находит соответствующую запись в базе данных и устанавливает поле revokedAt в текущее время, делая токен недействительным. Cookie с refresh-токеном очищается.

Такая схема обеспечивает баланс между безопасностью и удобством использования. Короткий срок жизни access-токена снижает окно уязвимости при компрометации токена. Хранение refresh-токена в HttpOnly cookie защищает от атак типа XSS. Ротация refresh-токенов при каждом обновлении и хранение их состояния в базе данных позволяют отслеживать активные сессии и немедленно отзывать доступ при необходимости.
