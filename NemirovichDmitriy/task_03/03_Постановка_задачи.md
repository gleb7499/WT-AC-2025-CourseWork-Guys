# 1 Постановка задачи

## 1.1 Исходные данные

Проектируемая система предназначена для организации совместного планирования поездок. Основными объектами предметной области являются поездки с маршрутами, остановки на маршруте, заметки участников и записи о расходах. Каждая поездка имеет владельца и может включать нескольких участников. Данные о поездках, пользователях и связанных сущностях хранятся в реляционной базе данных.

Схема данных включает следующие основные сущности:

**User** — пользователь системы. Атрибуты: уникальный идентификатор, имя пользователя, адрес электронной почты, хеш пароля, роль (администратор или обычный пользователь).

**Trip** — поездка. Атрибуты: уникальный идентификатор, название, описание, дата начала, дата окончания, общий бюджет, идентификатор владельца, дата создания.

**Stop** — остановка на маршруте. Атрибуты: уникальный идентификатор, идентификатор поездки, название места, адрес, координаты (широта и долгота), дата и время прибытия, дата и время отправления, порядковый номер в маршруте.

**Note** — заметка к поездке. Атрибуты: уникальный идентификатор, идентификатор поездки, идентификатор автора, текстовое содержание, дата создания.

**Expense** — запись о расходе. Атрибуты: уникальный идентификатор, идентификатор поездки, идентификатор автора, сумма, категория, описание, дата.

**TripParticipant** — связь между поездкой и участником. Атрибуты: уникальный идентификатор, идентификатор поездки, идентификатор пользователя, роль участника (владелец или участник).

Связи между сущностями: пользователь создаёт поездки и может быть участником нескольких поездок; поездка содержит остановки, заметки и записи о расходах; заметки и расходы имеют авторов из числа пользователей.

## 1.2 Функциональные требования

Система должна обеспечивать следующие функциональные возможности.

**Аутентификация и управление пользователями**. Регистрация новых пользователей с проверкой уникальности имени и адреса электронной почты. Вход в систему по адресу электронной почты и паролю. Хранение паролей в виде хешей с использованием алгоритма bcrypt. Выход из системы с отзывом токенов обновления. Восстановление сессии при перезагрузке страницы. Администратор может просматривать список всех пользователей и управлять их учётными записями.

**Управление поездками**. Создание новой поездки с указанием названия, описания, дат начала и окончания, планируемого бюджета. Просмотр списка поездок, в которых пользователь является владельцем или участником. Просмотр детальной информации о поездке, включая остановки, заметки и расходы. Редактирование поездки владельцем или администратором. Удаление поездки владельцем или администратором с каскадным удалением связанных данных.

**Совместная работа**. Владелец поездки может добавлять других пользователей в качестве участников, указывая их уникальный идентификатор. Участники имеют доступ к просмотру и редактированию содержимого поездки. Владелец может удалять участников из поездки. Участник может самостоятельно выйти из поездки.

**Управление остановками маршрута**. Добавление остановок к поездке с указанием названия места, адреса, координат, времени прибытия и отправления. Упорядочивание остановок по порядковому номеру для формирования последовательности маршрута. Редактирование и удаление остановок владельцем или участниками поездки.

**Ведение заметок**. Добавление текстовых заметок к поездке любым участником. Просмотр всех заметок поездки в хронологическом порядке. Редактирование заметки её автором. Удаление заметки автором, владельцем поездки или администратором.

**Учёт расходов и бюджета**. Добавление записей о расходах с указанием суммы, категории, описания и даты. Просмотр списка расходов с возможностью фильтрации по категориям. Расчёт общей суммы потраченных средств. Сравнение потраченной суммы с запланированным бюджетом. Редактирование и удаление записей о расходах автором, владельцем или администратором.

## 1.3 Нефункциональные требования

**Производительность**. Время отклика на запросы пользователя не должно превышать трёх секунд при нормальной нагрузке. Система должна поддерживать одновременную работу не менее ста пользователей.

**Безопасность**. Аутентификация реализована на основе JSON Web Tokens [3]. Access-токены имеют короткий срок жизни (пятнадцать минут) и хранятся в памяти клиентского приложения. Refresh-токены имеют длительный срок жизни (семь дней), хранятся в защищённых HttpOnly cookie и подлежат ротации при каждом обновлении. Пароли хранятся в виде хешей, полученных с помощью алгоритма bcrypt. Применяются заголовки безопасности с использованием библиотеки Helmet. Настроена политика CORS с ограничением допустимых источников запросов.

**Надёжность**. Использование транзакций базы данных для обеспечения целостности данных при выполнении связанных операций. Централизованная обработка ошибок с возвратом клиенту структурированных сообщений об ошибках.

**Масштабируемость**. Архитектура построена по принципу разделения клиентской и серверной частей, что позволяет масштабировать компоненты независимо. База данных PostgreSQL обеспечивает горизонтальное масштабирование при необходимости.

**Удобство использования**. Интерфейс построен с использованием современных паттернов проектирования пользовательских интерфейсов. Формы содержат валидацию на стороне клиента с информативными сообщениями об ошибках. Интерфейс скрывает элементы управления, недоступные пользователю в соответствии с его правами.

## 1.4 Ограничения и допущения

Система разработана как MVP-прототип и не предусматривает следующие возможности: интеграция с внешними картографическими сервисами для автоматического построения маршрутов; отправка уведомлений участникам при изменениях в поездке; экспорт данных о поездке в форматы PDF или Excel; поддержка нескольких языков интерфейса; мобильные приложения для платформ iOS и Android.

Предполагается, что система развёртывается в контролируемой среде с настроенной базой данных PostgreSQL. Пользователи имеют доступ к современным веб-браузерам с поддержкой JavaScript. Все участники поездки являются зарегистрированными пользователями системы.

## 1.5 Критерии приёмки MVP

Для подтверждения выполнения требований минимально жизнеспособного продукта необходимо выполнение следующих условий:

1. Пользователь может зарегистрироваться и войти в систему.
2. Аутентифицированный пользователь может создать поездку с указанием основных параметров.
3. Владелец поездки может добавлять остановки к маршруту с указанием названия, адреса и дат.
4. Участники поездки могут добавлять заметки и просматривать заметки других участников.
5. Участники поездки могут добавлять записи о расходах и видеть общую сумму потраченных средств.
6. Владелец поездки может пригласить другого пользователя, указав его уникальный идентификатор, и приглашённый пользователь получает доступ к поездке.
7. Система корректно разграничивает права доступа: участники не могут удалять поездку, только владелец может добавлять и удалять участников.
8. Все операции создания, чтения, обновления и удаления работают корректно и возвращают соответствующие коды состояния HTTP.
