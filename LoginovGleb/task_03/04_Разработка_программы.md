# 3. Разработка программы

## 3.1. Архитектура системы

Разрабатываемая система обработки заявок реализована как распределённое клиент-серверное веб-приложение. Архитектура построена по принципу разделения ответственности между слоями представления, прикладной логики и хранения данных. Данный подход обеспечивает независимое развитие пользовательского интерфейса и серверного API, а также упрощает масштабирование серверной части при увеличении нагрузки.

Клиентская часть представляет собой одностраничное веб-приложение (SPA), работающее в браузере пользователя. Интерфейс предоставляет средства аутентификации, просмотра и управления заявками в соответствии с ролью пользователя, а также административные разделы управления справочниками (формами и статусами). Клиент взаимодействует с сервером по HTTP(S), используя REST-подобные эндпоинты; основная часть обмена выполняется в формате JSON. Для загрузки файлов-вложений применяется формат `multipart/form-data`, что позволяет передавать бинарные данные файла совместно с метаданными и идентификатором заявки.

Серверная часть реализована как HTTP API, выполняющее функции аутентификации, авторизации (RBAC), валидации входных данных, применения бизнес-правил жизненного цикла заявки и формирования ответов для клиентского приложения. Сервер предоставляет как функциональные эндпоинты (работа с заявками, формами, статусами и вложениями), так и служебные эндпоинты для контроля работоспособности (например, проверки здоровья и готовности), что облегчает эксплуатацию в контейнерной среде.

Персистентное хранение доменных данных (пользователи, заявки, статусы, формы, история изменений) осуществляется в реляционной СУБД PostgreSQL. Доступ к базе данных организован через ORM, что обеспечивает единообразие работы с данными, формализацию схемы и поддержку миграций. Для ускорения части операций и снижения нагрузки на основное хранилище используется Redis, применяемый как кэш для данных с ограниченным временем жизни (например, справочники и результаты выборок). С точки зрения обмена данными PostgreSQL и Redis являются внутренними компонентами и недоступны напрямую из пользовательского браузера.

Подсистема работы с вложениями реализует хранение файлов в файловой системе сервера с сохранением метаданных в базе данных. При создании вложения сервер формирует относительный путь хранения вида `uploads/<applicationId>/<uuid>-<filename>`, что позволяет группировать файлы по заявкам и исключать коллизии имён. Данный подход достаточен для целей курсового проекта; при промышленной эксплуатации может потребоваться выделенное объектное хранилище или подключаемый том для сохранения файлов между перезапусками.

Взаимодействие компонентов в типовом сценарии включает следующие шаги: пользователь выполняет действие в интерфейсе, браузер отправляет запрос к серверному API, сервер проводит аутентификацию и авторизацию, выполняет операции чтения/записи в PostgreSQL (и при необходимости взаимодействует с Redis), после чего возвращает ответ клиенту. Для защищённых операций клиент передаёт access-токен в заголовке `Authorization: Bearer ...`, а обновление сессии выполняется через refresh-токен, хранимый в HttpOnly cookie, что снижает риск компрометации токена в браузерном окружении.

Декомпозиция по слоям и выделение инфраструктурных компонентов обеспечивает соответствие требованиям по ролям и трекингу статусов, а также создаёт основу для воспроизводимого запуска в контейнерной среде.

## 3.2. Выбранный технологический стек и обоснование

Выбор технологического стека определялся требованиями варианта 40 и практическими ограничениями курсового проекта: необходимостью реализовать типовой веб-интерфейс для нескольких ролей, обеспечить безопасную аутентификацию и авторизацию, поддержать загрузку файлов, а также организовать воспроизводимый запуск и возможность тестирования. Дополнительно учитывались доступность технологий, зрелость экосистемы и наличие инструментов типизации, что снижает вероятность ошибок при разработке.

Клиентская часть реализована на базе React и TypeScript. Использование React позволяет построить одностраничное приложение с повторно используемыми компонентами и предсказуемым обновлением интерфейса при изменении состояния. TypeScript обеспечивает статическую проверку типов, что особенно важно при работе с развитой моделью данных (заявки, формы, статусы, вложения) и уменьшает число ошибок на границе «клиент–сервер». В качестве инструмента сборки выбран Vite, который обеспечивает быстрый цикл разработки за счёт современного механизма сборки и горячей перезагрузки. Для маршрутизации используется React Router, позволяющий структурировать страницы по сценариям работы ролей и обеспечивать переходы без перезагрузки. Для обработки форм применяются связка React Hook Form и Zod: первая снижает накладные расходы на управление состоянием ввода, вторая формализует правила валидации и позволяет синхронизировать их с требованиями к данным.

Серверная часть реализована на Node.js и Express с использованием TypeScript. Данная платформа соответствует характеру задачи, так как обеспечивает простое построение HTTP API, тесно интегрируется с фронтендом по языку (TypeScript) и позволяет использовать единые подходы к типизации и форматам данных. Для аутентификации применяются JWT-токены (access + refresh) и механизмы хранения refresh-сессий, что даёт баланс между удобством пользователя и безопасностью. Для хранения данных выбрана PostgreSQL как реляционная СУБД, подходящая для строгих связей между сущностями и обеспечения целостности. Доступ к базе организован через Prisma ORM, что упрощает описание схемы данных, выполнение миграций и реализацию типобезопасных запросов. Для ускорения части операций и снижения повторяющихся обращений к базе используется Redis как кэш.

Для повышения наблюдаемости и упрощения сопровождения сервер использует структурированное логирование (Pino), что облегчает анализ ошибок и событий при выполнении пользовательских сценариев. Для воспроизводимого запуска применяется контейнеризация: компоненты (сервер, клиент, PostgreSQL, Redis) могут быть подняты в единой конфигурации, что снижает зависимость от локального окружения и облегчает проверку работоспособности. Для раздачи клиентской части в production-сценарии используется веб-сервер Nginx.

Исходный код организован в виде монорепозитория: отдельные приложения (сервер и веб-клиент) дополнены общими пакетами повторно используемого кода. Это позволяет разделить ответственность, переиспользовать общие утилиты/компоненты и унифицировать управление зависимостями.

## 3.3. Описание модулей серверной части

Серверная часть построена по модульному принципу, при котором каждая функциональная область выделяется в самостоятельный модуль с единообразной внутренней структурой. Общая схема обработки HTTP-запроса включает последовательность уровней: маршрутизация (router) → контроллер (handler) → сервис (business logic) → слой доступа к данным (ORM) и инфраструктурные компоненты. Для выполнения сквозных требований (аутентификация, авторизация, обработка ошибок, логирование) используются middleware и общие библиотеки.

В качестве точки входа API используется агрегирующий роутер, который подключает доменные роутеры по префиксам ресурсов (аутентификация, пользователи, формы, статусы, заявки, вложения). Внутри каждого доменного роутера определяются маршруты и правила доступа: часть эндпоинтов доступна только аутентифицированным пользователям, а часть ограничивается конкретными ролями (например, операции администрирования доступны администратору, смена статусов — модератору/администратору).

Контроллерный слой выполняет обработку HTTP-аспектов: чтение параметров запроса и тела, преобразование и валидацию входных данных, формирование HTTP-ответов и кодов состояния. Для валидации используются схемы, что позволяет единообразно контролировать формат UUID, структуру JSON и ограничения по длинам/типам. Бизнес-правила сосредоточены в сервисном слое. Сервисы реализуют операции жизненного цикла доменных объектов (например, создание черновика заявки, отправка на рассмотрение, смена статуса, управление формами/статусами) и выполняют проверки прав доступа на уровне предметной области (владелец заявки, роль, статус заявки).

Слой инфраструктуры включает общие компоненты: конфигурацию, логирование, работу с JWT, кэширование, метрики, обработку ошибок и т.п. Такой подход снижает дублирование кода между модулями и повышает согласованность поведения сервера (единые форматы ответов и ошибок, единые правила аутентификации).

Ключевые доменные модули серверной части можно сгруппировать следующим образом:

- Модуль аутентификации (auth) реализует регистрацию и вход, выпуск пары токенов (access/refresh), обновление сессии и выход. Логика обновления основана на refresh-токене, хранимом в HttpOnly cookie, и серверном контроле refresh-сессий.
- Модуль пользователей (users) предоставляет операции получения данных о пользователях и административного управления (в зависимости от роли), обеспечивая основу для управления ролями.
- Модуль форм (forms) реализует создание и сопровождение настраиваемых форм заявок: администратор управляет схемой полей, а пользователи используют активные формы при создании заявок. Для публичного отображения перечня форм допускается опциональная аутентификация.
- Модуль статусов (statuses) обеспечивает управление справочником статусов жизненного цикла заявки и параметрами визуализации (например, цвет и признак финальности).
- Модуль заявок (applications) реализует основную бизнес-функциональность: создание черновика, редактирование/удаление, отправку на рассмотрение, получение списка/деталей, отзыв, а также смену статуса уполномоченными ролями с обязательной фиксацией переходов в истории.
- Модуль вложений (attachments) отвечает за метаданные вложенных файлов и контроль доступа к ним; реализуются ограничения по количеству и суммарному объёму вложений, а операции изменения вложений ограничиваются состоянием «черновик».

## 3.4. Описание клиентской части

Клиентская часть системы реализована как одностраничное приложение (SPA) и предназначена для выполнения основных пользовательских сценариев: просмотра доступных форм, регистрации и входа, создания и редактирования заявок, отслеживания статусов, а также административного управления справочниками и обработки заявок в зависимости от роли. Архитектура клиентского приложения ориентирована на разделение ответственности между страницами (routes), переиспользуемыми компонентами интерфейса и слоем взаимодействия с серверным API.

Маршрутизация построена на базе React Router и включает две группы экранов. Первая группа — публичные маршруты аутентификации (страницы входа и регистрации). Вторая группа — рабочие разделы приложения, подключаемые внутри общего макета и защищённые механизмом контроля доступа. Защита маршрутов реализуется компонентом «защищённого маршрута», который проверяет факт аутентификации и (при необходимости) принадлежность пользователя к допустимым ролям. Такой подход обеспечивает единообразный контроль доступа на уровне UI и снижает вероятность отображения пользователю страниц, не соответствующих его полномочиям.

Состояние аутентификации поддерживается через контекст приложения. Контекст хранит сведения о текущем пользователе и признаке аутентифицированности, а также инкапсулирует операции входа, выхода и обновления сессии. Взаимодействие с сервером для защищённых операций основано на передаче access-токена в заголовке `Authorization: Bearer ...`. При истечении access-токена клиент инициирует обновление сессии через refresh-механизм (refresh-токен хранится в HttpOnly cookie и не обрабатывается напрямую в коде интерфейса), после чего повторяет запрос с новым access-токеном.

Структурно интерфейс организован по следующим уровням:

- Слой страниц (pages) описывает основные экраны приложения и их композицию из компонентов. К страницам относятся: список заявок, детальная страница заявки, форма создания/редактирования заявки, список форм и детальная страница формы, управление статусами, а также административный раздел.
- Слой компонентов (components) содержит общие элементы интерфейса (макеты страниц, навигация, защищённые маршруты), которые используются в разных разделах и задают единый стиль взаимодействия.
- Слой работы с API (api) инкапсулирует HTTP-вызовы к серверу и преобразование ответов в типизированные структуры. Выделение API-слоя позволяет отделить сетевую логику от страниц и упрощает сопровождение при изменении контрактов.
- Уровни features, entities, shared и hooks поддерживают переиспользование бизнес-ориентированных компонентов, типов и утилит; такое разбиение уменьшает связность кода и облегчает расширение функциональности.

С точки зрения пользовательских сценариев выделяются роли и связанные с ними разделы интерфейса. Пользователь (role user) выполняет основные операции с заявками: создаёт черновик, заполняет данные формы, прикладывает вложения, отправляет заявку на рассмотрение и отслеживает изменения статуса. Модератор (role moderator) имеет доступ к управлению статусами и обработке заявок, что проявляется в интерфейсе через расширенную видимость данных и доступность операций смены статуса. Администратор (role admin) дополнительно получает административный раздел для управления справочниками (формами и статусами) и выполнением административных функций.

## 3.5. Спецификация программного интерфейса (API)

Взаимодействие клиентской и серверной частей реализовано через HTTP API, основанное на ресурсном подходе. Основной формат обмена данными — JSON. Для защищённых операций используется access-токен, передаваемый в заголовке `Authorization: Bearer <token>`. Обновление сессии выполняется через refresh-токен, устанавливаемый сервером в HttpOnly cookie `refresh_token`, что позволяет обновлять access-токен без хранения refresh-токена в JavaScript-коде браузера [8].

Контракт API формализован спецификацией OpenAPI (Swagger), что обеспечивает однозначность структуры запросов и ответов, перечня эндпоинтов, а также фиксирует типовые коды ошибок и схемы данных. Фрагмент спецификации (группировка по доменным тегам и перечень операций) приведён на рисунке 3.10.

## 3.6. Модель данных

Модель данных системы ориентирована на поддержку жизненного цикла заявки, хранение настраиваемых форм и обеспечение аудита изменений. Реализация опирается на реляционную модель данных, что позволяет применять ограничения целостности и формализовать связи между сущностями при использовании ORM-подхода [5], [6]. В качестве идентификаторов во всех основных сущностях используются UUID, что упрощает генерацию ключей на сервере и снижает риск коллизий при распределённой обработке. Для большинства сущностей предусмотрены поля времени создания и обновления, позволяющие вести временную привязку событий и поддерживать типовые сценарии сортировки.

В системе выделяются следующие ключевые сущности.

Сущность пользователя содержит учётные данные и роль доступа. Для идентификации и контроля уникальности предусмотрены уникальные ограничения на поля имени пользователя и электронной почты. Пароль хранится не в открытом виде, а в виде хэш-значения (passwordHash), что соответствует базовым требованиям безопасности.

Для управления сессиями используется сущность refresh-сессии, в которой хранится хэш refresh-токена (tokenHash) и служебные атрибуты (срок действия, признаки отзыва и замены, IP-адрес, user-agent). Привязка refresh-сессий к пользователю реализована внешним ключом; при удалении пользователя связанные refresh-сессии каскадно удаляются, что предотвращает накопление «осиротевших» записей.

Сущность формы предназначена для описания структуры пользовательского ввода. Поле fields хранит JSON-описание набора полей формы, что позволяет динамически настраивать структуру данных заявок без изменения схемы базы данных. Признак isActive используется для разделения актуальных и архивных форм; дополнительно фиксируется автор создания.

Сущность статуса описывает возможные состояния заявки и параметры отображения. Название статуса уникально, что исключает дублирование в справочнике. Наличие полей order и isFinal поддерживает сортировку статусов и разграничение финальных состояний.

Сущность заявки связывает пользователя, выбранную форму и текущий статус. Данные, введённые пользователем, хранятся в JSON-поле data, что согласуется с идеей настраиваемых форм. Дополнительно фиксируются комментарий, временные метки, а также момент отправки на рассмотрение (submittedAt), что позволяет различать черновики и отправленные заявки.

Сущность вложения хранит метаданные прикреплённого файла: имя, MIME-тип, размер, а также путь хранения в файловой системе сервера. Вложения связаны с заявкой и пользователем, загрузившим файл, что обеспечивает контроль доступа и возможность аудита.

Сущность истории статусов фиксирует переходы статусов заявки: исходный статус (опционально для первого события), целевой статус, пользователя, выполнившего изменение, время изменения и комментарий. Наличие истории позволяет восстанавливать цепочку обработки заявки и подтверждать корректность выполнения регламентов.

Таблица 3.2 – Основные сущности модели данных

| Сущность | Назначение | Ключевые поля (кратко) | Связи и ограничения (кратко) |
| --- | --- | --- | --- |
| User | Пользователь системы и его роль | id, username, email, passwordHash, role, createdAt | username и email уникальны; 1:M с Application, Attachment, RefreshToken; 1:M с Form (как автор); 1:M с StatusHistory (как изменивший) |

Таким образом, модель данных обеспечивает хранение заявок и их состояния, поддерживает динамическую структуру форм и данных заявок за счёт JSON-полей, а также реализует аудит обработки через историю статусов. Наличие уникальных ограничений для ключевых идентификаторов (email, username, tokenHash, имя статуса) и внешних ключей между сущностями обеспечивает целостность данных и согласованность работы бизнес-операций.

## 3.7. Конфигурация окружения и инструкция по запуску

Конфигурация системы включает параметры подключения к базе данных, настройки аутентификации, правила CORS и параметры работы cookies, а также адрес серверного API для клиентской части. Данные параметры вынесены в переменные окружения, что позволяет запускать проект в режиме разработки и в контейнерной среде без изменения исходного кода.

Для серверной части ключевыми параметрами являются строка подключения к PostgreSQL (DATABASE_URL), секреты и сроки действия JWT-токенов (JWT_ACCESS_SECRET, JWT_REFRESH_SECRET, JWT_ACCESS_TTL, JWT_REFRESH_TTL), разрешённые источники CORS (CORS_ORIGIN), параметры безопасной передачи cookies (COOKIE_SECURE, COOKIE_SAMESITE), а также настройки инфраструктуры (REDIS_URL, LOG_LEVEL и значения TTL кэша). Для клиентской части используется параметр VITE_API_BASE_URL, определяющий базовый URL API.

В проекте предусмотрены два типовых способа запуска. Для контейнерного запуска используется Docker Compose как стандартный инструмент описания и управления многоконтейнерными конфигурациями [9].

Первый способ ориентирован на разработку и предполагает запуск из исходного кода. В этом варианте после установки зависимостей выполняется инициализация базы данных (генерация Prisma-клиента, применение миграций, при необходимости заполнение демонстрационными данными), затем поднимаются сервер и веб-клиент. Такой запуск удобен для отладки, так как обеспечивает быстрый цикл изменений и позволяет использовать встроенные средства разработки (горячая перезагрузка, отладчик Node.js).

Второй способ основан на контейнеризации и предназначен для воспроизводимого развёртывания системы. Конфигурации Docker Compose включают сервисы PostgreSQL, Redis, серверного API и веб-клиента. Межсервисные зависимости дополняются healthcheck-проверками, что снижает вероятность некорректного старта при недоступности базы данных или кэша. Для режима разработки предусмотрена отдельная конфигурация, в которой исходные тексты монтируются в контейнеры, а дополнительные порты (например, порт отладчика) публикуются наружу.

Корректность запуска в контейнерной среде подтверждается состоянием сервисов (healthy) и доступностью веб-интерфейса и API. Пример результата запуска (статус контейнеров или фрагмент логов) приведён на рисунке 3.11.

## 3.8. План развёртывания системы

Развёртывание системы предполагает поставку и запуск серверной и клиентской частей совместно с инфраструктурными сервисами (СУБД PostgreSQL и кэш Redis). Для обеспечения воспроизводимости и упрощения эксплуатации используется контейнеризация и сценарии автоматизированной сборки. В качестве целевого подхода рассматриваются два уровня развёртывания: контейнерный запуск на одном узле (Docker Compose) и оркестрация в кластере (Kubernetes) как расширяемый вариант.

Базовый сценарий развёртывания в контейнерной среде включает сборку Docker-образов и запуск сервисов в фоне с помощью Docker Compose. Для удобства эксплуатации предусмотрены команды управления жизненным циклом стека (сборка, запуск, остановка, просмотр логов). В данном сценарии веб-клиент раздаётся через Nginx, серверное API запускается как отдельный контейнер и получает параметры подключения к PostgreSQL/Redis через переменные окружения. Healthcheck-проверки используются как механизм контроля готовности сервисов и корректной последовательности старта.

Альтернативный сценарий развёртывания ориентирован на использование Kubernetes. Манифесты организованы с применением Kustomize и разделены на базовую конфигурацию и оверлеи окружений. Базовый набор ресурсов включает пространства имён, Deployments и Services для серверной и клиентской частей, PVC для компонентов, требующих персистентного хранения, конфигурацию через ConfigMap и Secret, а также Ingress для маршрутизации внешнего трафика. Для серверного приложения предусмотрен HPA, позволяющий автоматически масштабировать число реплик при росте нагрузки при наличии metrics-server.

Оверлеи окружений (dev/prod) задают отличия в параметрах развёртывания: пространства имён, число реплик, ограничения ресурсов и особенности Ingress (например, отдельное доменное имя и правила обработки префикса /api). Такой подход позволяет поддерживать единый набор базовых ресурсов и минимизировать риск расхождений между окружениями за счёт патчей поверх общего шаблона.

Факт успешного запуска компонентов системы в кластере Kubernetes подтверждается состоянием ресурсов в целевом пространстве имён (например, выводом команд просмотра pods/services/ingress). Пример проверки статуса развёртывания приведён на рисунке 3.12.

![](../photos/3_8_k8s_status.png)

Для автоматизации проверки качества и воспроизводимой сборки используется CI/CD на базе GitHub Actions. Пайплайн включает стадии статического анализа (lint и typecheck), модульного тестирования, интеграционного тестирования с поднятием зависимостей (PostgreSQL и Redis) и запуском миграций, а также E2E-тестирование с использованием Playwright. Таким образом, план развёртывания предусматривает практичный контейнерный запуск в Docker Compose как основной способ поставки и расширяемый вариант в Kubernetes для сценариев, где требуется оркестрация, масштабирование и централизованное управление конфигурацией. Наличие CI/CD обеспечивает регулярную проверку качества, автоматизацию тестирования и воспроизводимую сборку артефактов поставки.

Таким образом, в данном разделе описаны ключевые аспекты реализации системы обработки заявок: архитектура клиент-серверного взаимодействия и распределение ответственности между компонентами, обоснование выбранного технологического стека, модульная структура серверной части и организация клиентского приложения, спецификация программного интерфейса и принципы построения модели данных. Рассмотрены конфигурация окружения и типовые способы запуска, а также подходы к развёртыванию и автоматизации проверки качества. Совокупность принятых решений обеспечивает воспроизводимую эксплуатацию системы, согласованность клиентской и серверной частей и возможность дальнейшего развития функциональности без нарушения требований по ролям и жизненному циклу заявок.
