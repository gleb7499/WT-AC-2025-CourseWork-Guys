# 2. Разработка алгоритмов

## 2.1. Описание сущностей и связей

Разработка алгоритмов в рамках системы обработки заявок опирается на устойчивую модель предметных данных, отражающую жизненный цикл заявки: от создания пользователем черновика до изменения статусов уполномоченными ролями и фиксации истории изменений. Модель данных проектируется с учётом требований варианта 40 и реализуется в реляционной базе данных PostgreSQL с использованием ORM Prisma, что позволяет формально задать типы атрибутов, ограничения целостности и связи между сущностями [5], [6]. Модель сущностей и связей предметной области представлена на рисунке 2.1.

![ERD системы обработки заявок](../photos/2_1_erd.png)
Рисунок 2.1 – Диаграмма сущностей (ERD) системы обработки заявок

В системе выделяются основные сущности, обеспечивающие хранение данных о пользователях, настраиваемых формах, статусах обработки, заявках, вложениях и журнале изменений статусов. Дополнительно для реализации механизма аутентификации применяется сущность refresh-токена, используемая для обновления access-токена без повторного ввода учётных данных.

Таблица 2.1 – Основные сущности и связи предметной области

| --- | --- | --- | --- |
| User | Хранение учётных данных и роли доступа | `id`, `email` (unique), `username` (unique), `passwordHash`, `role`, `createdAt` | 1:M с Application (владелец заявок); 1:M с Form (создатель форм); 1:M с Attachment (загрузивший); 1:M с StatusHistory (инициатор изменения); 1:M с RefreshToken |

Связи и ограничения целостности определяют допустимые операции и обеспечивают непротиворечивость данных при выполнении алгоритмов системы. В частности, уникальность `email` и `username` предотвращает неоднозначность идентификации пользователей, уникальность `Status.name` обеспечивает однозначное обращение к системным статусам (например, `draft`, `pending`, `withdrawn`), а внешние ключи фиксируют принадлежность заявок конкретному пользователю и форме, привязку вложений к заявке и корректность ссылок на статусы в истории изменений.

Таким образом, выделенные сущности и их связи формируют основу для описания алгоритмов управления жизненным циклом заявки, обеспечивая целостность данных, возможность аудита и однозначную интерпретацию статусов.

## 2.2. Алгоритм формирования списка заявок

Под «списком заявок» в рамках варианта 40 понимается основное списочное представление заявок, отображаемое пользователю в интерфейсе и формируемое серверной частью по запросу клиента. Алгоритм должен учитывать ролевую модель (RBAC) и ограничения области видимости данных (scope), а также обеспечивать фильтрацию и постраничную выдачу для устойчивой работы при росте объёма данных.

Входными параметрами алгоритма являются идентификатор аутентифицированного пользователя и его роль, а также параметры запроса: `statusId`, `formId`, `userId`, `page`, `pageSize`. Параметр `userId` используется только для ролей администратора и модератора; для роли пользователя область видимости жёстко ограничивается собственными заявками.

Формирование результата выполняется следующим образом. На первом этапе вычисляются параметры пагинации: номер страницы приводится к целому значению не ниже 1, размер страницы приводится к целому значению и ограничивается диапазоном 1–100, при отсутствии значения используется размер страницы по умолчанию 20. Затем строятся условия отбора данных (предикат `where`) на основе фильтров `statusId` и `formId`. Далее применяется правило области видимости: если роль пользователя — `admin` или `moderator`, допускается просмотр заявок всех пользователей, а при передаче параметра `userId` добавляется дополнительный фильтр по владельцу заявки; если роль — `user`, к условиям отбора добавляется `userId = currentUser.id`, что исключает выдачу чужих заявок.

После построения условий выборки выполняются две согласованные операции к базе данных: получение страницы записей и подсчёт общего количества записей, удовлетворяющих фильтрам. Для обеспечения стабильного порядка выдачи применяется сортировка по дате создания заявки в порядке убывания. В ответ возвращается структура, содержащая список элементов и метаданные пагинации: `items`, `page`, `pageSize`, `total`. Каждый элемент списка включает сведения, необходимые для отображения (например, связанная форма и текущий статус), что снижает потребность клиента в дополнительных запросах.

Псевдокод алгоритма формирования списка заявок представлен ниже.

```text
ВХОД: currentUser(id, role), query(statusId?, formId?, userId?, page?, pageSize?)
ВЫХОД: data = { items, page, pageSize, total }

1. (skip, take, pageN, pageSizeN) := BuildPagination(page, pageSize)
   - pageN := max(int(page) or 1, 1)
   - pageSizeN := clamp(int(pageSize) or 20, 1..100)
   - skip := (pageN - 1) * pageSizeN

2. where := {}
3. if statusId задан -> where.statusId := statusId
4. if formId задан   -> where.formId := formId

5. if currentUser.role ∈ {admin, moderator} then
      if userId задан -> where.userId := userId
   else
      where.userId := currentUser.id

6. items := SELECT Application
          WHERE where
          ORDER BY createdAt DESC
          OFFSET skip LIMIT take
          INCLUDE (form, status)

7. total := COUNT(Application WHERE where)

8. return { items, page: pageN, pageSize: pageSizeN, total }
```

Представленный алгоритм обеспечивает выполнение требований по трекингу статуса (каждая заявка в списке содержит актуальный статус), разграничению доступа (пользователь не получает чужие заявки), а также масштабируемости за счёт пагинации и ограничений размера страницы.

## 2.3. Алгоритмы ключевых операций

Ключевые операции системы определяются требованиями варианта 40 и связаны с управлением жизненным циклом заявки и сопутствующими данными. К критичным операциям относятся: создание заявки в статусе «черновик», редактирование и удаление черновика, отправка на рассмотрение (submit), изменение статуса уполномоченными ролями, отзыв заявки, а также работа с вложениями при соблюдении ограничений доступа и лимитов. При выполнении операций используются унифицированные правила валидации входных данных и обработки ошибок (например, проверка формата UUID, ограничение длины комментария), а также централизованный контроль прав (роль и область видимости).

Жизненный цикл заявки начинается с создания новой записи пользователем. Назначение данной операции заключается в формировании заявки на основе выбранной активной формы и фиксации стартового состояния жизненного цикла в системном статусе `draft`.

Выполнение операции включает следующие шаги:

1. Проверяется корректность входных данных (наличие `formId`, структуры `data`, ограничения на длину `comment`).
2. Выполняется проверка доступности формы: форма должна существовать и быть активной.
3. Определяется системный статус `draft` (по имени статуса).
4. Создаётся запись заявки с привязкой к пользователю и форме, присваивается `statusId = draft`.
5. Создаётся запись истории статусов: переход `null → draft` с указанием инициатора.
6. Возвращается созданная заявка.

Ниже приведён псевдокод операции.

```text
ВХОД: currentUser(id), payload(formId, data, comment?)
ВЫХОД: application

1. Validate(payload)
2. form := FindFormById(formId)
3. if form отсутствует или form.isActive = false -> error(400, invalid_form)
4. draftStatus := EnsureStatusByName("draft")
5. application := CreateApplication(
   formId=formId,
   userId=currentUser.id,
   statusId=draftStatus.id,
   data=data,
   comment=comment
   )
6. CreateStatusHistory(applicationId=application.id,
   fromStatusId=null,
   toStatusId=draftStatus.id,
   changedById=currentUser.id,
   comment="created")
7. return application
```

До отправки на рассмотрение пользователь выполняет корректировку данных заявки, а при необходимости может удалить черновик. Для роли пользователя действует ограничение: изменять и удалять разрешено только собственные заявки и только в статусе `draft`; администратору допускается обход данного ограничения.

Редактирование выполняется следующим образом:

1. Проверяется корректность идентификатора заявки.
2. Загружается заявка по `id`; если не найдена, возвращается ошибка `404`.
3. Проверяется принадлежность заявки (владелец или admin).
4. Для роли пользователя дополнительно проверяется, что текущий статус — `draft`, иначе возвращается `403`.
5. Выполняется обновление полей (`data`, `comment`) с частичным обновлением.

Удаление черновика выполняется следующим образом:

1. Загружается заявка; при отсутствии — `404`.
2. Для роли пользователя проверяется принадлежность и статус `draft`, иначе — `403`.
3. Выполняется удаление заявки.

После заполнения черновика выполняется операция отправки на рассмотрение (`submit`), переводящая заявку из состояния редактируемого черновика в состояние обработки. Одновременно фиксируется факт отправки (временная метка `submittedAt`) и создаётся запись в журнале истории статусов.

Операция отправки выполняется по следующей схеме:

1. Загружается заявка по `id`; при отсутствии — `404`.
2. Проверяется, что операцию выполняет владелец заявки или администратор.
3. Проверяется, что текущий статус заявки — `draft` (для роли пользователя); при нарушении — `403`.
4. Определяются статусы `draft` и `pending` по их системным именам.
5. Заявка обновляется: `statusId := pending`, `submittedAt := now()`.
6. В журнале создаётся запись `draft → pending` с указанием инициатора.

Ниже приведён псевдокод операции.

```text
ВХОД: currentUser(id, role), applicationId
ВЫХОД: updatedApplication

1. app := FindApplicationById(applicationId)
2. if app отсутствует -> error(404, not_found)
3. AssertIsOwnerOrAdmin(currentUser, app.userId)
4. draft := EnsureStatusByName("draft")
5. pending := EnsureStatusByName("pending")
6. if currentUser.role != admin and app.statusId != draft.id -> error(403, forbidden)
7. updated := UpdateApplication(id=applicationId,
   statusId=pending.id,
   submittedAt=now())
8. CreateStatusHistory(applicationId=applicationId,
   fromStatusId=app.statusId,
   toStatusId=pending.id,
   changedById=currentUser.id,
   comment="submitted")
9. return updated
```

Дальнейшая обработка заявок выполняется ответственными ролями посредством операции изменения статуса. Операция доступна только `admin` и `moderator`. При изменении статуса допускается фиксировать комментарий, а факт перехода обязательно отражается в `StatusHistory`.

Изменение статуса выполняется по следующей схеме:

1. Проверяется роль: операция разрешена только `admin` и `moderator`.
2. Загружается заявка по `id`; при отсутствии — `404`.
3. Проверяется существование целевого статуса по `statusId`; при отсутствии — ошибка `400`.
4. Заявка обновляется: `statusId := newStatusId`, при наличии — обновляется комментарий.
5. В журнале создаётся запись перехода `oldStatusId → newStatusId` с указанием инициатора и комментария.

Отдельной операцией жизненного цикла является отзыв заявки (`withdraw`). Отзыв доступен владельцу (или администратору) и запрещён для заявок, находящихся в финальном статусе (`isFinal = true`). При выполнении операции заявка переводится в системный статус `withdrawn`.

Операция отзыва выполняется по следующей схеме:

1. Загружается заявка вместе с текущим статусом; при отсутствии — `404`.
2. Проверяется принадлежность (владелец или admin).
3. Проверяется, что текущий статус не является финальным; иначе — `403`.
4. Определяется статус `withdrawn` по имени.
5. Заявка обновляется: `statusId := withdrawn`.
6. Создаётся запись истории статусов `oldStatusId → withdrawn`.

Работа с вложениями выделяется в отдельный класс операций, поскольку одновременно затрагивает правила доступа и ресурсные ограничения. Алгоритмы операций с вложениями реализуют два класса требований: (1) разграничение доступа к вложениям по области видимости заявки и роли; (2) соблюдение лимитов на число и суммарный объём вложений. Дополнительно действует правило жизненного цикла: для роли пользователя добавление и удаление вложений допускается только для заявок в статусе `draft`.

Добавление вложения (создание метаданных) выполняется следующим образом:

1. Проверяется корректность `applicationId` и атрибутов файла (`filename`, `mimeType`, `fileSize`).
2. Выполняется проверка прав доступа к заявке: владелец заявки, модератор или администратор.
3. Запрещается добавление вложений для роли модератора.
4. Для роли пользователя дополнительно проверяется, что заявка находится в статусе `draft`.
5. Подсчитывается количество вложений по заявке; при превышении лимита (10) возвращается ошибка `400`.
6. Подсчитывается суммарный размер вложений по заявке; при превышении лимита (50 МБ) возвращается ошибка `400`.
7. Генерируется серверный путь хранения файла и создаётся запись вложения.

Ниже приведён псевдокод операции.

```text
ВХОД: currentUser(id, role), payload(applicationId, filename, mimeType, fileSize)
ВЫХОД: attachment

1. Validate(payload)
2. app := FindApplicationById(applicationId) + include(status)
3. if app отсутствует -> error(404, not_found)
4. if not (isOwner(app) or role ∈ {admin, moderator}) -> error(403, forbidden)
5. if role == moderator -> error(403, forbidden)
6. if role != admin and app.status.name != "draft" -> error(403, forbidden)
7. if CountAttachments(applicationId) >= 10 -> error(400, validation_failed)
8. if SumFileSize(applicationId) + fileSize > 50MB -> error(400, validation_failed)
9. filePath := "uploads/" + applicationId + "/" + uuid() + "-" + sanitize(filename)
10. attachment := CreateAttachment(applicationId, filename, mimeType, fileSize, filePath, uploadedById=currentUser.id)
11. return attachment
```

Просмотр вложений выполняется следующим образом:

1. Для получения списка обычным пользователем требуется параметр `applicationId`; иначе возвращается ошибка `400`.
2. Выполняется проверка прав доступа к заявке (владелец или роли `admin/moderator`).
3. Возвращается список метаданных вложений, отсортированных по времени загрузки (по убыванию).

Удаление вложения выполняется следующим образом:

1. Загружается вложение и связанная заявка со статусом; при отсутствии — `404`.
2. Проверяется право удаления: владелец заявки или admin.
3. Для роли пользователя дополнительно проверяется, что заявка находится в статусе `draft`.
4. Выполняется удаление записи вложения.

Таким образом, представленные алгоритмы ключевых операций определяют последовательность действий и контрольных проверок, необходимых для корректного управления заявками и вложениями, а также обеспечивают соблюдение бизнес-правил варианта 40 и требований безопасности (RBAC/scope) при изменении состояния заявки.

## 2.4. Транзакции и согласованность данных

Согласованность данных в системе обработки заявок обеспечивается на двух уровнях: (1) на уровне базы данных за счёт ограничений целостности и ACID-семантики PostgreSQL; (2) на уровне прикладных алгоритмов, которые определяют порядок проверок и изменений состояния.

Дополнительно в системе может использоваться кэширование части данных во внешнем хранилище Redis; при этом консистентность обеспечивается тем, что критичные операции изменения состояния выполняются через основную транзакционную БД, а кэш применяется для данных с ограниченным временем жизни и допускает обновление по истечении TTL [7].

На уровне схемы данных применяются механизмы ссылочной и доменной целостности. Уникальные ограничения `User.email`, `User.username`, `RefreshToken.tokenHash` и `Status.name` предотвращают появление неоднозначных идентификаторов и дублирующих системных значений. Внешние ключи в сущностях `Application`, `Attachment`, `StatusHistory` фиксируют принадлежность заявки пользователю и форме, вложений — заявке, а истории статусов — заявке и конкретным статусам. Таким образом, любая запись в прикладных таблицах не может быть создана без существования связанных сущностей, а попытки нарушить ссылочную целостность завершаются ошибкой на стороне СУБД.

На уровне прикладных операций значительная часть изменений выполняется атомарно в рамках одного SQL-выражения (операции `create`, `update`, `delete` Prisma), что гарантирует целостность отдельного шага модификации. Например, смена статуса заявки (`submit`, `changeStatus`, `withdraw`) реализуется как единичная операция обновления `Application.statusId` (а также `submittedAt` при отправке), что исключает «частичное» применение конкретного обновления.

При этом ряд операций имеет составной характер и требует согласованного выполнения нескольких модификаций: изменение состояния заявки должно сопровождаться записью в журнале `StatusHistory`. В текущей реализации изменения сущности `Application` и добавление записи `StatusHistory` выполняются последовательно. Для обеспечения строгой атомарности и исключения ситуаций, когда статус изменён, но запись истории не создана (например, при ошибке вставки истории), такие действия концептуально должны выполняться в рамках единой транзакции. В контексте курсового проекта данная согласованность поддерживается порядком действий и централизованной обработкой ошибок, а усиление гарантий атомарности предусматривается как направление развития.

Отдельный аспект согласованности связан с параллельным доступом при получении списков и вычислении агрегатов. В алгоритме формирования списка заявок получение страницы (`findMany`) и подсчёт общего числа записей (`count`) выполняются параллельно, что повышает производительность, однако при конкурентных изменениях данных возможны незначительные расхождения между `items` и `total` в рамках одного ответа. Для сценариев отображения списка данное поведение является допустимым, поскольку при последующем запросе данные приводятся к актуальному состоянию.

Для вложений применяются лимиты на количество и суммарный объём (10 файлов и 50 МБ). В текущей реализации соблюдение лимитов обеспечивается проверками `count` и `aggregate(_sum)` перед созданием записи `Attachment`. При высокой конкурентности возможны гонки (несколько одновременных загрузок могут пройти проверку до вставки). Для строгого соблюдения лимитов в условиях параллельных запросов данные операции целесообразно выполнять транзакционно с использованием блокировок или более строгого уровня изоляции, либо переносить часть ограничений на уровень СУБД.

Таким образом, согласованность данных достигается сочетанием ограничений целостности на уровне PostgreSQL и проверок на уровне прикладной логики, а транзакционный подход рассматривается как механизм усиления гарантий для составных операций (обновление состояния заявки и запись аудита, а также контроль лимитов вложений) при параллельной нагрузке.

## 2.5. Схема аутентификации

Аутентификация и авторизация пользователей реализованы на основе пары токенов JWT (JSON Web Token): короткоживущего access-токена и долгоживущего refresh-токена. Access-токен используется для доступа к защищённым ресурсам и передаётся клиентом в HTTP-заголовке `Authorization: Bearer <accessToken>`. Refresh-токен используется для обновления access-токена без повторного ввода учётных данных и хранится на стороне клиента в HttpOnly cookie `refresh_token` [8].

Access- и refresh-токены подписываются алгоритмом HS256 с использованием секретов и времени жизни, задаваемых конфигурацией окружения (`accessTokenSecret`, `refreshTokenSecret`, `accessTokenTtl`, `refreshTokenTtl`). Полезная нагрузка access-токена включает идентификатор пользователя (`sub`) и роль (`role`), что позволяет выполнять разграничение доступа (RBAC) на уровне middleware и сервисов. Refresh-токен дополнительно содержит идентификатор сессии `jti`, применяемый для контроля и ротации сессий.

Для управления refresh-сессиями в базе данных поддерживается таблица `RefreshToken`, в которой хранится не сам refresh-токен, а хэш идентификатора `jti` (поле `tokenHash = sha256(jti)`), а также метаданные сессии (`expiresAt`, `revokedAt`, `replacedByTokenId`, `createdByIp`, `userAgent`). Такой подход позволяет отзывать refresh-сессии на сервере и снижает последствия компрометации базы данных.

Процедура регистрации и входа в систему выполняется по единому принципу: после валидации данных и успешной проверки учётных данных формируется новая refresh-сессия и выдаётся пара токенов. При регистрации пароль сохраняется в виде стойкого хэша (`bcrypt`). Далее генерируется `jti`, выпускаются access- и refresh-токены, создаётся запись refresh-сессии в таблице `RefreshToken`, после чего refresh-токен устанавливается в cookie, а access-токен возвращается клиенту в теле ответа вместе с профилем пользователя.

Проверка access-токена выполняется middleware аутентификации: извлекается заголовок `Authorization`, проверяется формат `Bearer <token>`, затем токен верифицируется по подписи и сроку действия. При успешной проверке в контекст запроса помещаются `req.user = { id, role }`. Для части публичных эндпоинтов используется режим «опциональной аутентификации»: при наличии заголовка он обязан быть валидным, но при отсутствии запрос допускается без пользователя.

Обновление access-токена выполняется через эндпоинт `POST /auth/refresh`. Входными данными выступает cookie `refresh_token`. Сервер верифицирует refresh-токен, извлекает `jti`, вычисляет `sha256(jti)` и проверяет наличие активной refresh-сессии в базе. При отсутствии сессии или при наличии признака отзыва (`revokedAt`) выполняется отзыв всех активных refresh-сессий пользователя и возвращается ошибка `401`. При истечении срока действия сессии она отзывается, также возвращается `401`. При успешной проверке выполняется ротация: генерируется новый `jti`, создаётся новая запись `RefreshToken` (с указанием `replacedByTokenId` для связи), старая сессия помечается как отозванная, клиенту устанавливается новая cookie `refresh_token`, а в ответе возвращается новый access-токен.

Завершение сессии (`POST /auth/logout`) реализовано как отзыв refresh-сессии, соответствующей текущей cookie `refresh_token`, с последующей очисткой cookie на стороне клиента. Если cookie отсутствует или refresh-токен некорректен, операция завершается без ошибки, что упрощает поведение клиента при истекших сессиях.

Псевдокод ключевых этапов схемы аутентификации представлен ниже.

```text
Регистрация/вход:
1) Validate(credentials)
2) CreateOrVerifyUser(credentials)
3) jti := uuid()
4) access := SignJWT({sub: userId, role}, accessSecret, accessTtl)
5) refresh := SignJWT({sub: userId, role, jti}, refreshSecret, refreshTtl)
6) Save RefreshToken(tokenHash=sha256(jti), userId, expiresAt, ip, userAgent)
7) Set-Cookie refresh_token=refresh (HttpOnly, SameSite, Secure)
8) return access + user

Обновление (refresh):
1) token := cookie.refresh_token
2) payload := VerifyJWT(token, refreshSecret)
3) session := Find RefreshToken by tokenHash=sha256(payload.jti)
4) if session missing/revoked/expired -> revoke (token or all tokens) and error(401)
5) rotate: newJti := uuid(); issue new tokens; save new session; revoke old session
6) Set-Cookie refresh_token=newRefresh
7) return newAccess + user

Доступ к защищённым ресурсам:
1) token := Authorization Bearer access
2) payload := VerifyJWT(token, accessSecret)
3) req.user := { id: payload.sub, role: payload.role }
```

Таким образом, схема аутентификации сочетает stateless-проверку access-токена с серверно управляемыми refresh-сессиями (хранение хэша `jti`, ротация и отзыв), что обеспечивает баланс между удобством пользователя, безопасностью и возможностью контролируемого завершения сессий.
