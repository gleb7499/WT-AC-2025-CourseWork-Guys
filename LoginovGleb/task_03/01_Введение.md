# Введение

Во многих организациях и проектных командах процесс приёма заявок (на участие в мероприятии, получение услуги, регистрацию в программе, предоставление документов и т.п.) представляет собой повторяющийся цикл: заявитель заполняет форму, прикладывает подтверждающие файлы, затем уполномоченные лица проверяют данные и принимают решение. На практике такие процессы часто реализуются разрозненно: часть данных собирается в электронных таблицах, часть — в переписке, часть — через отдельные формы без единого механизма контроля статусов. Это затрудняет мониторинг текущего состояния обращения, повышает риск потери информации и увеличивает время обработки.

Рассматриваемая в курсовом проекте система относится к классу информационных систем управления обращениями/заявками и обеспечивает централизованный приём заявок по настраиваемым шаблонам форм с дальнейшей обработкой по ролям и обязательным трекингом статусов.

Актуальность разработки обусловлена необходимостью унификации и автоматизации процессов обработки заявок при сохранении гибкости структуры входных данных. Существенным требованием для подобных задач является поддержка «настраиваемых форм», когда состав полей определяется администратором и может изменяться без переписывания пользовательского интерфейса и серверной логики на уровне бизнес-процесса. Дополнительную значимость имеет обеспечение прозрачности жизненного цикла заявки: пользователь должен иметь возможность отслеживать состояние своего обращения, а модератор и администратор — управлять статусами и фиксировать решения.

Важным аспектом также является безопасность и разграничение прав доступа. В системе одновременно присутствуют роли с различными полномочиями (гость, пользователь, модератор, администратор), а операции над данными (включая просмотр и скачивание вложений) должны выполняться только при наличии необходимых прав. Таким образом, внедрение централизованной системы с аутентификацией, авторизацией и формализованным API позволяет повысить качество обработки заявок, снизить количество ошибок и обеспечить воспроизводимость процедур.

Практическая реализация подобных решений в веб-среде обычно опирается на архитектуру одностраничных приложений (SPA) и компонентный подход к построению интерфейса, что обеспечивает переиспользуемость элементов UI и предсказуемое управление состоянием [1]. Дополнительно использование статической типизации на уровне прикладного кода снижает вероятность ошибок интеграции между клиентом и сервером при работе с развитой моделью данных [2].

Целью курсового проекта является разработка полнофункционального веб-приложения для приёма и обработки заявок через настраиваемые формы, обеспечивающего хранение данных, работу с вложениями, управление статусами и разграничение доступа по ролям.

Для достижения поставленной цели в рамках проекта решаются следующие задачи:

- Проанализировать предметную область обработки заявок и определить основные сценарии использования для ключевых ролей (гость, пользователь, модератор, администратор).
- Спроектировать модель данных и определить набор сущностей, необходимых для хранения заявок, форм, статусов, вложений и истории изменений.
- Разработать серверную часть приложения, реализующую REST API для управления ресурсами системы, а также механизмы аутентификации и авторизации.
- Реализовать клиентскую часть веб-приложения, предоставляющую пользовательский интерфейс для создания и просмотра заявок, администрирования форм и статусов, а также обработки заявок модератором.
- Обеспечить поддержку загрузки, хранения и выдачи файлов-вложений с учётом ограничений по размерам и правам доступа.
- Подготовить инфраструктуру запуска и развёртывания (контейнеризация и конфигурация окружения), обеспечивающую воспроизводимость установки и запуска.
- Выполнить тестирование основных пользовательских сценариев и проверить корректность трекинга статусов и разграничения прав доступа.

Курсовой проект выполнен по варианту 40 — «Заявки “Да, я в деле”». В рамках варианта требуется разработать систему, в которой заявки проходят этапы обработки, а события жизненного цикла заявки фиксируются и доступны для просмотра. Минимально жизнеспособный продукт (MVP — Minimum Viable Product) включает:

- формы заявок и механизм их настройки;
- заявки и их статусы с возможностью отслеживания прогресса;
- работу с ролями пользователей (администратор, модератор, пользователь; а также гость для операций регистрации/входа);
- загрузку и управление файлами-вложениями;
- программный интерфейс на основе ресурсов `/applications`, `/forms`, `/statuses`, `/attachments`.

Ключевые сущности предметной области представлены объектами User, Form, Status, Application, Attachment, а также сущностью истории смены статусов, позволяющей фиксировать изменения состояния заявки и обеспечивать аудит действий. Приёмка MVP ориентирована на корректный трекинг статуса заявки на протяжении всего процесса обработки, включая переходы из состояния черновика к рассмотрению и дальнейшие решения уполномоченных ролей.

Таким образом, во введении обоснована актуальность разработки системы обработки заявок, определены цель и задачи проекта, а также описан вариант задания, что задаёт основу для дальнейшего формализованного представления требований, алгоритмов и архитектурных решений.
