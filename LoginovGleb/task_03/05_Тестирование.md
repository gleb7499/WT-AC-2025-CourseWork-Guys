# 4. Тестирование

## 4.1. План тестирования

Тестирование системы обработки заявок направлено на подтверждение корректности реализованных пользовательских сценариев, устойчивости серверной части при типовых ошибках ввода и соблюдения правил разграничения доступа. План тестирования построен по многоуровневой схеме и включает статический контроль качества, автоматизированные тесты серверного API и сквозную проверку пользовательских сценариев в браузере.

На предварительном этапе выполняется статическая проверка качества кода: проверка типизации TypeScript (typecheck) и проверка правил кодовой базы (lint). Данный этап позволяет выявлять ошибки на уровне компиляции и нарушения контрактов типов до запуска приложения, снижая трудозатраты на последующее функциональное тестирование.

Далее выполняется модульное тестирование (unit) серверной части. Оно применяется для проверки изолированных функций и компонент прикладного слоя: вспомогательных утилит, middleware и сервисных операций (например, обработки ошибок, проверки токенов, преобразования параметров пагинации). Модульные тесты реализованы с использованием фреймворка Vitest и не требуют развёртывания внешних сервисов, что обеспечивает быстрый цикл обратной связи при разработке. По исходным текстам набора unit-тестов определено 19 тест-кейсов (подсчёт выполнен по количеству объявлений `it(...)`/`test(...)` в файлах модульных тестов).

Следующий уровень — интеграционное тестирование (integration) серверного API. Оно предназначено для проверки взаимодействия основных модулей с базой данных и инфраструктурой, а также корректности HTTP-контрактов (коды состояния, структура ответов, обработка ошибок). Для интеграционных тестов используется тестовое окружение с отдельными параметрами конфигурации, при этом база данных перед каждым тестом приводится к предсказуемому состоянию путём автоматического сброса данных и повторного заполнения базовыми записями. Такой подход обеспечивает воспроизводимость результатов и исключает влияние остаточных данных. Интеграционные тесты выполняются через HTTP-запросы к приложению (Supertest), что приближает проверку к реальному режиму эксплуатации API. По исходным текстам набора интеграционных тестов определено 16 тест-кейсов (подсчёт выполнен по количеству объявлений `it(...)`/`test(...)`).

Для подтверждения корректности пользовательских сценариев на уровне интерфейса применяется сквозное тестирование (end-to-end, E2E) клиентского приложения. E2E-тесты выполняются в браузере с использованием Playwright и проверяют цепочки действий пользователя, включая переходы между страницами, ввод данных в формы, обработку сообщений об ошибках и проверку ограничений по ролям. Для повышения устойчивости E2E-тестов ключевые элементы интерфейса размечены идентификаторами `data-testid`, что уменьшает зависимость тестов от изменений в визуальном представлении. По исходным текстам E2E-набора определено 57 тест-кейсов (подсчёт выполнен по количеству объявлений `test(...)`).

Подход к построению E2E-проверок и формированию отчётов соответствует рекомендуемой практике использования инструмента Playwright [10].

План выполнения тестирования включает последовательность этапов: (1) статические проверки, (2) модульные тесты сервера, (3) интеграционные тесты API в тестовом окружении, (4) E2E-тесты интерфейса при запущенных сервере и клиенте. В условиях автоматизации (CI) указанные этапы целесообразно объединять в единый пайплайн, при этом отчёт Playwright формируется как артефакт сборки.

Таким образом, план тестирования обеспечивает поэтапную проверку качества системы: от выявления ошибок на уровне типизации до проверки работы пользовательских сценариев в браузере, что позволяет подтверждать соответствие реализованной функциональности требованиям и снижать риск регрессий при последующих изменениях.

## 4.2. Список тестовых сценариев

Список тестовых сценариев сформирован на основе реализованных функций системы: аутентификации и ролевого разграничения доступа, управления заявками и их статусами, администрирования справочников (форм и статусов), а также работы с вложениями. Сценарии сгруппированы по уровням тестирования, поскольку одни и те же требования проверяются разными способами: на уровне API через запросы к серверу, а на уровне интерфейса через действия пользователя в браузере.

Таблица 4.1 содержит сводный перечень базовых сценариев, рекомендуемых к выполнению при регрессионной проверке.

Таблица 4.1 – Базовые тестовые сценарии системы

| Идентификатор | Уровень | Сценарий | Предусловия | Ожидаемый результат |
| --- | --- | --- | --- | --- |
| TS-01 | E2E/API | Регистрация пользователя (валидные данные) | Система запущена, email не занят | Пользователь создаётся, выполняется вход, доступна рабочая зона |
| TS-02 | E2E/API | Регистрация (ошибки валидации: email/пароль) | Система запущена | Возвращается ошибка валидации; пользователь не создаётся |
| TS-03 | E2E/API | Вход (валидные учётные данные) | Пользователь существует | Возвращается access-токен; refresh-токен устанавливается в HttpOnly cookie |
| TS-04 | E2E/API | Вход (неверный пароль) | Пользователь существует | Возвращается отказ в доступе (401); сессия не создаётся |
| TS-05 | API | Обновление access-токена (refresh) | Есть валидная refresh-сессия | Возвращается новый access-токен; refresh-сессия ротируется |
| TS-06 | API | Выход (logout) | Есть активная refresh-сессия | Refresh-сессия отзывается; cookie очищается; дальнейший refresh даёт 401 |
| TS-07 | API | Доступ к защищённому ресурсу без токена | Нет авторизации | Возвращается 401; данные не выдаются |
| TS-08 | E2E | Контроль доступа по ролям к страницам (RBAC) | Есть учётные записи admin/moderator/user | Недоступные разделы не открываются; при прямом переходе отображается отказ |
| TS-09 | API | Получение профиля текущего пользователя | Пользователь авторизован | Возвращаются корректные данные профиля |
| TS-10 | API/E2E | Получение списка форм | Необязательно быть авторизованным | Гости видят только активные формы; администратор — полный список |
| TS-11 | API/E2E | Создание/редактирование/удаление формы (admin) | Вход под admin | Операции выполняются; для не-admin возвращается 403 |
| TS-12 | API/E2E | Управление статусами (admin) | Вход под admin | CRUD доступен; для других ролей ограничен согласно политике доступа |
| TS-13 | API/E2E | Создание заявки в статусе draft | Вход под user или admin; есть активная форма | Создаётся черновик; в истории фиксируется стартовое состояние |
| TS-14 | API/E2E | Редактирование и удаление заявки (только draft) | Есть черновик | В статусе draft изменения применяются; в иных статусах возвращается 403 |
| TS-15 | API/E2E | Отправка заявки на рассмотрение (submit) | Есть draft заявка | Статус меняется на pending; фиксируется submittedAt и запись истории |
| TS-16 | API/E2E | Смена статуса заявки (moderator/admin) | Есть заявка; вход под moderator/admin | Статус меняется; создаётся запись истории; для user возвращается 403 |
| TS-17 | API/E2E | Отзыв заявки владельцем | Заявка не в финальном статусе | Заявка переводится в withdrawn; фиксируется запись истории |
| TS-18 | API | Список заявок с фильтрацией и пагинацией | Есть набор заявок разных форм/статусов | Корректно работают page/pageSize; фильтры применяются; scope по ролям соблюдён |
| TS-19 | API/E2E | Работа с вложениями: добавление/просмотр/удаление | Есть draft заявка и файл | Вложение создаётся и доступно владельцу; удаление доступно владельцу/admin |
| TS-20 | API | Лимиты вложений (количество/общий размер) | Есть draft заявка | При превышении лимитов возвращается ошибка; данные не повреждаются |
| TS-21 | API | Служебные эндпоинты здоровья и готовности | Система запущена | health возвращает ok; ready отражает доступность базы данных |

При выполнении E2E-сценариев рекомендуется использовать предзаполненные тестовые учётные записи и демонстрационные данные, поскольку они обеспечивают воспроизводимость проверки ролей и бизнес-переходов без ручной подготовки окружения. В интеграционных тестах серверной части дополнительно применяется автоматический сброс и повторное заполнение базы данных перед выполнением тестов, что исключает влияние предыдущих запусков.

Таким образом, перечисленные сценарии покрывают критические функции системы: безопасность доступа (аутентификация и RBAC), корректность жизненного цикла заявки (draft -> pending -> финальные состояния/withdrawn), администрирование справочников, работу с вложениями и устойчивость API при ошибках ввода и нарушениях прав.

## 4.3. Критерии прохождения тестов

Критерии прохождения тестов определяют условия, при которых проверка считается успешной (pass), а также условия, при которых фиксируется отказ (fail). Для обеспечения сопоставимости результатов критерии задаются единообразно для всех уровней тестирования и конкретизируются для ключевых групп сценариев.

Общими критериями успешного прохождения автоматизированных тестов являются: корректное завершение набора тестов со статусом выполнения без ошибок; отсутствие необработанных исключений на сервере; соответствие фактических HTTP-ответов ожидаемым контрактам (коды статуса и структура данных); корректность ролевого разграничения доступа (401 для неаутентифицированных запросов и 403 для недостаточных прав).

Дополнительным критерием для E2E-тестов является устойчивость пользовательского сценария: тест должен проходить без ручных действий, а взаимодействие с ключевыми элементами интерфейса должно выполняться по стабильным селекторам (в том числе `data-testid`).

Таблица 4.2 содержит минимально необходимые критерии прохождения, привязанные к идентификаторам тестовых сценариев.

Таблица 4.2 – Критерии прохождения тестовых сценариев

| Группа сценариев | Идентификаторы | Критерии pass | Критерии fail |
| --- | --- | --- | --- |
| Регистрация и вход | TS-01…TS-04 | При валидных данных выполняется успешная аутентификация, формируется сессия: access-токен возвращается в ответе, refresh-токен устанавливается в HttpOnly cookie; при ошибках ввода или неверном пароле возвращается отказ (коды 4xx) без создания пользователя/сессии | Создан пользователь при невалидных данных; отсутствует cookie refresh при успешном входе; возвращён неверный код статуса или нарушен формат ответа |
| Обновление токена и выход | TS-05…TS-06 | Refresh-операция выдаёт новый access-токен и корректно обрабатывает ротацию сессии; logout отзывает refresh-сессию, повторный refresh возвращает 401 | Refresh выдаёт токен при отозванной/невалидной сессии; logout не инвалидирует сессию; cookie не очищается (если предусмотрено контрактом) |
| Защищённые ресурсы и RBAC | TS-07…TS-09 | Без авторизации сервер возвращает 401; при наличии токена профиль пользователя доступен; доступ к страницам/операциям соответствует роли | Данные выдаются без авторизации; операции доступны для роли, которой они не предназначены; возвращаются несоответствующие коды 401/403 |
| Формы и статусы | TS-10…TS-12 | Гости видят только активные формы; административные операции доступны только для роли admin; для остальных ролей возвращается 403 | Гости получают доступ к скрытым/неактивным данным; CRUD доступен не-admin; отсутствует корректная обработка ошибок доступа |
| Жизненный цикл заявки | TS-13…TS-17 | Черновик создаётся и редактируется только в статусе draft; submit переводит в pending и фиксирует событие; смена статуса доступна moderator/admin и фиксируется историей; владелец может отозвать заявку в допустимых состояниях | Изменения применяются вне draft; статус меняется без прав; отсутствует запись истории при переходах; submit/withdraw нарушают допустимые переходы |
| Списки заявок, фильтрация, пагинация | TS-18 | Параметры page/pageSize корректно ограничивают выборку; фильтры применяются; область видимости данных соответствует роли (scope) | Пагинация возвращает некорректный набор данных; фильтры игнорируются; пользователь видит чужие заявки |
| Вложения и лимиты | TS-19…TS-20 | Добавление/просмотр/удаление вложений соответствует правам (владелец/admin) и ограничениям; превышение лимитов возвращает ошибку без порчи данных | Вложения доступны посторонним; лимиты не применяются; превышение лимитов приводит к неконсистентному состоянию |
| Технические эндпоинты | TS-21 | Эндпоинты health/ready возвращают ожидаемый формат и коды; ready корректно отражает доступность зависимостей | health/ready возвращают неверный код/формат; ready сообщает «ok» при недоступных зависимостях |

Таким образом, заданные критерии обеспечивают проверку не только факта выполнения операций, но и соблюдения контрактов API, ограничений безопасности и согласованности данных.

## 4.4. Отчёт о результатах тестирования

Отчёт о результатах тестирования предназначен для фиксации итогов выполнения тестов по уровням (unit, integration, E2E) и подтверждения готовности системы к демонстрации и дальнейшему развитию. В рамках проекта отчёт формируется на основе консольного вывода тестовых раннеров и артефактов, которые автоматически создаются средствами тестирования (в частности, отчёта Playwright).

В качестве минимально необходимого состава отчёта фиксируются: дата и версия тестируемой сборки; перечень выполненных наборов тестов; суммарный результат (passed/failed); перечень упавших сценариев (при наличии) и краткое описание причин; ссылки на артефакты (логи, отчёты, скриншоты E2E) в случае выполнения в CI.

Таблица 4.3 представляет рекомендуемую форму отчёта, которую следует заполнять после каждого регрессионного прогона.

Таблица 4.3 – Форма отчёта о результатах тестирования

| Уровень | Инструмент | Объект проверки | Результат прогона | Примечание |
| --- | --- | --- | --- | --- |
| Unit | Vitest | Изолированные функции и компоненты серверной части | Успешно: 19/19 (failed: 0) | Ошибок выполнения не обнаружено |
| Integration | Vitest + Supertest | HTTP-контракты API и взаимодействие с БД | Успешно: 16/16 (failed: 0) | Тестовая БД сбрасывается и заполняется перед тестами |
| E2E | Playwright | Пользовательские сценарии в браузере | Успешно: 57/57 (failed: 0) | Сформирован отчёт Playwright (см. рисунок 4.2) |

Если при выполнении тестов обнаруживаются несоответствия, в отчёте дополнительно фиксируются: идентификатор сценария (например, TS-15), фактическое поведение системы, ожидаемое поведение, условия воспроизведения и рекомендации по исправлению. После устранения дефекта выполняется повторный прогон соответствующего набора тестов с фиксацией обновлённого результата.
