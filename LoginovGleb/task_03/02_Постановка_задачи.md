# 1. Постановка задачи

## 1.1. Исходные данные

Предметная область проекта связана с организацией процесса приёма и обработки заявок в веб-среде. Под заявкой понимается структурированный набор данных, сформированный пользователем на основе заранее настроенной формы и, при необходимости, дополненный файлами-вложениями. После создания заявка проходит последовательные этапы обработки, которые отражаются в виде статусов; переходы между статусами выполняются уполномоченными ролями и фиксируются в истории.

Исходными данными для разработки выступают требования варианта 40 «Заявки “Да, я в деле”», включающие:

К указанным требованиям относятся роли и пользовательские сценарии (гость для операций регистрации/входа; пользователь для создания и отслеживания заявок; модератор для рассмотрения и изменения статуса; администратор для управления пользователями, формами и статусами), перечень ключевых сущностей и связей (User, Form, Status, Application, Attachment и StatusHistory как журнал изменений жизненного цикла заявки), необходимость поддержки настраиваемых форм (с хранением схемы полей и валидацией пользовательского ввода по этой схеме), а также требование трекинга статуса заявки как критерий приёмки MVP.

С точки зрения информационного обмена система является клиент-серверной и использует несколько форматов передачи данных. Основной обмен между клиентским приложением и серверным API выполняется в формате JSON и включает операции регистрации/аутентификации, создание и редактирование заявок, управление формами и статусами, а также получение списков и детальных представлений сущностей. Для загрузки файлов-вложений применяется формат multipart/form-data, в котором бинарное содержимое файла передаётся совместно с идентификатором заявки. Доступ к защищённым ресурсам осуществляется с использованием заголовка авторизации `Authorization: Bearer <jwt>`, при этом для части операций предусматривается механизм обновления access-токена посредством refresh-токена.

Реализация серверной части в виде HTTP API в рамках курсового проекта целесообразна на платформе Node.js и типовом веб-фреймворке для маршрутизации и обработки запросов, что соответствует распространённой практике построения прикладных сервисов и упрощает интеграцию с клиентом [3], [4].

Входные данные, формируемые пользователями и администраторами в рамках основных сценариев, включают:

- Данные учётной записи (регистрация/вход):
   - email (строка в формате email, уникальная);
   - username (строка 3–50 символов, буквы/цифры, уникальная);
   - password (строка, не менее 6 символов).
- Описание формы заявки (Form), создаваемое администратором:
   - name (название формы);
   - description (описание);
   - fields (описание полей формы в виде JSON-структуры, определяющей состав, типы и обязательность полей пользовательского ввода);
   - is_active (признак активности формы).
- Данные заявки (Application), создаваемые пользователем:
   - form_id (идентификатор выбранной формы);
   - data (JSON-объект с заполненными значениями полей формы; валидируется по схеме, заданной в Form.fields);
   - comment (опциональный комментарий, в том числе используемый модератором при принятии решения);
   - submitted_at (время отправки на рассмотрение, заполняется при переходе из состояния черновика).
- Статусы (Status), определяющие жизненный цикл заявки и создаваемые администратором:
   - name (уникальное имя статуса);
   - color (цветовое представление для UI);
   - order (порядок в жизненном цикле);
   - is_final (признак финального статуса).
- Вложения (Attachment), загружаемые пользователем в рамках заявки:
   - filename (имя файла);
   - mime_type (тип содержимого, ограниченный допустимыми форматами);
   - file_size (размер файла, ограниченный сверху);
   - file_path (путь хранения, формируемый на стороне сервера).

Принятые в варианте ограничения на исходные данные задают дополнительные условия корректности, в частности: уникальность email и имени пользователя, лимиты на размеры и количество прикрепляемых файлов, а также ограничение на редактирование и загрузку вложений только для заявок, находящихся в состоянии черновика.

Таким образом, в подразделе определены исходные данные и их форматы, а также зафиксированы ограничения предметной области, которые в дальнейшем используются при проектировании модели данных и формализации правил обработки заявок.

## 1.2. Функциональные требования

Функциональные требования формулируются на основе пользовательских историй и матрицы прав варианта 40 и разделяются на базовый функционал минимально жизнеспособного продукта (MVP) и дополнительные возможности.

Функциональные требования (MVP) охватывают подсистемы аутентификации, управления предметными сущностями и контроля жизненного цикла заявки. На уровне идентификации пользователя система должна поддерживать регистрацию по данным `{email, username, password}` с проверкой корректности и уникальности атрибутов, а также вход по `{email, password}` с выдачей access-токена (JWT) и refresh-токена. Для обеспечения непрерывности пользовательской сессии требуется механизм обновления access-токена по refresh-токену без повторного ввода учётных данных и операция завершения сессии (logout), приводящая к отзыву/удалению refresh-токена.

В части управления формами заявок система должна предоставлять просмотр списка доступных форм, включая гостевой доступ к активным формам. Администратор должен иметь возможность создавать, редактировать и удалять формы, а также управлять их активностью, определяющей доступность форм для подачи заявок. Схема полей формы хранится в структуре `fields` и служит источником описания состава пользовательского ввода; при изменении формы должны актуализироваться данные, необходимые для корректной валидации.

Для организации жизненного цикла заявок требуется подсистема статусов. Система должна поддерживать просмотр списка статусов, а также операции создания, редактирования и удаления статусов администратором. В составе статуса должны поддерживаться свойства, необходимые для UI и регламента обработки (в частности, порядок прохождения и признак финального состояния).

Подсистема заявок должна обеспечивать создание пользователем заявки по выбранной форме и редактирование данных до отправки на рассмотрение, то есть только в состоянии «черновик». До отправки на рассмотрение допускается удаление заявки в пределах прав доступа. Отправка заявки на рассмотрение (операция submit) должна фиксировать момент отправки и инициировать смену статуса. Для работы с данными необходимы операции просмотра списка заявок с фильтрацией (по пользователю, форме, статусу) и постраничным выводом, а также получение детальной информации о заявке, включающей текущий статус, заполненные данные, вложения и историю изменений.

Трекинг статусов и аудит должны обеспечивать воспроизводимость действий и возможность контроля процесса. При создании заявке автоматически присваивается статус `draft`, а при смене статуса (для ролей модератора/администратора) должна существовать возможность добавления комментария. Каждый переход статуса фиксируется в журнале истории с указанием исходного и целевого статуса, инициатора изменения и времени события, а пользователь должен иметь возможность просматривать историю изменения статуса для отслеживания прогресса обработки.

Для работы с документами требуется подсистема вложений, поддерживающая загрузку файлов к заявке в формате multipart/form-data с проверкой ограничений на тип и размер, получение списка вложений, скачивание вложений при соблюдении прав доступа и удаление вложений в пределах прав доступа и условий бизнес-процесса (например, для черновика).

Функциональные требования предполагают разграничение доступа по ролям (RBAC) и ограничения области видимости данных (scope). Операции системы должны быть доступны в зависимости от роли (admin/moderator/user/guest), при этом пользователь должен иметь доступ только к собственным заявкам и вложениям, тогда как модератор и администратор — к более широкому набору данных.

Для однозначной интерпретации ролей и операций требования к доступу фиксируются следующей моделью (укрупнённо). Укрупнённая матрица прав доступа по ролям приведена в таблице 1.1.

Дополнительные возможности (после MVP) включают:

- Поддержку многоэтапного согласования (workflow) за счёт расширяемого набора статусов и правил переходов.
- Расширение средств наблюдаемости и администрирования (журналирование событий, расширенная аналитика и отчёты по заявкам).
- Расширение комплекта автоматизированных тестов (интеграционные и сквозные сценарии) как части процесса качества.
- Поддержку развёртывания в оркестраторах контейнеров (например, Kubernetes) и автоматизацию в CI/CD.

Таким образом, функциональные требования описывают полный набор сценариев MVP (от аутентификации до трекинга статуса и работы с вложениями) и формируют основу для последующей разработки алгоритмов и реализации REST API.

## 1.3. Нефункциональные требования

Нефункциональные требования определяют качественные характеристики системы и условия её эксплуатации. Для рассматриваемого проекта приоритетными являются показатели производительности, требования информационной безопасности, надёжность работы при частичных отказах, масштабируемость в условиях роста нагрузки, а также наблюдаемость и сопровождаемость программного решения.

С точки зрения производительности система должна корректно обрабатывать типовые операции просмотра и поиска данных при росте объёма записей, поэтому для списочных представлений (заявок, форм, статусов) требуется поддержка фильтрации и постраничной выдачи. Для сокращения времени ответа при повторных обращениях допускается использование кэширования данных; при этом кэш рассматривается как некритичный компонент, и при его недоступности система должна сохранять работоспособность за счёт обращения к первичным источникам. Времена жизни кэшируемых данных должны задаваться параметрами окружения, что позволяет адаптировать поведение приложения под различные профили нагрузки.

Требования безопасности включают применение аутентификации на основе JWT: access-токен передаётся в заголовке `Authorization: Bearer <jwt>`, а refresh-токен хранится в HttpOnly cookie и используется для обновления access-токена без повторной аутентификации пользователя. Разграничение доступа должно обеспечиваться сочетанием ролевой модели (RBAC) и ограничением области видимости данных (scope), при котором пользователь имеет доступ только к собственным заявкам и вложениям, тогда как модератор и администратор могут работать с расширенным набором данных. Конфиденциальные параметры (секреты токенов, строки подключения и иные чувствительные значения) должны храниться во внешней конфигурации (переменных окружения) и не включаться в репозиторий в явном виде. На уровне HTTP-приложения должны применяться базовые меры защиты, включая настройку CORS для перечня разрешённых источников и установку защитных заголовков. Для предотвращения утечки данных при эксплуатации требуется, чтобы журналы запросов не содержали секретов и идентификаторов, способных привести к компрометации сессии (например, значение заголовка авторизации и cookie должны исключаться из логов либо маскироваться).

Надёжность системы обеспечивается единым подходом к обработке ошибок и предсказуемым поведением при исключительных ситуациях. Ответы об ошибках должны иметь унифицированный формат и позволять различать ошибки валидации входных данных, ожидаемые прикладные ошибки и непредвиденные исключения. В качестве отказоустойчивого поведения допускается деградация функциональности при отказе некритичных компонентов (например, кэша) без полной остановки приложения. Для интеграции с инфраструктурой развёртывания требуется наличие механизмов контроля работоспособности и готовности (health/readiness), позволяющих автоматизированным средствам определять состояние сервиса и его зависимостей.

С точки зрения масштабируемости и развёртывания приложение должно быть пригодно для запуска в контейнеризированном окружении с воспроизводимой конфигурацией и поддерживать горизонтальное масштабирование серверной части путём запуска нескольких экземпляров. Все параметры, влияющие на поведение системы (сетевые настройки, ограничения CORS, секреты, времена жизни токенов и параметров кэша), должны задаваться конфигурацией окружения без необходимости изменения исходного кода и повторной сборки.

Наблюдаемость предполагает ведение структурированных логов запросов и ошибок, достаточных для диагностики инцидентов и анализа поведения системы в эксплуатации, а также предоставление метрик (например, по количеству запросов и длительности их обработки), пригодных для сбора внешними системами мониторинга. Сопровождаемость обеспечивается модульной организацией кода и использованием статической типизации, что упрощает развитие функциональности и снижает риск регрессий; дополнительно должны предусматриваться автоматизированные тесты (модульные, интеграционные и сквозные) для контроля качества ключевых сценариев.

Таким образом, нефункциональные требования задают целевые показатели качества (производительность, безопасность, надёжность, масштабируемость и наблюдаемость), определяющие требования к архитектуре и эксплуатационным механизмам системы.

## 1.4. Ограничения и допущения

При проектировании и реализации системы приняты ограничения и допущения, определяющие границы применимости решения и условия его корректной эксплуатации.

К техническим ограничениям относится используемое окружение разработки и исполнения. Серверная часть ориентирована на платформу Node.js версии 20 и выше, клиентская часть разрабатывается с применением современного стека на базе React, а в качестве СУБД используется PostgreSQL (версия 14 и выше). Управление зависимостями и запуск в режиме разработки предполагают наличие пакетного менеджера pnpm. Для воспроизводимого развёртывания применяется контейнеризация и сценарии запуска на основе Docker Compose; при использовании оркестрации допускается масштабирование серверной части горизонтально, однако корректность работы зависит от доступности базы данных как критической зависимости.

Ограничения предметной области и бизнес-правил варианта 40 задают требования к данным и операциям пользователей. Для сущностей предусмотрены ограничения на формат и уникальность атрибутов (например, корректность email и уникальность идентификаторов пользователя/статуса), а также на длину текстовых полей (в частности, для названия формы и комментариев). Работа с вложениями ограничена набором допустимых типов файлов (PDF, DOC/DOCX, JPG, PNG), максимальным размером одного файла (до 10 МБ), максимальным количеством файлов на одну заявку (до 10) и совокупным объёмом вложений в рамках одной заявки (до 50 МБ). Дополнительно фиксируется ограничение процесса: загрузка вложений и редактирование заявки допускаются только для заявок в состоянии «черновик», а доступ к скачиванию вложений ограничивается владельцем заявки и ролями модератора/администратора.

В качестве допущений по эксплуатации принимается, что доступ к защищённым операциям осуществляется только после аутентификации, а политика доступа реализуется в соответствии с моделью ролей и областью видимости данных. Предполагается, что секреты и параметры безопасности (JWT-секреты, параметры cookie, параметры CORS, строка подключения к базе данных) задаются через переменные окружения и корректно настроены в целевом окружении. Также принимается, что система мониторинга и диагностики может опираться на эндпоинты проверки работоспособности и готовности (health/readiness), а обмен данными между клиентом и сервером выполняется по HTTP с использованием JSON, за исключением операций загрузки файлов, где применяется multipart/form-data.

К временным и ресурсным ограничениям разработки относится выполнение работ в рамках курсового проекта, что предполагает фокус на реализации требований MVP (в первую очередь трекинга статуса заявки) и ограничение глубины проработки дополнительных возможностей (расширенные отчёты, сложные правила многоэтапного согласования, расширенная аналитика) до уровня, достаточного для демонстрации и проверки основных сценариев.

Таким образом, ограничения и допущения фиксируют технические и организационные рамки проекта и уточняют условия корректной эксплуатации решения в целевом окружении.

## 1.5. Чеклист приёмки MVP

Чеклист приёмки MVP фиксирует проверяемые критерии готовности системы и ориентирован на подтверждение ключевого требования варианта — трекинга статуса заявки. Для каждого пункта указаны способ проверки и статус реализации на момент подготовки пояснительной записки.
