# 1 Постановка задачи

## 1.1 Описание предметной области

Предметная область системы охватывает процессы создания, хранения, организации и совместного использования текстовых заметок. Пользователи системы могут создавать тетради для группировки связанных заметок, применять метки для категоризации контента и предоставлять доступ к своим тетрадям другим участникам [1].

Основные роли в системе включают администратора и обычного пользователя. Администратор обладает полными правами на управление пользовательскими аккаунтами и данными в системе. Обычный пользователь может создавать и редактировать собственные тетради и заметки, управлять метками, а также делиться тетрадями с другими пользователями, указывая уровень предоставляемого доступа [2].

Система поддерживает два уровня доступа при совместном использовании тетрадей: только чтение и редактирование. При предоставлении доступа на чтение пользователь может просматривать тетрадь и содержащиеся в ней заметки, но не может вносить изменения. Доступ с правом редактирования позволяет не только просматривать, но и изменять заметки в расшаренной тетради [3].

## 1.2 Исходные данные

Система оперирует следующими основными сущностями данных, которые хранятся в реляционной базе данных:

**User** — учётная запись пользователя. Содержит уникальный идентификатор, имя пользователя, хэш пароля и роль в системе. Имя пользователя должно быть уникальным в рамках всей системы. Роль определяет набор доступных операций и может принимать значения администратор или пользователь [4].

**Notebook** — тетрадь для группировки заметок. Каждая тетрадь имеет уникальный идентификатор, название, необязательное описание, ссылку на владельца и временные метки создания и последнего обновления. Владелец тетради обладает полными правами на управление её содержимым и может делиться ею с другими пользователями [5].

**Note** — заметка, содержащая текстовую информацию. Включает уникальный идентификатор, ссылку на тетрадь, в которой она находится, заголовок, текстовое содержимое и временные метки создания и обновления. Заметка обязательно принадлежит одной тетради, при удалении тетради все её заметки также удаляются [6].

**Label** — метка для категоризации заметок. Содержит уникальный идентификатор, название, цвет для визуального отображения и ссылку на владельца метки. Одна заметка может иметь несколько меток, и одна метка может быть применена к нескольким заметкам [7].

**Share** — запись о предоставлении доступа к тетради. Определяет, какому пользователю предоставлен доступ к какой тетради, с каким уровнем прав и когда был предоставлен этот доступ. Для одной пары тетрадь-пользователь может существовать только одна запись о доступе [8].

Связи между сущностями реализуют следующие отношения. Один пользователь может владеть множеством тетрадей, но каждая тетрадь имеет ровно одного владельца. Одна тетрадь содержит множество заметок, каждая заметка принадлежит одной тетради. Связь между заметками и метками является многие-ко-многим через промежуточную таблицу. Один пользователь может владеть множеством меток. Одна тетрадь может быть расшарена для множества пользователей, один пользователь может получить доступ ко множеству тетрадей [9].

## 1.3 Функциональные требования

Система должна обеспечивать выполнение следующих функциональных требований, разделённых на обязательные возможности MVP и дополнительные опции.

**Требования MVP:**

**FR1. Управление пользователями.** Администратор должен иметь возможность просматривать список пользователей, создавать новые учётные записи, редактировать параметры существующих пользователей и удалять аккаунты. Обычный пользователь может просматривать и редактировать параметры своей учётной записи [1].

**FR2. Аутентификация и авторизация.** Система должна обеспечивать безопасный вход пользователей с проверкой учётных данных и разграничением доступа к операциям в соответствии с ролью пользователя. Пароли должны храниться в хэшированном виде [2].

**FR3. Управление тетрадями.** Пользователь должен иметь возможность создавать новые тетради с указанием названия и необязательного описания, просматривать список своих тетрадей и тетрадей с предоставленным доступом, редактировать название и описание собственных тетрадей, удалять свои тетради. Администратор может выполнять эти операции с любыми тетрадями в системе [3].

**FR4. Управление заметками.** Пользователь должен иметь возможность создавать заметки в своих тетрадях и в тетрадях с предоставленным доступом на редактирование, просматривать содержимое заметок, редактировать заголовок и содержимое заметок при наличии соответствующих прав, удалять заметки из своих тетрадей. Администратор может выполнять операции с любыми заметками [4].

**FR5. Работа с метками.** Пользователь должен иметь возможность создавать собственные метки с указанием названия и цвета, присваивать метки своим заметкам и заметкам в расшаренных тетрадях при наличии прав на редактирование, удалять метки от заметок, фильтровать заметки по присвоенным меткам, удалять свои метки [5].

**FR6. Совместный доступ.** Владелец тетради должен иметь возможность предоставлять доступ к своей тетради другому пользователю с указанием уровня прав — только чтение или редактирование. Пользователь, получивший доступ, должен видеть расшаренную тетрадь в своём списке. Владелец тетради должен иметь возможность отозвать ранее предоставленный доступ. Администратор может управлять доступами к любым тетрадям [6].

**FR7. Просмотр истории изменений.** Система должна сохранять историю редактирования заметок, позволяя пользователям просматривать, когда и кем были внесены изменения. Это обеспечивает прозрачность при совместной работе [7].

**Дополнительные возможности:**

**FR8. Восстановление предыдущих версий.** Пользователь с правами редактирования заметки может восстановить её содержимое из предыдущей версии в истории изменений [8].

**FR9. Совместное редактирование в реальном времени.** Несколько пользователей с доступом к тетради могут одновременно редактировать заметки с синхронизацией изменений через WebSocket [9].

**FR10. Офлайн-режим.** Клиентское приложение может кэшировать данные для работы без постоянного подключения к сети с последующей синхронизацией изменений [10].

## 1.4 Нефункциональные требования

**NFR1. Производительность.** Время отклика API на типовые запросы не должно превышать 500 миллисекунд при нормальной нагрузке. Список заметок в тетради должен загружаться не более 2 секунд [1].

**NFR2. Безопасность.** Пароли пользователей должны храниться только в хэшированном виде с использованием современных алгоритмов хэширования. Аутентификация должна осуществляться с применением JWT. Передача данных между клиентом и сервером должна осуществляться по защищённому протоколу HTTPS в производственной среде. API должно быть защищено от типовых веб-уязвимостей [2].

**NFR3. Масштабируемость.** Архитектура системы должна допускать горизонтальное масштабирование серверных компонентов для увеличения пропускной способности при росте числа пользователей [3].

**NFR4. Удобство использования.** Пользовательский интерфейс должен быть интуитивно понятным и не требовать специального обучения для выполнения базовых операций. Время выполнения типовых сценариев использования должно быть минимальным [4].

**NFR5. Надёжность.** Система должна обеспечивать целостность данных при параллельных операциях нескольких пользователей. При возникновении ошибок пользователь должен получать понятные сообщения [5].

## 1.5 Ограничения и допущения

При проектировании и реализации системы приняты следующие ограничения и допущения.

**Ограничения:**

**L1.** Система не поддерживает работу с вложенными файлами и медиа-контентом — заметки содержат только текстовую информацию [1].

**L2.** Отсутствует возможность вложенности тетрадей — все тетради находятся на одном уровне иерархии [2].

**L3.** Функциональность полнотекстового поиска по содержимому заметок не реализована в текущей версии [3].

**L4.** Система не предоставляет возможности экспорта заметок в внешние форматы документов [4].

**Допущения:**

**A1.** Предполагается, что количество пользователей и объём хранимых данных не превысят возможностей одного экземпляра сервера базы данных в рамках MVP [5].

**A2.** Клиентское приложение используется в современных веб-браузерах с поддержкой стандартов ES6 и выше [6].

**A3.** Пользователи имеют стабильное подключение к сети интернет для работы с системой [7].

**A4.** Администратор несёт ответственность за своевременное резервное копирование базы данных [8].

## 1.6 Критерии приёмки MVP

Для подтверждения готовности MVP системы определены следующие критерии приёмки, которые должны быть выполнены.

**AC1. Регистрация и аутентификация.** Новый пользователь может зарегистрироваться в системе, указав уникальное имя пользователя и пароль. После регистрации пользователь может войти в систему, используя свои учётные данные. При вводе неверных учётных данных система отклоняет попытку входа с соответствующим сообщением [1].

**AC2. Создание и управление тетрадями.** Авторизованный пользователь может создать новую тетрадь с указанием названия. Созданная тетрадь отображается в списке тетрадей пользователя. Пользователь может редактировать название и описание своей тетради, а также удалять свои тетради [2].

**AC3. Создание и редактирование заметок.** Пользователь может создать заметку в своей тетради, указав заголовок и содержимое. Созданная заметка отображается в списке заметок выбранной тетради. Пользователь может редактировать заголовок и содержимое заметки, изменения сохраняются корректно [3].

**AC4. Работа с метками.** Пользователь может создать новую метку с указанием названия. Пользователь может присвоить метку любой своей заметке. Присвоенная метка отображается у соответствующей заметки. Пользователь может удалить метку от заметки [4].

**AC5. Предоставление доступа к тетради.** Владелец тетради может предоставить доступ к своей тетради другому пользователю, выбрав пользователя из списка и указав уровень доступа — только чтение или редактирование. После предоставления доступа выбранный пользователь видит расшаренную тетрадь в своём списке тетрадей с соответствующей пометкой [5].

**AC6. Использование расшаренной тетради.** Пользователь с доступом на чтение может просматривать содержимое расшаренной тетради и её заметок, но не может вносить изменения. Пользователь с доступом на редактирование может создавать новые заметки в расшаренной тетради и редактировать существующие заметки [6].

**AC7. Отзыв доступа.** Владелец тетради может отозвать ранее предоставленный доступ к своей тетради. После отзыва доступа соответствующий пользователь больше не видит эту тетрадь в своём списке и не может выполнять с ней операции [7].

**AC8. История изменений заметки.** При просмотре заметки пользователь может открыть историю изменений и увидеть список версий с указанием времени изменения. Для каждой версии отображается содержимое заметки на тот момент времени [8].

**AC9. Разграничение прав администратора.** Пользователь с ролью администратора может просматривать список всех пользователей системы, создавать новых пользователей и удалять существующие учётные записи. Администратор имеет доступ ко всем тетрадям и заметкам в системе [9].

**AC10. Обработка ошибочных ситуаций.** При попытке создать тетрадь или заметку с пустым обязательным полем система выводит сообщение об ошибке валидации. При попытке доступа к чужой тетради без предоставленного доступа система возвращает ошибку отсутствия прав [10].
