# 2 Разработка алгоритмов

## 2.1 Описание сущностей и связей

В основе системы лежит реляционная модель данных, включающая пять основных сущностей и вспомогательную таблицу для реализации связи многие-ко-многим. Каждая сущность представлена отдельной таблицей в базе данных PostgreSQL [1].

Сущность **User** описывает учётную запись пользователя системы. Таблица содержит следующие поля: идентификатор типа UUID в качестве первичного ключа, текстовое поле username с ограничением уникальности для имени пользователя, поле password_hash для хранения хэшированного пароля и текстовое поле role со значениями admin или user для определения роли. Все поля обязательны для заполнения [2].

Сущность **Notebook** представляет тетрадь для группировки заметок. Включает идентификатор UUID, текстовое поле title для названия тетради, необязательное текстовое поле description для описания, внешний ключ owner_id ссылающийся на идентификатор пользователя-владельца, временные метки created_at и updated_at типа timestamp с временной зоной. Удаление пользователя-владельца приводит к каскадному удалению всех его тетрадей [3].

Сущность **Note** описывает отдельную заметку. Содержит идентификатор UUID, внешний ключ notebook_id ссылающийся на тетрадь, текстовое поле title для заголовка, текстовое поле content для содержимого заметки, временные метки created_at и updated_at. При удалении тетради все связанные заметки удаляются каскадно [4].

Сущность **Label** представляет метку для категоризации заметок. Включает идентификатор UUID, текстовое поле name для названия метки, необязательное текстовое поле color для хранения цвета в формате HEX, внешний ключ owner_id ссылающийся на создателя метки. Связь между заметками и метками реализована через промежуточную таблицу note_labels с композитным первичным ключом из пары note_id и label_id [5].

Сущность **Share** описывает запись о предоставлении доступа к тетради. Содержит идентификатор UUID, внешний ключ notebook_id ссылающийся на тетрадь, внешний ключ user_id ссылающийся на пользователя получающего доступ, текстовое поле permission со значениями read или write, временную метку created_at. Для одной пары notebook_id и user_id может существовать только одна запись благодаря уникальному ограничению на эти поля [6].

Связи между сущностями реализуют отношения один-ко-многим и многие-ко-многим. Пользователь связан с тетрадями отношением один-ко-многим через поле owner_id в таблице notebooks. Тетрадь связана с заметками отношением один-ко-многим через поле notebook_id в таблице notes. Заметки и метки связаны отношением многие-ко-многим через промежуточную таблицу note_labels. Пользователь связан с метками отношением один-ко-многим через поле owner_id в таблице labels. Тетради и пользователи связаны через таблицу shares отношением многие-ко-многим для реализации совместного доступа [7].

## 2.2 Алгоритм формирования списка доступных тетрадей

При запросе списка тетрадей система должна вернуть пользователю как его собственные тетради, так и тетради, к которым ему предоставлен доступ. Алгоритм формирования списка включает следующие шаги [1].

На входе алгоритма имеется идентификатор текущего пользователя из JWT токена и параметры фильтрации из запроса, включая флаг отображения только расшаренных тетрадей, параметры пагинации limit и offset.

Алгоритм начинается с проверки роли пользователя. Если роль пользователя — администратор, то формируется запрос, возвращающий все тетради в системе с учётом параметров пагинации. Для каждой тетради дополнительно загружается информация о владельце [2].

Если пользователь не является администратором, то выполняется проверка флага отображения расшаренных тетрадей. При установленном флаге формируется запрос к таблице shares с условием равенства user_id идентификатору текущего пользователя. Для каждой записи shares загружается связанная тетрадь и информация о её владельце. Применяются параметры пагинации [3].

Если флаг расшаренных тетрадей не установлен, то формируется объединяющий запрос. Первая часть запроса выбирает тетради, где owner_id равен идентификатору текущего пользователя. Вторая часть запроса выбирает тетради из таблицы shares, где user_id равен идентификатору текущего пользователя. Результаты обеих частей объединяются с исключением дубликатов. Для каждой тетради загружается информация о владельце. Применяются параметры пагинации [4].

Для каждой тетради в результирующем списке вычисляется дополнительная информация. Определяется признак владения — является ли текущий пользователь владельцем тетради. Если тетрадь получена через share, то добавляется информация об уровне доступа из поля permission. Загружается количество заметок в тетради путём подсчёта записей в таблице notes с соответствующим notebook_id [5].

Результат алгоритма представляет собой массив объектов тетрадей с полями идентификатор, название, описание, информация о владельце, признак владения текущим пользователем, уровень доступа если тетрадь расшарена, количество заметок, временные метки создания и обновления [6].

## 2.3 Алгоритм проверки прав доступа к операциям

Перед выполнением операций изменения данных система должна проверить наличие соответствующих прав у пользователя. Алгоритм проверки прав включает следующие этапы [1].

На входе алгоритма имеется идентификатор пользователя, его роль, тип запрашиваемой операции и идентификатор целевого объекта. Операции классифицируются на чтение, создание, обновление и удаление [2].

Алгоритм начинается с проверки роли пользователя. Если роль равна admin, то алгоритм немедленно возвращает положительный результат, так как администратор имеет доступ ко всем операциям со всеми объектами [3].

Для обычных пользователей выполняется проверка типа целевого объекта. При операциях с тетрадью загружается запись тетради из базы данных по её идентификатору. Проверяется равенство поля owner_id идентификатору текущего пользователя. Если пользователь является владельцем, возвращается положительный результат для операций чтения, обновления и удаления [4].

Если пользователь не является владельцем тетради, выполняется запрос к таблице shares для поиска записи с условиями равенства notebook_id целевой тетради и user_id текущему пользователю. При отсутствии такой записи возвращается отрицательный результат. При наличии записи проверяется тип операции. Операция чтения разрешена при любом значении permission. Операции создания и обновления разрешены только при значении permission равном write. Операция удаления запрещена для не-владельцев [5].

При операциях с заметкой алгоритм сначала загружает заметку по идентификатору, затем загружает связанную тетрадь по полю notebook_id заметки. Далее применяется описанная выше логика проверки прав на тетрадь, так как права на заметку наследуются от прав на содержащую её тетрадь [6].

При операциях с меткой проверяется равенство поля owner_id метки идентификатору текущего пользователя. Операции разрешены только владельцу метки. Присвоение метки заметке дополнительно требует наличия прав на редактирование заметки [7].

При операциях с записью share проверяется владение тетрадью, на которую создаётся или удаляется доступ. Только владелец тетради может создавать и удалять записи share для своей тетради [8].

Результатом алгоритма является булево значение, указывающее разрешена ли операция, и необязательное сообщение об ошибке для отрицательного результата [9].

## 2.4 Алгоритм аутентификации с использованием JWT

Система использует механизм аутентификации на основе пары токенов — краткосрочного access token и долгосрочного refresh token. Алгоритм аутентификации включает процессы входа, обновления токенов и выхода [1].

**Процесс входа в систему.** На входе алгоритма имеется имя пользователя и пароль. Выполняется поиск пользователя в таблице users по полю username. При отсутствии пользователя возвращается ошибка с кодом 401 и сообщением о неверных учётных данных [2].

Если пользователь найден, выполняется проверка пароля. Предоставленный пароль хэшируется с использованием того же алгоритма и соли, что применялись при регистрации. Полученный хэш сравнивается с хэшем из поля password_hash пользователя. При несовпадении хэшей возвращается ошибка с кодом 401 [3].

При успешной проверке пароля генерируются два токена. Access token создаётся с полезной нагрузкой, содержащей идентификатор пользователя, имя пользователя и роль, с временем жизни 15 минут. Refresh token создаётся с полезной нагрузкой, содержащей только идентификатор пользователя, с временем жизни 7 дней. Оба токена подписываются секретными ключами с использованием алгоритма HS256 [4].

Access token возвращается в теле ответа в формате JSON. Refresh token устанавливается в HTTP-only cookie с параметрами sameSite равным lax и secure равным true для производственной среды. Это предотвращает доступ к refresh token из JavaScript и защищает от CSRF атак [5].

**Процесс обновления access token.** Клиентское приложение хранит access token в памяти и включает его в заголовок Authorization каждого запроса к API. При получении ответа с кодом 401 клиент выполняет запрос на обновление токена [6].

На входе алгоритма обновления имеется refresh token из cookie. Выполняется проверка подписи и срока действия токена. При невалидном токене возвращается ошибка 401. Из полезной нагрузки валидного токена извлекается идентификатор пользователя. Выполняется запрос к базе данных для получения актуальных данных пользователя [7].

Генерируется новый access token с текущими данными пользователя и временем жизни 15 минут. Опционально может быть сгенерирован новый refresh token для реализации ротации токенов. Новый access token возвращается в теле ответа. Если был создан новый refresh token, он устанавливается в cookie [8].

**Процесс выхода из системы.** При запросе выхода сервер очищает cookie с refresh token путём установки пустого значения и времени жизни в прошлом. Клиентское приложение удаляет access token из памяти. После выхода для повторного доступа требуется новый процесс входа [9].

## 2.5 Алгоритм сохранения истории изменений заметок

Для обеспечения прозрачности при совместной работе система сохраняет историю изменений заметок. В базе данных создаётся дополнительная таблица note_history для хранения версий заметок [1].

Таблица note_history содержит поля: идентификатор записи UUID, внешний ключ note_id ссылающийся на заметку, поля title и content для сохранения заголовка и содержимого версии, поле edited_by ссылающееся на пользователя внёсшего изменения, временную метку edited_at [2].

Алгоритм сохранения версии выполняется при каждом обновлении заметки. На входе имеется идентификатор заметки, новые значения title и content, идентификатор пользователя выполняющего изменение. Перед применением изменений к основной записи заметки выполняется чтение текущих значений полей title и content [3].

Создаётся новая запись в таблице note_history с текущими значениями заголовка и содержимого, идентификатором заметки, идентификатором пользователя и текущим временем. После успешного сохранения версии применяются изменения к основной записи заметки путём обновления полей title, content и updated_at [4].

При запросе истории заметки выполняется запрос к таблице note_history с условием равенства note_id идентификатору заметки, упорядоченный по полю edited_at в обратном хронологическом порядке. Для каждой версии загружается информация о пользователе, внёсшем изменения. Применяются параметры пагинации для ограничения количества возвращаемых версий [5].

Алгоритм восстановления версии позволяет откатить заметку к состоянию из истории. На входе имеется идентификатор записи в note_history. Загружается выбранная версия, извлекаются значения title и content. Создаётся новая версия в истории с текущим содержимым заметки. Применяются к заметке значения из выбранной версии. Таким образом текущее содержимое не теряется и может быть восстановлено при необходимости [6].

## 2.6 Алгоритм фильтрации заметок по меткам

Пользователь может фильтровать список заметок, выбирая одну или несколько меток. Алгоритм формирования отфильтрованного списка включает следующие этапы [1].

На входе алгоритма имеется массив идентификаторов меток для фильтрации, идентификатор тетради для ограничения области поиска, параметры пагинации. Если массив меток пуст, возвращается полный список заметок в тетради без фильтрации [2].

При наличии меток для фильтрации формируется запрос к таблице notes с соединением таблицы note_labels. Условие запроса включает равенство notebook_id указанной тетради и вхождение label_id в массив идентификаторов меток. Группировка результатов выполняется по идентификатору заметки [3].

Для реализации логики «И» при множественных метках применяется условие на количество совпадений. Подсчитывается количество различных label_id для каждой заметки. Условие HAVING требует равенства этого количества размеру массива меток. Таким образом в результат попадают только заметки, имеющие все указанные метки [4].

Для каждой заметки в результате загружаются связанные метки путём дополнительного запроса к таблице note_labels с соединением таблицы labels. Также загружается информация о тетради и временные метки создания и обновления заметки. Применяются параметры пагинации [5].

Результатом алгоритма является массив объектов заметок с полями идентификатор, заголовок, содержимое, массив присвоенных меток, информация о тетради, временные метки, а также общее количество заметок соответствующих фильтру для реализации пагинации на клиенте [6].
