# **3 Разработка программы**

## **3.1 Архитектура системы**

Система агрегации новостей «Без фейков» реализована по трёхзвенной архитектуре клиент-сервер с разделением на презентационный, логический и уровень данных [16]. Архитектура системы представлена на рисунке 3.1.

![](../photos/3_1_photo.txt)
Рисунок 3.1 – Архитектура системы

Согласно рисунку 3.1, система состоит из следующих основных компонентов.

**1. Клиентская часть (Frontend):**
   - Одностраничное приложение (SPA) на базе React 18
   - Управление маршрутизацией через React Router
   - Управление состоянием приложения через Zustand
   - Взаимодействие с API через Axios
   - Хранение JWT-токена в localStorage

**2. Серверная часть (Backend):**
   - REST API на базе Node.js и Express
   - Middleware для аутентификации и авторизации
   - Валидация входных данных с использованием Zod
   - Логирование запросов и ошибок с помощью Winston
   - Защита HTTP-заголовков с помощью Helmet
   - Настройка CORS для взаимодействия с клиентом

**3. Уровень доступа к данным:**
   - Prisma ORM для работы с базой данных
   - Миграции схемы базы данных
   - Seed-скрипты для наполнения тестовыми данными

**4. База данных:**
   - PostgreSQL 15 для хранения реляционных данных
   - Индексы для оптимизации запросов
   - Ограничения целостности (foreign keys, unique constraints)

**5. Инфраструктура:**
   - Docker для контейнеризации приложений
   - Docker Compose для оркестрации сервисов
   - pnpm для управления зависимостями в монорепозитории

Взаимодействие между компонентами осуществляется следующим образом:
1. Пользователь взаимодействует с клиентским приложением через веб-браузер
2. Клиент отправляет HTTP-запросы к REST API сервера
3. Сервер обрабатывает запросы, выполняя аутентификацию и авторизацию
4. Сервер использует Prisma ORM для выполнения операций с базой данных
5. База данных возвращает результаты запросов серверу
6. Сервер формирует ответ и отправляет его клиенту
7. Клиент обновляет интерфейс в соответствии с полученными данными

**8. Схемы валидации (src/schemas):**

**9. Конфигурация (src/config):**

Такая структура обеспечивает разделение ответственности, упрощает тестирование и поддержку кода [28].

## **3.5 Спецификация API**

API системы построено в соответствии с принципами REST и предоставляет единообразный интерфейс для взаимодействия клиента с сервером [32].

**Общие принципы API:**

1. Базовый URL: `http://localhost:3000/api`
2. Формат данных: JSON
3. Аутентификация: Bearer token в заголовке `Authorization: Bearer <token>`
4. Стандартные коды ответов:
   - 200 OK — успешный запрос
   - 201 Created — ресурс создан
   - 204 No Content — успешное удаление
   - 400 Bad Request — ошибка валидации
   - 401 Unauthorized — требуется аутентификация
   - 403 Forbidden — недостаточно прав
   - 404 Not Found — ресурс не найден
   - 500 Internal Server Error — внутренняя ошибка сервера

## **3.6 Модель данных и схема базы данных**

Модель данных реализована в PostgreSQL с использованием Prisma ORM для управления схемой и миграциями [33]. Схема базы данных показана на рисунке 3.4.

![](../photos/3_4_photo.txt)
Рисунок 3.4 – Схема базы данных

Согласно рисунку 3.4, база данных состоит из семи таблиц, описанных ранее в разделе 2.1.

**Индексация для оптимизации запросов:**

1. Индекс на `users.username` для быстрой аутентификации
2. Индекс на `tags.name` для фильтрации по тегам
3. Индекс на `articles.source_id` для фильтрации по источникам
4. Индекс на `articles.published_at` для сортировки статей
5. Составной индекс на `favorites(user_id, article_id)` для быстрой проверки существования
6. Индекс на `reports.status` для фильтрации жалоб по статусу
7. Составной индекс на `article_tags(article_id, tag_id)` для связи many-to-many

**Ограничения целостности:**

1. `FOREIGN KEY` на всех внешних ключах с каскадным удалением где применимо
2. `UNIQUE` ограничения на `users.username`, `tags.name`
3. `UNIQUE` ограничение на `favorites(user_id, article_id)` для предотвращения дубликатов
4. `CHECK` ограничения на enum-поля (`users.role`, `reports.status`)
5. `NOT NULL` ограничения на обязательных полях

Prisma автоматически генерирует типы TypeScript на основе схемы, что обеспечивает type-safety при работе с базой данных [34].

## **3.8 План развёртывания**

Система поддерживает развёртывание с использованием Docker и Docker Compose для обеспечения консистентности окружений [36].

**Структура развёртывания:**

1. **Docker образы:**
   - Образ для серверной части на базе `node:18-alpine`
   - Образ для клиентской части с nginx для раздачи статики
   - Образ PostgreSQL 15

2. **Docker Compose конфигурация:**
   - Сервис `db` (PostgreSQL)
   - Сервис `server` (Node.js API)
   - Сервис `web` (React приложение)
   - Внутренняя сеть для связи сервисов
   - Volume для персистентности данных БД

3. **Команды развёртывания:**

```bash
# Сборка образов
docker-compose build

# Запуск сервисов
docker-compose up -d

# Применение миграций
docker-compose exec server pnpm db:push

# Наполнение тестовыми данными
docker-compose exec server pnpm db:seed

# Просмотр логов
docker-compose logs -f

# Остановка сервисов
docker-compose down
```

4. **Продакшн-окружение:**

Для продакшн-развёртывания рекомендуется:
- Использование управляемой БД (AWS RDS, Azure Database for PostgreSQL)
- Настройка reverse proxy (nginx) для SSL/TLS
- Использование orchestration системы (Kubernetes) для масштабирования
- Настройка CI/CD pipeline для автоматического развёртывания
- Мониторинг и логирование (Prometheus, Grafana, ELK stack)
- Регулярное резервное копирование базы данных

**Примерная схема развёртывания в Kubernetes:**

1. Deployment для API сервера с несколькими репликами
2. Deployment для фронтенд приложения
3. StatefulSet для PostgreSQL (или использование внешнего managed сервиса)
4. Service для внутренней связи между компонентами
5. Ingress для маршрутизации внешнего трафика
6. ConfigMap для конфигурации
7. Secret для хранения чувствительных данных (пароли, ключи)

Такой подход обеспечивает высокую доступность, масштабируемость и отказоустойчивость системы в продакшн-окружении [37].
