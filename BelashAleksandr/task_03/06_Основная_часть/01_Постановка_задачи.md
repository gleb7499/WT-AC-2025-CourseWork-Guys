# **1 Постановка задачи**

## **1.1 Описание предметной области и варианта**

Предметной областью курсового проекта является агрегация новостей из различных источников с механизмами контроля качества информации [1]. Система «Без фейков» предназначена для сбора, хранения и отображения новостных статей, предоставляя пользователям удобный интерфейс для работы с новостным контентом.

Основными объектами предметной области являются:

- **Источники новостей (Source)** — внешние ресурсы, из которых агрегируются новости
- **Статьи (Article)** — новостные материалы, получаемые от источников
- **Теги (Tag)** — тематические метки для классификации статей
- **Пользователи (User)** — участники системы с различными ролями
- **Избранное (Favorite)** — персональные коллекции статей пользователей
- **Жалобы (Report)** — сообщения пользователей о недостоверном контенте

Система реализует следующие основные сценарии использования [3]:

1. Администратор заполняет список источников и тегов
2. Система агрегирует статьи из добавленных источников
3. Пользователи просматривают ленту новостей с возможностью фильтрации по тегам и источникам
4. Пользователи добавляют интересные статьи в избранное
5. При обнаружении недостоверной информации пользователь подаёт жалобу
6. Модератор рассматривает жалобу и принимает решение об удалении статьи или отклонении жалобы

## **1.2 Функциональные требования**

Функциональные требования к системе определяются вариантом задания и включают обязательные требования MVP и опциональные расширения [3].

**Требования MVP (обязательные):**

**FR1. Управление пользователями:**
- FR1.1: Регистрация новых пользователей с указанием username и password
- FR1.2: Аутентификация пользователей (вход в систему)
- FR1.3: Назначение ролей пользователям: admin, moderator, user
- FR1.4: Администратор может просматривать список пользователей
- FR1.5: Администратор может создавать, редактировать и удалять пользователей

**FR2. Управление источниками новостей:**
- FR2.1: Администратор может создавать источники с указанием названия, URL и описания
- FR2.2: Администратор может редактировать информацию об источниках
- FR2.3: Администратор может удалять источники
- FR2.4: Все пользователи могут просматривать список источников

**FR3. Работа с лентой новостей:**
- FR3.1: Отображение списка статей в ленте новостей
- FR3.2: Просмотр детальной информации о статье (заголовок, содержание, источник, дата публикации)
- FR3.3: Фильтрация статей по тегам
- FR3.4: Фильтрация статей по источникам
- FR3.5: Пагинация списка статей

**FR4. Управление тегами:**
- FR4.1: Администратор может создавать новые теги
- FR4.2: Администратор может редактировать названия тегов
- FR4.3: Администратор может удалять теги
- FR4.4: Все пользователи могут просматривать список доступных тегов

**FR5. Работа с избранным:**
- FR5.1: Пользователь может добавлять статьи в избранное
- FR5.2: Пользователь может просматривать список своих избранных статей
- FR5.3: Пользователь может удалять статьи из избранного
- FR5.4: Каждый пользователь видит только свои избранные статьи

**FR6. Система жалоб и модерация (критерий приёмки MVP):**
- FR6.1: Пользователь может подать жалобу на статью с указанием причины
- FR6.2: При создании жалоба получает статус "new"
- FR6.3: Модератор и администратор могут просматривать список всех жалоб
- FR6.4: Модератор и администратор могут просматривать детальную информацию о жалобе
- FR6.5: Модератор и администратор могут изменять статус жалобы (reviewed, closed)
- FR6.6: Модератор и администратор могут удалять статьи по результатам рассмотрения жалоб

**Опциональные требования (расширения):**
- Полнотекстовый поиск по статьям
- Экспорт избранных статей
- Уведомления о новых статьях по выбранным тегам
- Статистика активности пользователей

## **1.3 Нефункциональные требования**

**NFR1. Производительность:**
- NFR1.1: Время отклика API на запрос списка статей не должно превышать 500 мс при объёме до 10000 записей
- NFR1.2: Система должна поддерживать одновременную работу до 100 пользователей
- NFR1.3: Загрузка страницы ленты новостей не должна превышать 2 секунд [5]

**NFR2. Безопасность:**
- NFR2.1: Пароли пользователей должны храниться в виде хеша с использованием алгоритма bcrypt [6]
- NFR2.2: Аутентификация должна выполняться с использованием JWT-токенов с ограниченным временем жизни
- NFR2.3: Все API endpoints должны быть защищены механизмом авторизации на основе ролей (RBAC)
- NFR2.4: Валидация всех входных данных для предотвращения SQL-инъекций и XSS-атак [7]
- NFR2.5: Использование HTTPS для защиты данных при передаче
- NFR2.6: Настройка CORS для ограничения доступа к API

**NFR3. Масштабируемость:**
- NFR3.1: Архитектура должна поддерживать горизонтальное масштабирование серверной части
- NFR3.2: База данных должна поддерживать индексирование для оптимизации запросов

**NFR4. Надёжность:**
- NFR4.1: Система должна обеспечивать целостность данных при concurrent операциях
- NFR4.2: Обработка ошибок с возвратом информативных сообщений пользователю
- NFR4.3: Логирование критических операций и ошибок

**NFR5. Удобство использования:**
- NFR5.1: Интерфейс должен быть интуитивно понятным
- NFR5.2: Адаптивный дизайн для различных размеров экранов
- NFR5.3: Время обучения работе с системой для нового пользователя не должно превышать 10 минут

**NFR6. Сопровождаемость:**
- NFR6.1: Код должен соответствовать принципам clean code
- NFR6.2: Использование TypeScript для статической типизации
- NFR6.3: Документирование API endpoints
- NFR6.4: Наличие инструкций по развёртыванию системы

## **1.4 Ограничения и допущения**

**Ограничения проекта:**

1. **Технологические ограничения:**
   - Использование PostgreSQL версии 15 или выше в качестве СУБД
   - Использование Node.js версии 18 или выше
   - Использование React 18 для фронтенда
   - Монорепозиторий с использованием pnpm в качестве пакетного менеджера

2. **Функциональные ограничения:**
   - В MVP не реализован автоматический парсинг новостей из источников (статьи добавляются вручную администратором)
   - Отсутствует функционал комментариев к статьям
   - Не реализована система уведомлений в реальном времени
   - Отсутствует функционал восстановления пароля

3. **Временные ограничения:**
   - Срок разработки проекта ограничен одним семестром
   - Реализуется только функциональность MVP согласно варианту задания

**Допущения:**

1. Администратор системы является доверенным лицом и имеет неограниченный доступ ко всем функциям
2. Источники новостей являются статическими (не требуется автоматическое обнаружение новых источников)
3. Все пользователи имеют базовые навыки работы с веб-приложениями
4. Система развёртывается в локальной сети или на выделенном сервере с настроенной инфраструктурой
5. Объём новостных данных не превышает 100000 статей (для оценки производительности)

## **1.5 Критерии приёмки MVP**

Критерии приёмки определяют минимальный набор функциональности, который должен быть реализован и протестирован [3].

**AC1. Аутентификация и авторизация:**
- AC1.1: Пользователь может зарегистрироваться в системе с валидными данными
- AC1.2: Пользователь может войти в систему с корректными учётными данными
- AC1.3: При неверных учётных данных отображается сообщение об ошибке
- AC1.4: После входа пользователь получает JWT-токен для доступа к защищённым ресурсам
- AC1.5: Доступ к функциям системы ограничен в соответствии с ролью пользователя

**AC2. Управление источниками и тегами:**
- AC2.1: Администратор может создать источник с валидными данными (name, url)
- AC2.2: Администратор может редактировать информацию об источнике
- AC2.3: Администратор может удалить источник
- AC2.4: Администратор может создать тег с уникальным названием
- AC2.5: При попытке создания тега с существующим названием отображается ошибка

**AC3. Работа с лентой новостей:**
- AC3.1: Пользователь видит список статей на главной странице
- AC3.2: Пользователь может открыть детальную страницу статьи
- AC3.3: Пользователь может отфильтровать статьи по тегу
- AC3.4: Пользователь может отфильтровать статьи по источнику
- AC3.5: При фильтрации отображаются только статьи, соответствующие критериям

**AC4. Работа с избранным:**
- AC4.1: Пользователь может добавить статью в избранное
- AC4.2: Пользователь может просмотреть список своих избранных статей
- AC4.3: Пользователь может удалить статью из избранного
- AC4.4: Пользователь видит только свои избранные статьи (не других пользователей)
- AC4.5: При повторном добавлении статьи в избранное система предотвращает дублирование

**AC5. Модерация жалоб (критерий приёмки MVP):**
- AC5.1: Пользователь может подать жалобу на статью с указанием причины
- AC5.2: При создании жалобы ей присваивается статус "new"
- AC5.3: Модератор может просмотреть список всех жалоб
- AC5.4: Модератор может открыть детальную информацию о жалобе
- AC5.5: Модератор может изменить статус жалобы на "reviewed" или "closed"
- AC5.6: Модератор может удалить статью по результатам рассмотрения жалобы
- AC5.7: После удаления статьи она исчезает из ленты новостей всех пользователей
- AC5.8: Обычный пользователь не может просматривать список жалоб

**AC6. Валидация данных:**
- AC6.1: При попытке создания сущности с пустыми обязательными полями отображается сообщение об ошибке
- AC6.2: При вводе некорректного URL источника отображается сообщение об ошибке
- AC6.3: При попытке создания пользователя с существующим username отображается сообщение об ошибке

**AC7. Обработка ошибок:**
- AC7.1: При ошибке на сервере клиент получает информативное сообщение об ошибке
- AC7.2: При попытке доступа к несуществующему ресурсу отображается ошибка 404
- AC7.3: При попытке выполнения операции без необходимых прав доступа отображается ошибка 403
