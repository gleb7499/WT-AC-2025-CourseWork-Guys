# **2 Разработка алгоритмов**

## **2.1 Описание сущностей и связей модели данных**

Модель данных системы агрегации новостей включает семь основных сущностей, связанных между собой отношениями [8]. Диаграмма сущностей представлена на рисунке 2.1.

![](../photos/2_1_photo.txt)
Рисунок 2.1 – Диаграмма сущностей (ERD)

Как видно из рисунка 2.1, модель данных построена на основе следующих сущностей.

**Таблица 2.1 – Сущность User (Пользователь)**

| Поле | Тип | Описание | Ограничения |
|------|-----|----------|-------------|
| id | UUID | Уникальный идентификатор | PRIMARY KEY |
| username | string | Имя пользователя | UNIQUE, NOT NULL |
| password_hash | string | Хеш пароля | NOT NULL |
| role | enum | Роль пользователя | NOT NULL, CHECK (admin, moderator, user) |

**Таблица 2.2 – Сущность Source (Источник новостей)**

| Поле | Тип | Описание | Ограничения |
|------|-----|----------|-------------|
| id | UUID | Уникальный идентификатор | PRIMARY KEY |
| name | string | Название источника | NOT NULL |
| url | string | URL источника | NOT NULL |
| description | text | Описание источника | NULLABLE |

**Таблица 2.3 – Сущность Article (Статья)**

| Поле | Тип | Описание | Ограничения |
|------|-----|----------|-------------|
| id | UUID | Уникальный идентификатор | PRIMARY KEY |
| source_id | UUID | Ссылка на источник | FOREIGN KEY (Source.id), NOT NULL |
| title | string | Заголовок статьи | NOT NULL |
| content | text | Содержание статьи | NULLABLE |
| url | string | URL статьи | NULLABLE |
| published_at | timestamp | Дата публикации | NULLABLE |

**Таблица 2.4 – Сущность Tag (Тег)**

| Поле | Тип | Описание | Ограничения |
|------|-----|----------|-------------|
| id | UUID | Уникальный идентификатор | PRIMARY KEY |
| name | string | Название тега | UNIQUE, NOT NULL |

**Таблица 2.5 – Сущность ArticleTag (Связь статьи и тега)**

| Поле | Тип | Описание | Ограничения |
|------|-----|----------|-------------|
| article_id | UUID | Ссылка на статью | FOREIGN KEY (Article.id), NOT NULL |
| tag_id | UUID | Ссылка на тег | FOREIGN KEY (Tag.id), NOT NULL |

Составной первичный ключ: (article_id, tag_id)

**Таблица 2.6 – Сущность Favorite (Избранное)**

| Поле | Тип | Описание | Ограничения |
|------|-----|----------|-------------|
| id | UUID | Уникальный идентификатор | PRIMARY KEY |
| user_id | UUID | Ссылка на пользователя | FOREIGN KEY (User.id), NOT NULL |
| article_id | UUID | Ссылка на статью | FOREIGN KEY (Article.id), NOT NULL |
| created_at | timestamp | Дата добавления | DEFAULT NOW() |

Уникальное ограничение: UNIQUE (user_id, article_id)

**Таблица 2.7 – Сущность Report (Жалоба)**

| Поле | Тип | Описание | Ограничения |
|------|-----|----------|-------------|
| id | UUID | Уникальный идентификатор | PRIMARY KEY |
| user_id | UUID | Ссылка на пользователя | FOREIGN KEY (User.id), NOT NULL |
| article_id | UUID | Ссылка на статью | FOREIGN KEY (Article.id), NOT NULL |
| reason | text | Причина жалобы | NOT NULL |
| status | enum | Статус жалобы | NOT NULL, CHECK (new, reviewed, closed) |
| created_at | timestamp | Дата создания | DEFAULT NOW() |

**Связи между сущностями:**

1. **Source → Article (1:N):** один источник может содержать множество статей, каждая статья принадлежит ровно одному источнику
2. **Article ↔ Tag (N:M):** статья может иметь множество тегов, тег может быть присвоен множеству статей (связь реализуется через промежуточную таблицу ArticleTag)
3. **User → Favorite (1:N):** один пользователь может иметь множество избранных статей
4. **Article → Favorite (1:N):** одна статья может быть добавлена в избранное множеством пользователей
5. **User → Report (1:N):** один пользователь может создать множество жалоб
6. **Article → Report (1:N):** на одну статью может быть подано множество жалоб

Для обеспечения производительности в модели данных используются следующие индексы:
- Индекс на поле username в таблице User для быстрого поиска при аутентификации
- Индекс на поле name в таблице Tag для оптимизации фильтрации
- Составные индексы на внешние ключи в таблицах ArticleTag, Favorite, Report
- Индекс на поле status в таблице Report для фильтрации жалоб по статусу

## **2.2 Алгоритм формирования ленты новостей**

Алгоритм формирования ленты новостей обеспечивает извлечение статей из базы данных с учётом фильтров и пагинации [9].

**Входные параметры:**
- tagId (опционально) — идентификатор тега для фильтрации
- sourceId (опционально) — идентификатор источника для фильтрации
- limit — максимальное количество записей в ответе (по умолчанию 50)
- offset — смещение для пагинации (по умолчанию 0)

**Выходные данные:**
- Список статей с полной информацией (заголовок, содержание, источник, теги, дата публикации)
- Общее количество статей, соответствующих фильтрам

**Алгоритм:**

```
1. Начало
2. Инициализировать базовый запрос: SELECT * FROM articles
3. Если указан параметр sourceId:
   3.1. Добавить условие: WHERE source_id = sourceId
4. Если указан параметр tagId:
   4.1. Выполнить JOIN с таблицей article_tags
   4.2. Добавить условие: WHERE tag_id = tagId
5. Выполнить JOIN с таблицей sources для получения информации об источнике
6. Выполнить LEFT JOIN с таблицей article_tags и tags для получения всех тегов статьи
7. Добавить сортировку: ORDER BY published_at DESC
8. Применить пагинацию: LIMIT limit OFFSET offset
9. Выполнить запрос к базе данных
10. Для каждой статьи в результате:
    10.1. Сформировать объект статьи с полями: id, title, content, url, published_at
    10.2. Добавить информацию об источнике: source { id, name, url }
    10.3. Добавить массив тегов: tags []
11. Подсчитать общее количество статей, соответствующих фильтрам
12. Вернуть результат: { data: articles[], total: count }
13. Конец
```

Согласно алгоритму, система выполняет оптимизированный запрос к базе данных с использованием индексов на внешних ключах, что обеспечивает быструю выборку данных [10].

## **2.3 Алгоритм обработки жалоб и модерации**

Система модерации жалоб включает два основных алгоритма: создание жалобы пользователем и обработка жалобы модератором.

**Алгоритм создания жалобы:**

**Входные данные:**
- userId — идентификатор пользователя
- articleId — идентификатор статьи
- reason — причина жалобы

**Выходные данные:**
- Созданная жалоба с идентификатором и статусом "new"

**Алгоритм:**

```
1. Начало
2. Проверить аутентификацию пользователя
3. Проверить наличие роли user, moderator или admin
4. Валидировать входные данные:
   4.1. Проверить, что articleId существует в базе данных
   4.2. Проверить, что reason не пустое
5. Если валидация не пройдена:
   5.1. Вернуть ошибку 400 с описанием проблемы
   5.2. Завершить
6. Создать запись в таблице reports:
   6.1. id = generateUUID()
   6.2. user_id = userId
   6.3. article_id = articleId
   6.4. reason = reason
   6.5. status = "new"
   6.6. created_at = NOW()
7. Сохранить запись в базе данных
8. Записать событие в журнал: "Report created: report_id by user_id"
9. Вернуть созданную жалобу со статусом 201
10. Конец
```

**Алгоритм обработки жалобы модератором:**

**Входные данные:**
- reportId — идентификатор жалобы
- newStatus — новый статус ("reviewed" или "closed")
- userId — идентификатор модератора
- deleteArticle (опционально) — флаг удаления статьи

**Выходные данные:**
- Обновлённая жалоба с новым статусом

**Алгоритм:**

```
1. Начало
2. Проверить аутентификацию пользователя
3. Проверить наличие роли moderator или admin
4. Если роль не соответствует:
   4.1. Вернуть ошибку 403 "Access denied"
   4.2. Завершить
5. Получить жалобу по reportId из базы данных
6. Если жалоба не найдена:
   6.1. Вернуть ошибку 404 "Report not found"
   6.2. Завершить
7. Валидировать новый статус:
   7.1. Проверить, что newStatus входит в список ["reviewed", "closed"]
8. Если валидация не пройдена:
   8.1. Вернуть ошибку 400 "Invalid status"
   8.2. Завершить
9. Если установлен флаг deleteArticle:
   9.1. Начать транзакцию
   9.2. Удалить статью из таблицы articles по article_id
   9.3. Удалить связанные записи из article_tags
   9.4. Удалить связанные записи из favorites
   9.5. Обновить все жалобы на эту статью, установив status = "closed"
   9.6. Зафиксировать транзакцию
   9.7. Записать в журнал: "Article deleted: article_id by moderator user_id"
10. Иначе:
    10.1. Обновить статус жалобы в базе данных: status = newStatus
11. Записать в журнал: "Report updated: report_id status = newStatus by user_id"
12. Вернуть обновлённую жалобу
13. Конец
```

Согласно алгоритму, при удалении статьи используется транзакция для обеспечения целостности данных [11]. Все связанные записи удаляются каскадно, что предотвращает появление «висячих» ссылок в базе данных.

## **2.4 Алгоритм управления избранным**

Алгоритм управления избранным обеспечивает добавление и удаление статей из персональной коллекции пользователя.

**Алгоритм добавления статьи в избранное:**

**Входные данные:**
- userId — идентификатор пользователя
- articleId — идентификатор статьи

**Выходные данные:**
- Созданная запись в избранном

**Алгоритм:**

```
1. Начало
2. Проверить аутентификацию пользователя
3. Валидировать входные данные:
   3.1. Проверить существование статьи с articleId
4. Если статья не существует:
   4.1. Вернуть ошибку 404 "Article not found"
   4.2. Завершить
5. Проверить наличие записи в таблице favorites с парой (user_id, article_id)
6. Если запись уже существует:
   6.1. Вернуть ошибку 409 "Article already in favorites"
   6.2. Завершить
7. Создать новую запись в таблице favorites:
   7.1. id = generateUUID()
   7.2. user_id = userId
   7.3. article_id = articleId
   7.4. created_at = NOW()
8. Сохранить запись в базе данных
9. Вернуть созданную запись со статусом 201
10. Конец
```

**Алгоритм удаления статьи из избранного:**

**Входные данные:**
- favoriteId — идентификатор записи в избранном
- userId — идентификатор пользователя

**Выходные данные:**
- Статус успешного удаления

**Алгоритм:**

```
1. Начало
2. Проверить аутентификацию пользователя
3. Получить запись из таблицы favorites по favoriteId
4. Если запись не найдена:
   4.1. Вернуть ошибку 404 "Favorite not found"
   4.2. Завершить
5. Проверить, что запись принадлежит текущему пользователю:
   5.1. Если favorite.user_id != userId:
       5.1.1. Вернуть ошибку 403 "Access denied"
       5.1.2. Завершить
6. Удалить запись из таблицы favorites
7. Вернуть статус 204 "No Content"
8. Конец
```

Алгоритмы управления избранным обеспечивают изоляцию данных пользователей: каждый пользователь может управлять только своими избранными статьями [12].

## **2.5 Схема аутентификации и авторизации**

Система использует токен-базированную аутентификацию на основе JWT (JSON Web Tokens) [13]. Схема аутентификации показана на рисунке 2.2.

![](../photos/2_2_photo.txt)
Рисунок 2.2 – Схема аутентификации с использованием JWT

Согласно рисунку 2.2, процесс аутентификации включает следующие этапы.

**Алгоритм регистрации:**

```
1. Начало
2. Получить данные регистрации: username, password
3. Валидировать входные данные:
   3.1. Проверить формат username (только буквы и цифры)
   3.2. Проверить длину password (минимум 6 символов)
4. Проверить уникальность username в базе данных
5. Если username уже существует:
   5.1. Вернуть ошибку 409 "Username already exists"
   5.2. Завершить
6. Сгенерировать хеш пароля: password_hash = bcrypt.hash(password, saltRounds=10)
7. Создать новую запись в таблице users:
   7.1. id = generateUUID()
   7.2. username = username
   7.3. password_hash = password_hash
   7.4. role = "user" (по умолчанию)
8. Сохранить пользователя в базе данных
9. Вернуть информацию о созданном пользователе (без пароля) со статусом 201
10. Конец
```

**Алгоритм входа в систему:**

```
1. Начало
2. Получить данные входа: username, password
3. Найти пользователя в базе данных по username
4. Если пользователь не найден:
   4.1. Вернуть ошибку 401 "Invalid credentials"
   4.2. Завершить
5. Проверить пароль: isValid = bcrypt.compare(password, user.password_hash)
6. Если пароль неверен:
   6.1. Вернуть ошибку 401 "Invalid credentials"
   6.2. Завершить
7. Сгенерировать access token:
   7.1. payload = { userId: user.id, role: user.role }
   7.2. accessToken = jwt.sign(payload, ACCESS_SECRET, { expiresIn: "15m" })
8. Сгенерировать refresh token:
   8.1. refreshToken = jwt.sign({ userId: user.id }, REFRESH_SECRET, { expiresIn: "7d" })
9. Установить refresh token в HttpOnly cookie
10. Вернуть ответ: { accessToken, user: { id, username, role } }
11. Конец
```

**Алгоритм обновления токена:**

```
1. Начало
2. Извлечь refresh token из HttpOnly cookie
3. Если cookie отсутствует:
   3.1. Вернуть ошибку 401 "Refresh token required"
   3.2. Завершить
4. Попытаться верифицировать refresh token:
   4.1. payload = jwt.verify(refreshToken, REFRESH_SECRET)
5. Если токен недействителен или истёк:
   5.1. Вернуть ошибку 401 "Invalid refresh token"
   5.2. Завершить
6. Получить пользователя из базы данных по payload.userId
7. Если пользователь не найден:
   7.1. Вернуть ошибку 401 "User not found"
   7.2. Завершить
8. Сгенерировать новый access token (см. шаг 7 алгоритма входа)
9. Сгенерировать новый refresh token
10. Установить новый refresh token в HttpOnly cookie
11. Вернуть новый access token
12. Конец
```

**Алгоритм авторизации (middleware):**

```
1. Начало
2. Извлечь токен из заголовка Authorization: "Bearer <token>"
3. Если заголовок отсутствует или формат неверен:
   3.1. Вернуть ошибку 401 "Authorization token required"
   3.2. Завершить
4. Попытаться верифицировать access token:
   4.1. payload = jwt.verify(token, ACCESS_SECRET)
5. Если токен недействителен или истёк:
   5.1. Вернуть ошибку 401 "Invalid or expired token"
   5.2. Завершить
6. Получить пользователя из базы данных по payload.userId
7. Если пользователь не найден:
   7.1. Вернуть ошибку 401 "User not found"
   7.2. Завершить
8. Проверить соответствие роли требованиям маршрута
9. Если роль не соответствует:
   9.1. Вернуть ошибку 403 "Insufficient permissions"
   9.2. Завершить
10. Добавить информацию о пользователе в объект запроса: req.user = user
11. Передать управление следующему обработчику
12. Конец
```

Использование двух токенов (access и refresh) обеспечивает баланс между безопасностью и удобством использования [14]. Access token имеет короткое время жизни (15 минут), что снижает риски при компрометации. Refresh token хранится в HttpOnly cookie, что защищает его от XSS-атак [15].
