## 2. Разработка алгоритмов

### 2.1 Описание сущностей и связей

Информационная модель системы построена на семи основных сущностях с чётко определёнными связями и ограничениями целостности.

Сущность User представляет пользователя системы и содержит идентификатор типа UUID, уникальное имя пользователя, хеш пароля, роль из перечисления admin, moderator или user, версию токена для инвалидации сессий, метки времени создания и последнего обновления записи. Пользователь выступает владельцем коллекций избранных статей и автором жалоб, связи реализованы как один-ко-многим.

Сущность Source описывает источник новостей через идентификатор, наименование, веб-адрес, опциональное описание и временные метки. Один источник может быть издателем множества статей, при удалении источника связанные статьи удаляются каскадно для поддержания целостности данных.

Сущность Article представляет новостную статью с атрибутами: идентификатор, внешний ключ на источник, заголовок, текстовое содержимое, ссылка на оригинал, время публикации, метки создания и обновления. Статья обязательно связана с одним источником через поле sourceId. Множественные связи существуют с тегами через промежуточную таблицу, с избранным пользователей и жалобами.

Сущность Tag определяет тематическую метку через идентификатор, уникальное наименование и временные метки. Теги связаны со статьями отношением многие-ко-многим, реализованным через связующую таблицу ArticleTag.

Промежуточная сущность ArticleTag обеспечивает связь статей и тегов через пару внешних ключей articleId и tagId, образующих составной первичный ключ. Удаление статьи или тега приводит к каскадному удалению соответствующих записей связи.

Сущность Favorite фиксирует факт добавления статьи в избранное конкретным пользователем. Уникальность комбинации userId и articleId предотвращает дублирование избранного одной статьи пользователем. Каскадное удаление настроено для обоих внешних ключей.

Сущность Report представляет жалобу пользователя на статью и включает идентификатор, ссылки на пользователя и статью, текстовую причину, статус из перечисления new, reviewed, closed, временные метки создания и обновления. При удалении пользователя связанные жалобы не удаляются для сохранения истории модерации.

### 2.2 Алгоритм формирования ленты новостей

Формирование ленты статей реализуется через запрос к базе данных с применением фильтрации, упорядочивания и пагинации. Входными параметрами выступают опциональные идентификаторы тега и источника, ограничение количества записей и смещение для реализации постраничного вывода.

Алгоритм включает следующие шаги. На первом этапе формируется базовое условие выборки всех статей из таблицы articles. Если предоставлен параметр sourceId, к условию добавляется фильтр source_id = sourceId для отбора статей только указанного источника.

При наличии параметра tagId применяется соединение с таблицей article_tags и добавляется условие tag_id = tagId. Данный подход обеспечивает выборку только тех статей, которым присвоен указанный тег.

Результирующий набор упорядочивается по полю published_at в порядке убывания, что обеспечивает отображение наиболее свежих публикаций в начале ленты. Применяется ограничение LIMIT для задания максимального количества возвращаемых записей и смещение OFFSET для пропуска предыдущих страниц [5].

Для каждой статьи в результате дополнительно загружаются связанные данные источника через JOIN с таблицей sources и коллекция тегов через соединение с article_tags и tags. Данный подход минимизирует количество запросов к базе данных, реализуя паттерн eager loading.

Псевдокод алгоритма:

```
функция getArticlesFeed(filters):
  query = SELECT articles.* FROM articles
  
  если filters.sourceId существует:
    query += WHERE articles.source_id = filters.sourceId
  
  если filters.tagId существует:
    query += JOIN article_tags ON articles.id = article_tags.article_id
    query += WHERE article_tags.tag_id = filters.tagId
  
  query += ORDER BY articles.published_at DESC
  query += LIMIT filters.limit OFFSET filters.offset
  
  для каждой статьи в результате:
    загрузить связанный source
    загрузить связанные tags через article_tags
  
  вернуть коллекцию статей с вложенными данными
```

Сложность алгоритма составляет O(n), где n — количество статей, удовлетворяющих условиям фильтрации в пределах одной страницы. Использование индексов на полях source_id, published_at и внешних ключах таблицы article_tags обеспечивает эффективное выполнение запроса даже при больших объёмах данных.

### 2.3 Алгоритм управления избранным

Операция добавления статьи в избранное выполняется с проверкой уникальности записи для предотвращения дублирования. Входными параметрами являются идентификатор пользователя, полученный из контекста аутентификации, и идентификатор статьи из тела запроса.

Алгоритм начинается с проверки существования статьи с указанным идентификатором через запрос к таблице articles. В случае отсутствия статьи возвращается ошибка с кодом 404 и сообщением о ненайденном ресурсе.

Далее выполняется проверка наличия записи в таблице favorites с комбинацией user_id = userId и article_id = articleId. Если запись обнаружена, возвращается ошибка с кодом 409 указывающим на конфликт дублирования избранного.

При отсутствии конфликтов создаётся новая запись в таблице favorites с автоматической генерацией идентификатора и установкой текущего времени в поле created_at. Операция выполняется в транзакции для обеспечения атомарности [9].

Псевдокод добавления в избранное:

```
функция addToFavorites(userId, articleId):
  article = найти статью по articleId
  если article не существует:
    вернуть ошибку 404 "Статья не найдена"
  
  existing = найти запись favorites WHERE user_id = userId И article_id = articleId
  если existing существует:
    вернуть ошибку 409 "Статья уже в избранном"
  
  favorite = создать запись favorites с полями:
    id = сгенерировать UUID
    user_id = userId
    article_id = articleId
    created_at = текущее время
  
  вернуть созданный favorite со статусом 201
```

Удаление из избранного реализуется через идентификатор записи favorite с дополнительной проверкой принадлежности пользователю. Алгоритм извлекает запись по идентификатору, верифицирует совпадение user_id с идентификатором текущего пользователя для предотвращения несанкционированного удаления чужого избранного, выполняет операцию DELETE и возвращает статус 204 при успешном завершении.

### 2.4 Алгоритм модерации жалоб

Процесс модерации жалоб включает создание, просмотр и изменение статуса обращений пользователей.

Создание жалобы инициируется пользователем через API endpoint с передачей идентификатора статьи и текстовой причины обращения. Алгоритм валидирует наличие обязательных полей через схему Zod, проверяет существование статьи в базе данных, создаёт запись в таблице reports со статусом new и текущим временем создания, возвращает созданную жалобу с кодом 201.

Просмотр списка жалоб доступен пользователям с ролями moderator и admin. Алгоритм принимает опциональный параметр фильтрации по статусу, формирует запрос с соответствующим условием WHERE status = requestedStatus, применяет сортировку по времени создания в порядке возрастания для приоритета более старых жалоб, загружает связанные данные пользователя и статьи для полноты информации.

Изменение статуса жалобы выполняется модератором или администратором через операцию обновления. Входными параметрами являются идентификатор жалобы и новый статус из допустимых значений reviewed или closed.

Псевдокод обработки жалобы:

```
функция updateReportStatus(reportId, newStatus, moderatorRole):
  если moderatorRole не в [moderator, admin]:
    вернуть ошибку 403 "Недостаточно прав"
  
  report = найти жалобу по reportId
  если report не существует:
    вернуть ошибку 404 "Жалоба не найдена"
  
  если newStatus не в [reviewed, closed]:
    вернуть ошибку 400 "Недопустимый статус"
  
  обновить report.status = newStatus
  обновить report.updated_at = текущее время
  
  вернуть обновлённую жалобу
```

Удаление статьи по жалобе реализуется как отдельная операция с дополнительной проверкой прав доступа. Модератор или администратор инициирует удаление через соответствующий endpoint статьи, система выполняет каскадное удаление всех зависимых записей включая связи с тегами, избранное пользователей и жалобы на данную статью.

### 2.5 Схема аутентификации

Аутентификация реализована на основе JWT-токенов с механизмом обновления через refresh-токены. Процесс включает несколько этапов взаимодействия клиента и сервера [1].

При регистрации пользователь отправляет имя пользователя и пароль на endpoint регистрации. Сервер валидирует уникальность имени, хеширует пароль с использованием bcrypt с коэффициентом сложности 10, создаёт запись пользователя с ролью user по умолчанию, генерирует пару токенов и возвращает access-токен в теле ответа, refresh-токен устанавливается в HttpOnly cookie для защиты от XSS-атак [4].

Процесс входа аналогичен с той разницей, что вместо создания новой записи выполняется поиск существующего пользователя и проверка пароля через bcrypt.compare. При успешной верификации генерируется новая пара токенов с обновлением версии токена в записи пользователя.

Access-токен содержит идентификатор пользователя, имя пользователя, роль и версию токена в payload, подписывается секретным ключом JWT_ACCESS_SECRET, имеет время жизни 15 минут. Клиент включает access-токен в заголовок Authorization всех защищённых запросов в формате Bearer token.

Refresh-токен содержит только идентификатор пользователя и версию токена, подписывается отдельным секретом JWT_REFRESH_SECRET, имеет время жизни 7 дней, передаётся и хранится исключительно в HttpOnly cookie.

При истечении access-токена клиент отправляет запрос на endpoint обновления с включением refresh-токена в cookie. Сервер верифицирует refresh-токен, проверяет актуальность версии токена в базе данных для возможности принудительной инвалидации сессий, генерирует новый access-токен с актуальными данными пользователя, ротирует refresh-токен для повышения безопасности.

Псевдокод middleware аутентификации:

```
функция authMiddleware(request):
  token = извлечь из заголовка Authorization
  если token отсутствует:
    вернуть ошибку 401 "Требуется аутентификация"
  
  попытка:
    payload = верифицировать token с секретом JWT_ACCESS_SECRET
    user = найти пользователя по payload.userId
    
    если user не существует ИЛИ user.tokenVersion != payload.tokenVersion:
      вернуть ошибку 401 "Токен недействителен"
    
    добавить user в контекст запроса
    продолжить обработку запроса
  
  при ошибке верификации:
    вернуть ошибку 401 "Токен недействителен или истёк"
```

Для защиты операций в зависимости от роли применяется дополнительный middleware авторизации, проверяющий наличие требуемой роли у аутентифицированного пользователя. Неавторизованные попытки доступа возвращают статус 403 с сообщением о недостаточных правах.
