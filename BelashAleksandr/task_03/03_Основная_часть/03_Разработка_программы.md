## 3. Разработка программы

### 3.1 Архитектура системы

Приложение реализовано по клиент-серверной архитектуре с чётким разделением ответственности между компонентами. Взаимодействие осуществляется через HTTP-протокол с использованием REST API принципов [2].

Серверная часть функционирует как независимое приложение на платформе Node.js, обрабатывает входящие HTTP-запросы, выполняет бизнес-логику, взаимодействует с базой данных PostgreSQL через ORM Prisma, обеспечивает аутентификацию и авторизацию, валидирует данные и формирует структурированные ответы в формате JSON.

Клиентская часть представляет собой одностраничное приложение на React, отображает пользовательский интерфейс в браузере, управляет состоянием приложения через Zustand, отправляет HTTP-запросы к серверному API через Axios, обрабатывает маршрутизацию на стороне клиента посредством React Router, обеспечивает интерактивность и валидацию форм.

База данных PostgreSQL хранит персистентные данные всех сущностей системы, обеспечивает целостность через ограничения и внешние ключи, поддерживает транзакции для атомарных операций, предоставляет механизмы индексации для оптимизации запросов.

### 3.2 Выбор технологического стека

Выбор технологий обоснован требованиями к производительности, безопасности и удобству разработки.

Серверная платформа Node.js выбрана благодаря высокой производительности для операций ввода-вывода, единому языку программирования JavaScript с клиентской частью, обширной экосистеме пакетов npm, встроенной асинхронности для обработки множественных запросов [3].

Фреймворк Express предоставляет минималистичную и гибкую основу для построения веб-приложений, поддержку middleware для модульной обработки запросов, удобную маршрутизацию HTTP-запросов, широкое сообщество и документацию.

TypeScript применяется для статической типизации кода, что снижает количество ошибок времени выполнения, улучшает поддержку IDE с автодополнением и рефакторингом, обеспечивает самодокументируемость кода через типы и интерфейсы [3].

Prisma ORM выбран как современное решение для работы с базами данных, обеспечивающее типобезопасные запросы с автогенерацией TypeScript типов, декларативное описание схемы данных, удобные инструменты миграций, защиту от SQL-инъекций на уровне ORM [5].

PostgreSQL представляет собой надёжную реляционную СУБД с поддержкой сложных запросов и транзакций, механизмов обеспечения целостности данных, высокой производительности и масштабируемости, расширенных типов данных включая UUID и JSON.

Библиотека Zod применяется для валидации входных данных с декларативным описанием схем валидации, автоматической генерацией TypeScript типов из схем, информативными сообщениями об ошибках валидации.

Клиентская библиотека React выбрана как популярное решение для построения интерактивных интерфейсов с компонентным подходом к разработке UI, виртуальным DOM для эффективного обновления, обширной экосистемой библиотек и инструментов [3].

Библиотека Zustand для управления состоянием обеспечивает простой API без избыточного boilerplate, хорошую производительность, лёгкость тестирования компонентов.

Инструмент сборки Vite предоставляет мгновенный запуск dev-сервера с hot module replacement, быструю сборку production через Rollup, встроенную поддержку TypeScript и современных возможностей JavaScript.

### 3.3 Структура серверного приложения

Серверная часть организована по модульному принципу с разделением на функциональные слои.

Точка входа приложения расположена в файле index.ts, который инициализирует соединение с базой данных, запускает HTTP-сервер на сконфигурированном порту, устанавливает обработчики завершения для корректного закрытия соединений.

Модуль app.ts содержит конфигурацию Express-приложения с подключением middleware общего назначения: helmet для установки защитных HTTP-заголовков, cors для настройки политики cross-origin запросов, morgan для логирования HTTP-запросов, express.json для парсинга JSON-тел запросов, cookie-parser для обработки cookies.

Директория routes содержит определения маршрутов, сгруппированных по функциональности: auth.routes.ts для аутентификации и регистрации, users.routes.ts для управления пользователями, sources.routes.ts для источников, feed.routes.ts для ленты статей, tags.routes.ts для тегов, favorites.routes.ts для избранного, reports.routes.ts для жалоб. Каждый роутер применяет соответствующие middleware аутентификации и авторизации к защищённым endpoints.

Директория controllers реализует обработчики запросов с бизнес-логикой: извлечение и валидация параметров запроса, вызов методов работы с данными через Prisma Client, формирование структурированного ответа, обработка исключительных ситуаций с возвратом корректных HTTP-статусов.

Директория middleware содержит функции промежуточной обработки: auth.middleware.ts для верификации JWT-токенов и извлечения данных пользователя, role.middleware.ts для проверки соответствия роли требованиям endpoint, error.middleware.ts для централизованной обработки ошибок.

Директория lib включает вспомогательные модули: jwt.ts для генерации и верификации токенов, password.ts для хеширования и сравнения паролей, logger.ts для структурированного логирования событий через Winston.

Директория types определяет TypeScript интерфейсы и типы для структур данных, параметров запросов, тел ответов, что обеспечивает согласованность типов между модулями.

### 3.6 Модель данных

Схема базы данных реализована через Prisma ORM с описанием в файле schema.prisma. Основные таблицы и их структура представлены ниже.

Таблица users содержит данные пользователей системы с полями: id типа UUID как первичный ключ, username типа текст с ограничением уникальности, password_hash типа текст для хранения хеша пароля, role типа перечисление со значениями admin, moderator, user и значением по умолчанию user, token_version типа целое число со значением по умолчанию 0 для инвалидации сессий, created_at и updated_at типа timestamp для метаинформации.

Таблица sources описывает источники новостей через поля: id типа UUID, name типа текст, url типа текст, description типа текст с возможностью NULL, created_at и updated_at типа timestamp.

Таблица articles хранит статьи со структурой: id типа UUID, source_id типа UUID как внешний ключ на sources с каскадным удалением, title типа текст, content типа текст с возможностью NULL, url типа текст с возможностью NULL, published_at типа timestamp, created_at и updated_at типа timestamp.

Таблица tags определяет метки через поля: id типа UUID, name типа текст с ограничением уникальности, created_at и updated_at типа timestamp.

Связующая таблица article_tags реализует отношение многие-ко-многим между статьями и тегами через поля: article_id и tag_id типа UUID как внешние ключи с каскадным удалением, составной первичный ключ из обоих полей.

Таблица favorites фиксирует избранное пользователей полями: id типа UUID, user_id типа UUID как внешний ключ на users с каскадным удалением, article_id типа UUID как внешний ключ на articles с каскадным удалением, created_at типа timestamp, уникальное ограничение на пару user_id и article_id.

Таблица reports содержит жалобы со структурой: id типа UUID, user_id типа UUID как внешний ключ на users, article_id типа UUID как внешний ключ на articles, reason типа текст, status типа перечисление со значениями new, reviewed, closed и значением по умолчанию new, created_at и updated_at типа timestamp.

Индексация автоматически создаётся ORM для первичных ключей, внешних ключей и полей с ограничением уникальности. Для оптимизации запросов формирования ленты целесообразно создание дополнительного индекса на поле published_at таблицы articles с порядком DESC.

Миграции базы данных управляются через команды Prisma CLI с версионированием изменений схемы, что обеспечивает воспроизводимость структуры данных в различных окружениях [5].

### 3.7 Конфигурация и развёртывание

Настройка приложения осуществляется через переменные окружения с использованием файлов .env для каждого компонента.

Серверная часть требует следующие переменные: DATABASE_URL для строки подключения к PostgreSQL в формате postgresql://user:password@host:port/database, JWT_ACCESS_SECRET для подписи access-токенов, JWT_REFRESH_SECRET для подписи refresh-токенов, PORT для номера порта HTTP-сервера со значением по умолчанию 3000, NODE_ENV для определения окружения с возможными значениями development, production, test, CORS_ORIGIN для списка разрешённых источников CORS-запросов.

Клиентская часть настраивается через переменную VITE_API_BASE_URL для базового адреса серверного API со значением по умолчанию http://localhost:3000.

Процесс локального развёртывания для приёмки включает следующие шаги. Предварительно устанавливается Node.js версии 18 или выше, пакетный менеджер pnpm версии 8 или выше, PostgreSQL версии 15 или выше с созданием базы данных news_aggregator.

Клонируется репозиторий проекта и выполняется переход в директорию проекта. Копируются примеры файлов окружения с заполнением актуальных значений для секретных ключей JWT и параметров подключения к базе данных.

Устанавливаются зависимости всех пакетов монорепозитория командой pnpm install. Генерируется Prisma Client командой pnpm db:generate, применяется схема к базе данных командой pnpm db:push, заполняется база тестовыми данными командой pnpm db:seed.

Запуск приложения в режиме разработки осуществляется командой pnpm dev из корневой директории, что одновременно стартует серверную часть на порту 3000 и клиентскую на порту 5173 с автоматической перезагрузкой при изменении файлов.

Для продуктивного развёртывания выполняется сборка клиента командой pnpm build в директории apps/web, сборка сервера командой pnpm build в директории apps/server, применение миграций в продуктивной базе командой pnpm prisma migrate deploy. Запуск продуктивной версии осуществляется через node dist/index.js для сервера и раздачу статических файлов из директории dist клиента через веб-сервер nginx или альтернативный.

Опциональное развёртывание через Docker Compose предусматривает наличие файла docker-compose.yml с описанием сервисов PostgreSQL, сервера и клиента. Запуск всей инфраструктуры выполняется командой docker-compose up с автоматической сборкой образов, инициализацией базы данных и запуском приложений на определённых портах.

Логирование серверных операций осуществляется через Winston с выводом структурированных логов в консоль в режиме разработки и в файлы в продуктивном режиме. Уровни логирования настраиваются через переменную окружения LOG_LEVEL с возможными значениями error, warn, info, debug.
