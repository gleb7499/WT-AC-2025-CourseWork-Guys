## 1. Постановка задачи

### 1.1 Исходные данные

Разработка системы агрегации новостей основывается на предметной области работы с информационными источниками и публикациями. В качестве исходных данных выступают концептуальные требования к структуре информации, определяющие следующие типы объектов.

Источники новостей представляют собой зарегистрированные в системе информационные ресурсы, характеризующиеся наименованием, веб-адресом и текстовым описанием. Каждый источник выступает издателем множества статей, связь реализуется через внешний ключ на идентификатор источника.

Статьи являются основными информационными единицами системы и содержат заголовок, текстовое содержание, ссылку на оригинальную публикацию и метку времени публикации. Каждая статья обязательно связана с одним источником и может быть ассоциирована с произвольным количеством тегов через связующую таблицу.

Теги представляют собой классификаторы контента с уникальными наименованиями, применяемые для категоризации статей и обеспечения возможности тематической фильтрации. Связь между статьями и тегами реализована как отношение многие-ко-многим [5].

Пользователи системы характеризуются уникальным именем пользователя, хешированным паролем и ролью, определяющей уровень доступа к функциональности. Каждый пользователь может формировать персональную коллекцию избранных статей и подавать жалобы на сомнительный контент.

Избранное представляет собой связь между пользователем и статьёй, фиксирующую намерение пользователя сохранить публикацию для последующего просмотра. Комбинация идентификаторов пользователя и статьи является уникальной для предотвращения дублирования записей.

Жалобы фиксируют обращения пользователей относительно конкретных статей с указанием причины и текущего статуса рассмотрения. Статус жалобы может принимать одно из трёх значений: новая, рассмотренная или закрытая.

Формат хранения данных соответствует реляционной модели с использованием системы управления базами данных PostgreSQL. Все идентификаторы сущностей представлены типом UUID для обеспечения глобальной уникальности [6]. Временные метки фиксируются в формате ISO 8601 с учётом часового пояса.

### 1.2 Функциональные требования

Функциональность системы определяется требованиями MVP с разделением на обязательные компоненты и опциональные расширения. К обязательным требованиям MVP относятся следующие возможности.

Система аутентификации должна обеспечивать регистрацию новых пользователей с валидацией уникальности имени, вход в систему с проверкой учётных данных и выдачу JWT-токенов для последующей авторизации запросов. Токены доступа имеют ограниченный срок действия, механизм обновления реализован через refresh-токены, передаваемые в защищённых HTTP-only cookies [1].

Управление источниками новостей предоставляет администраторам возможности создания новых источников с указанием обязательных атрибутов, просмотра списка всех зарегистрированных источников с поддержкой пагинации, редактирования информации об источниках и удаления источников с каскадным удалением связанных статей.

Работа с тегами включает создание новых тегов с проверкой уникальности наименования, просмотр полного перечня доступных тегов, обновление наименований существующих тегов и удаление тегов с корректной обработкой связей со статьями.

Формирование и отображение ленты новостей реализует получение списка статей с поддержкой фильтрации по идентификатору тега и идентификатору источника, пагинацию результатов с настраиваемыми параметрами ограничения и смещения, просмотр детальной информации о статье включая связанные теги и сведения об источнике. Статьи в ленте упорядочиваются по времени публикации в обратном хронологическом порядке.

Функциональность избранного позволяет аутентифицированным пользователям добавлять статьи в персональную коллекцию, просматривать список собственных избранных материалов и удалять статьи из избранного. Каждый пользователь имеет доступ исключительно к собственному избранному, разграничение реализуется на уровне серверной логики.

Система модерации жалоб обеспечивает пользователям возможность создания жалобы на статью с обязательным указанием причины, модераторам и администраторам — просмотр списка всех жалоб с фильтрацией по статусу рассмотрения, детальный просмотр информации о жалобе включая данные инициатора и статьи, изменение статуса жалобы в процессе рассмотрения. Модераторы и администраторы имеют право удалять статьи, признанные нарушающими правила платформы.

Управление пользователями предоставляет администраторам инструменты для создания учётных записей с назначением роли, просмотра списка всех пользователей системы, обновления информации профиля и удаления учётных записей.

### 1.3 Нефункциональные требования

Система должна обеспечивать надёжную защиту пользовательских данных через хеширование паролей с использованием алгоритма bcrypt с достаточным числом раундов для противодействия атакам методом подбора [7]. Передача конфиденциальной информации должна осуществляться по защищённому протоколу HTTPS в продуктивной среде.

Производительность системы должна обеспечивать формирование ответов на типовые запросы получения списков в пределах одной секунды при объёме базы данных до десяти тысяч статей. Пагинация реализуется для всех операций получения коллекций с разумными ограничениями размера страницы для предотвращения перегрузки канала передачи данных [2].

Масштабируемость архитектуры достигается через разделение клиентской и серверной частей с взаимодействием посредством REST API, что позволяет независимое масштабирование компонентов. База данных проектируется с учётом возможности репликации для распределения нагрузки чтения.

Безопасность приложения обеспечивается комплексом мер: валидация всех входящих данных на серверной стороне с использованием библиотеки Zod, защита от основных веб-уязвимостей через middleware Helmet, настройка политики CORS для ограничения доступа к API только с доверенных доменов, использование параметризованных запросов через ORM для предотвращения SQL-инъекций [8].

Удобство использования интерфейса предполагает интуитивную навигацию с чёткой индикацией текущего раздела, информативные сообщения об ошибках валидации с указанием конкретных полей формы, визуальную обратную связь при выполнении длительных операций.

### 1.4 Ограничения и допущения

Разработка системы осуществляется с учётом следующих ограничений и допущений.

Автоматический сбор статей от внешних источников не входит в рамки MVP. Предполагается ручное добавление статей администраторами или импорт из подготовленных файлов данных через механизм seed-скриптов базы данных.

Полнотекстовый поиск по содержимому статей не реализован в базовой версии. Фильтрация ограничивается выбором по тегам и источникам через параметры запроса API.

Система уведомлений о статусе рассмотрения жалоб не включена в MVP. Пользователи могут отслеживать статус собственных жалоб через соответствующий раздел интерфейса при его наличии или получать информацию через прямое обращение к API.

Локализация интерфейса ограничена русским языком. Поддержка множественных языковых версий не предусмотрена в текущей реализации.

Развёртывание предполагает использование локальной установки PostgreSQL для демонстрации функциональности. Конфигурация для продуктивного окружения с использованием контейнеризации через Docker Compose доступна, но не является обязательной для приёмки MVP.

### 1.5 Критерии приёмки MVP

Приёмка минимально жизнеспособного продукта осуществляется на основании следующих технических критериев.

Критерий А1: Пользователь с ролью user успешно проходит аутентификацию и получает доступ к ленте новостей с возможностью просмотра статей, их детальной информации и связанных тегов.

Критерий А2: Пользователь может применять фильтрацию статей по одному или нескольким тегам, результаты отображают только статьи, помеченные выбранными тегами.

Критерий А3: Пользователь добавляет статью в избранное, впоследствии обнаруживает её в разделе избранного, удаляет из избранного и более не видит в соответствующем списке.

Критерий А4: Пользователь создаёт жалобу на статью с указанием причины, жалоба сохраняется в системе со статусом new и становится доступной для просмотра модераторами.

Критерий А5: Пользователь с ролью moderator или admin просматривает список всех жалоб, открывает детальную информацию о конкретной жалобе и изменяет её статус на reviewed или closed.

Критерий А6: Модератор принимает решение об удалении статьи по жалобе, статья удаляется из системы и более не отображается в ленте, попытки доступа к детальной информации возвращают ошибку отсутствия ресурса.

Критерий А7: Администратор создаёт новый источник новостей с корректными атрибутами, источник появляется в списке доступных источников и может быть использован при создании статей.

Критерий А8: Администратор создаёт новый тег, тег становится доступным для ассоциации со статьями и отображается в списке всех тегов системы.

Критерий А9: Все операции изменения данных через API возвращают корректные HTTP-статусы, успешные операции создания возвращают код 201 с идентификатором созданного ресурса, операции обновления и удаления возвращают код 200 или 204 соответственно.

Критерий А10: Попытки неавторизованного доступа к защищённым endpoints возвращают статус 401, попытки выполнения операций без достаточных прав возвращают статус 403 с информативным сообщением об ошибке.
