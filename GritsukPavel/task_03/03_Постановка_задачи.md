# 1. Постановка задачи

Данный раздел содержит описание исходных данных, функциональных и нефункциональных требований к разрабатываемой системе управления откликами на вакансии, а также ограничения и критерии приёмки минимально работоспособного продукта.

## 1.1. Исходные данные

Система предназначена для управления процессом поиска работы и должна обеспечивать хранение и обработку информации о шести основных сущностях предметной области [1].

Сущность User представляет пользователя системы и содержит уникальный идентификатор, имя пользователя, адрес электронной почты, хеш пароля и роль в системе. Поддерживаются две роли: обычный пользователь и администратор [2].

Сущность Company описывает компанию-работодателя и включает идентификатор, название, необязательное текстовое описание и ссылку на пользователя-владельца. Каждая компания принадлежит конкретному пользователю [2].

Сущность Job представляет вакансию и содержит идентификатор, название должности, ссылку на компанию, ссылку на пользователя-владельца, статус вакансии, ссылку на текущий этап, информацию о зарплате, локации, URL вакансии, а также временные метки создания и обновления. Каждая вакансия связана с одной компанией и принадлежит конкретному пользователю [2].

Сущность Stage описывает этап отклика на вакансию и включает идентификатор, ссылку на вакансию, название этапа, порядковый номер и необязательную дату. Вакансия может проходить через несколько этапов, таких как подача резюме, скрининг, интервью, оффер или отказ [2].

Сущность Note представляет заметку к вакансии и содержит идентификатор, ссылку на вакансию, текстовое содержимое и временную метку создания. Пользователь может добавлять произвольное количество заметок к каждой вакансии для фиксации важной информации [2].

Сущность Reminder описывает напоминание, связанное с вакансией, и включает идентификатор, ссылку на вакансию, название напоминания, дату и время напоминания, флаг завершённости и временную метку создания. Напоминания позволяют пользователю отслеживать предстоящие события, связанные с откликами [2].

Схема данных предполагает следующие связи между сущностями. Один пользователь может создать множество компаний. Один пользователь может отслеживать множество вакансий. Одна компания может иметь множество вакансий. Одна вакансия может проходить через множество этапов. Одна вакансия может иметь множество заметок. Одна вакансия может иметь множество напоминаний [2].

Все связи реализуются через внешние ключи с поддержкой каскадного удаления для зависимых сущностей. При удалении пользователя удаляются все его компании и вакансии. При удалении компании удаляются все связанные вакансии. При удалении вакансии удаляются все связанные этапы, заметки и напоминания [2].

## 1.2. Функциональные требования

Функциональные требования определяют основные возможности системы, доступные различным категориям пользователей [3].

Минимально работоспособный продукт включает следующую обязательную функциональность. Система должна обеспечивать регистрацию новых пользователей и аутентификацию существующих через форму входа с использованием электронной почты и пароля [1]. Пользователи должны иметь возможность создавать, просматривать, редактировать и удалять информацию о компаниях [1]. Система должна позволять управление вакансиями с возможностью создания новой вакансии, просмотра списка всех вакансий пользователя, редактирования информации о вакансии и удаления вакансии [1].

Для каждой вакансии пользователь должен иметь возможность управлять этапами отклика, создавая новые этапы с указанием названия и порядкового номера, изменяя информацию об этапах и удаляя ненужные этапы [1]. Система должна обеспечивать создание, просмотр, редактирование и удаление текстовых заметок, связанных с вакансиями [1]. Аналогичные операции должны быть доступны для напоминаний с указанием даты и времени события [1].

Ключевой функциональностью является отображение вакансий в формате канбан-доски, где каждый этап представлен отдельной колонкой, а вакансии отображаются в виде карточек [1]. Пользователь должен иметь возможность перемещать карточки вакансий между этапами для отражения изменения статуса отклика [1].

Система должна поддерживать фильтрацию вакансий по компаниям, этапам и датам для упрощения поиска нужной информации [1]. Необходимо обеспечить просмотр статистики откликов с группировкой по компаниям [1].

Администратор системы должен иметь расширенные права, включая управление учётными записями пользователей, просмотр статистики по всем пользователям и доступ к системным настройкам [2]. Администратор должен иметь доступ к журналу событий системы для мониторинга активности [2].

Опциональная функциональность, расширяющая минимально работоспособный продукт, может включать экспорт данных пользователя в распространённые форматы для внешнего анализа [1], уведомления о приближающихся напоминаниях в реальном времени через WebSocket-соединение [2], а также возможность прикрепления файлов к заметкам и вакансиям [3].

## 1.3. Нефункциональные требования

Нефункциональные требования определяют качественные характеристики системы, касающиеся производительности, безопасности, удобства использования и технической реализации [4].

С точки зрения производительности система должна обрабатывать запросы пользователей с задержкой не более двух секунд при нормальной загрузке [4]. Интерфейс должен оставаться отзывчивым при работе с большими объёмами данных, включая отображение канбан-доски с десятками вакансий [4]. Серверная часть должна поддерживать одновременную работу нескольких десятков пользователей без деградации производительности [4].

Требования к безопасности включают защиту пользовательских паролей путём хеширования с использованием современных алгоритмов [5]. Система должна использовать JWT-токены для аутентификации с разделением на короткоживущие access-токены и долгоживущие refresh-токены [5]. Необходимо обеспечить защиту от распространённых веб-уязвимостей, включая XSS, CSRF и SQL-инъекции [5]. Refresh-токены должны храниться в защищённых HTTP-only cookies для предотвращения доступа из JavaScript-кода [5]. Серверная часть должна использовать CORS для ограничения доступа с неавторизованных доменов [5].

Система должна обеспечивать разграничение доступа на основе ролей. Обычные пользователи должны иметь доступ только к собственным данным, включая компании, вакансии, этапы, заметки и напоминания [2]. Администраторы должны иметь доступ ко всем данным в режиме чтения для целей модерации и аналитики [2].

С точки зрения удобства использования интерфейс должен быть интуитивно понятным и соответствовать современным стандартам веб-дизайна [3]. Система должна предоставлять информативные сообщения об ошибках валидации данных и недоступности сервера [3]. Интерфейс должен быть адаптивным и корректно отображаться на различных размерах экранов [3].

Технические требования включают использование современного технологического стека на основе JavaScript/TypeScript [1]. Серверная часть должна быть реализована с использованием Node.js и фреймворка Express для обработки HTTP-запросов [1]. Клиентская часть должна использовать библиотеку React для построения пользовательского интерфейса [1]. В качестве системы управления базами данных должна использоваться PostgreSQL [1]. Для работы с базой данных рекомендуется использовать ORM Prisma [1].

Система должна предоставлять REST API с соблюдением принципов архитектурного стиля REST [2]. Все ответы API должны быть в формате JSON с единообразной структурой, содержащей поле статуса и либо данные, либо информацию об ошибке [2]. API должно поддерживать пагинацию для операций получения списков с использованием параметров limit и offset [2].

Валидация данных должна выполняться как на клиентской стороне для немедленной обратной связи, так и на серверной стороне для обеспечения целостности данных [2]. Система должна проверять обязательность заполнения требуемых полей, соответствие данных заданным форматам, уникальность значений для соответствующих полей и допустимые диапазоны значений [2].

## 1.4. Ограничения и допущения

При разработке системы приняты следующие ограничения и допущения, определяющие границы функциональности минимально работоспособного продукта.

Система ориентирована на использование в среде современных веб-браузеров, поддерживающих актуальные стандарты HTML5, CSS3 и ECMAScript 2015 и выше [3]. Мобильные нативные приложения не входят в рамки текущей версии системы, однако веб-интерфейс должен быть адаптивным для использования на мобильных устройствах через браузер [3].

В минимально работоспособной версии не реализована функциональность прикрепления файлов к вакансиям или заметкам [3]. Экспорт данных в форматы Excel или PDF может быть добавлен в последующих версиях [3]. Уведомления о напоминаниях в реальном времени через WebSocket являются опциональной функциональностью и могут отсутствовать в базовой версии [2].

Предполагается, что система будет развёртываться в контролируемом окружении с гарантированной доступностью сервера базы данных PostgreSQL [1]. Резервное копирование и восстановление данных выходит за рамки разработки приложения и должно обеспечиваться инфраструктурными средствами [4].

Локализация интерфейса на языки, отличные от русского и английского, не предусмотрена в текущей версии [3]. Интеграция с внешними сервисами поиска работы или календарями не реализована [3].

Система не предоставляет механизмов совместного использования данных между пользователями [2]. Каждый пользователь работает только со своими вакансиями, компаниями и напоминаниями [2]. Функциональность командной работы или назначения задач другим пользователям отсутствует [2].

## 1.5. Критерии приёмки минимально работоспособного продукта

Для подтверждения готовности минимально работоспособного продукта должны быть выполнены следующие технические критерии [1].

База данных должна содержать таблицы для всех шести основных сущностей с корректно настроенными связями и ограничениями целостности [2]. Миграции базы данных должны применяться без ошибок, создавая требуемую структуру таблиц [1].

Серверная часть должна предоставлять REST API endpoints для всех основных операций, включая аутентификацию пользователей, управление компаниями, вакансиями, этапами, заметками и напоминаниями [2]. Каждый endpoint должен корректно обрабатывать входные данные, выполнять валидацию и возвращать ответ в установленном формате JSON [2].

Аутентификация должна работать с использованием JWT-токенов, обеспечивая защиту приватных endpoints [5]. Refresh-механизм должен позволять обновление access-токена без повторного ввода учётных данных [5]. При выходе из системы refresh-токен должен аннулироваться [5].

Авторизация должна корректно разграничивать доступ между ролями администратора и обычного пользователя [2]. Пользователи не должны иметь возможности просматривать или изменять данные других пользователей [2]. Администраторы должны иметь доступ к управлению пользователями и просмотру общей статистики [2].

Клиентская часть должна предоставлять пользовательский интерфейс для регистрации, входа и управления всеми сущностями системы [3]. Интерфейс должен корректно отображать ошибки валидации и недоступность сервера [3].

Канбан-доска должна отображать вакансии, сгруппированные по этапам, с возможностью перемещения карточек между колонками [1]. При перемещении карточки должно происходить обновление данных на сервере [1]. Канбан должен корректно отображать только вакансии текущего пользователя [2].

Система фильтрации должна позволять отбор вакансий по компаниям, этапам и временным периодам [1]. Результаты фильтрации должны обновляться без перезагрузки страницы [3].

Приложение должно успешно запускаться в режиме разработки с использованием предоставленных инструкций [1]. Должна быть возможность применения миграций базы данных и заполнения демонстрационными данными [1]. Backend и frontend должны корректно взаимодействовать через настроенные CORS-политики [5].

Код приложения должен соответствовать принятым в проекте соглашениям по форматированию и проходить проверку линтерами без критических ошибок [3]. Структура проекта должна быть логичной и понятной для дальнейшего развития [3].
